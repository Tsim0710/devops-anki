## 0. Что это и в каком состоянии

Пайплайн, который превращает теорию и собесовые вопросы по DevOps в колоду карточек.
Источник правды — YAML в этом репозитории. Сборка автоматическая через CI.
Иван — middle DevOps, готовится к собесам; цель двойная: качать глубину
и освежать базу.

**Текущее состояние: 1088 карт, 7 доменов закрыто, 5 не начато.**
Актуальные цифры и покрытие — в [`plans/README.md`](plans/README.md), он
генерируется и не устаревает.

**Ты работаешь прямо в репозитории**: создаёшь и правишь файлы, запускаешь сборку,
коммитишь сам. Не выдавай YAML «на вставку».

**В сообщения коммитов не добавляй строку соавторства и упоминания инструментов** —
решение Ивана от 07.09.2026, история репозитория была специально от них очищена.

## 1. С чего начинать в новом чате

Каркас собран, содержимое наполняется. Порядок при подключении к работе:

1. **Прочитай [`plans/README.md`](plans/README.md)** — что уже закрыто и что нет.
2. **Перед генерацией в домен** — `python build.py --index <domain>`: увидишь
   существующие карты, чтобы не плодить дубли и продолжить нумерацию `id`.
3. **Работай доменами**, а не вперемешку: домен закрывается целиком, потом
   регенерируются карты покрытия.
4. **После каждого батча — аудит** (раздел 8). Это не опция.

Окружение:

```bash
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
.venv/bin/python build.py --validate     # только проверка
.venv/bin/python build.py                # сборка apkg + тренажёра
.venv/bin/python -m pytest tests/ -q     # автотесты инвариантов
.venv/bin/python tools/coverage.py       # регенерация plans/
```

## 2. Структура репозитория

```
devops-anki/
  CLAUDE.md                 # этот файл
  taxonomy.yaml             # домены -> разрешённые subtopic (контролируемый словарь)
  schema.json               # JSON Schema для формы карты
  ids.lock                  # реестр всех id, когда-либо существовавших (append-only)
  cards/
    <domain>/<subtopic>.yaml    # один файл на подтему, ~10-25 карт
  sources/                  # снапшоты конспектов (раздел 7)
    manifest.json
    k8s.md  networks.md
  plans/                    # карты покрытия, генерируются
    README.md               # индекс: статус всех доменов
    <domain>-coverage.md
    notes.yaml              # текстовая часть карт покрытия, правится руками
  web/drill.html            # шаблон веб-тренажёра, карты подставляются на сборке
  tools/coverage.py         # генератор plans/
  build.py                  # cards/**/*.yaml -> apkg + тренажёр + manifest
  tests/test_build.py       # автотесты инвариантов
  requirements.txt
  .github/workflows/build.yml
  build/                    # артефакты (gitignore): devops.apkg, index.html, manifest.json
  README.md
```

**Правило дробления файлов.** Один файл на subtopic: `cards/<domain>/<subtopic>.yaml`.
Новый домен раскладывается так **с первого батча**, а не когда станет больно —
`cards/k8s.yaml` дорос до 8300 строк, прежде чем его разложили.

Файл — только удобство редактирования. На группировку в колоде он не влияет:
дек задаётся полем `domain`, тема — полем `subtopic`. `build.py` собирает
`cards/**/*.yaml` рекурсивно, поэтому **перекладывание карт между файлами
полностью безопасно**: GUID считается из `id`, путь в него не входит.

## 3. Домены и subtopic

| закрыты | не начаты |
|---|---|
| `k8s`, `networks`, `terraform`, `ansible`, `cicd`, `linux`, `docker` | `git`, `security`, `observability`, `gcp`, `cloudflare` |

- **Jenkins** — subtopic внутри `cicd`, не домен. **Хостинг кода** — subtopic внутри `git`.
- Кандидаты на будущее: `databases`, `bash-scripting`, `messaging`. Пустые домены
  заранее не заводить.

**Контролируемый словарь subtopic.** Все допустимые subtopic перечислены
в `taxonomy.yaml`. Не придумывай их на лету: нужна новая — сначала добавь
в `taxonomy.yaml` единообразным kebab-case, потом используй. CI фейлит карту
с subtopic не из словаря. Это защита от зоопарка тегов
(`probes` / `Probes` / `liveness-probe` как три разных набора).

Переименование subtopic безопасно — это тег, а не дек. Меняешь значение
в `taxonomy.yaml` и в картах, тег на устройстве обновляется. `id` при этом
**не трогается никогда**.

## 4. Схема карты

```yaml
- id: k8s-probes-001        # вечный непрозрачный ключ; НИКОГДА не меняется
  domain: k8s
  subtopic: probes          # обязан быть в taxonomy.yaml
  difficulty: middle        # junior | middle | senior
  source: theory            # theory | interview | web | core (можно список)
  type: basic               # basic | mcq (по умолчанию basic)
  situational: false        # true только для ситуационных собесовых карт
  verified: false           # true ставит только Иван, после вычитки
  deprecated: false         # true = выведена из оборота, но не удалена (раздел 5)
  prompt: |
    Текст вопроса. RU. Термины, команды, код — EN.
    Markdown разрешён: **жирный**, списки, `инлайн-код`, блоки кода.
  options:                  # только для type: mcq, от 3 до 5 вариантов
    a: "..."
    b: "..."
    c: "..."
  answer: |
    mcq -> одна буква из options.
    basic -> эталонный ответ, по которому Иван себя оценивает.
  explanation: |
    ПОЧЕМУ ответ такой. Не пересказ ответа. Глубина растёт с difficulty.
  ref: "sources/k8s.md#M13-3, ссылка на доку, или цитата вопроса для source: interview"
```

### Правила по `id`

- `id` — **вечный непрозрачный ключ**. Из него детерминированно считается GUID
  заметки, а GUID — единственное, что связывает карту в репозитории с историей
  повторений.
- Формат при создании `<domain>-<subtopic>-<NNN>`, но после создания это просто
  строка. Карта переехала в другую subtopic — меняется поле `subtopic`, `id`
  остаётся. **Несовпадение id и subtopic — норма, не повод для рефакторинга.**
- Смена `id` = потеря истории повторений. Никогда.
- `id` удалённой карты не переиспользуется: все выданные лежат в `ids.lock`,
  валидатор падает при попытке выдать снятый id заново.

### Правила по YAML (проверено на PyYAML 6, грабли реальные)

- **Многострочные поля — только `|` (literal), никогда `>` (folded).**
  `>` склеивает строки и ломает отступы внутри кода.
- Строковые значения — либо в `|`, либо в кавычках. Неквотированный текст
  с двоеточием — это `ScannerError`.
- YAML 1.1: `no` → `False`, `on` → `True`, `off` → `False`. Такие значения
  только в кавычках.

### Правила контента

- **Атомарность:** один *извлекаемый факт* на карту.
- **Но не дроби до интерференции.** Две карты, которые можно перепутать
  при повторении, мешают вспоминаться обе. Одна карта = один вопрос,
  на который есть ровно один правильный способ ответить.
- **Язык:** вопрос и пояснение RU, термины и код EN. Термины не переводить.
- **explanation отвечает на «почему»**, а не повторяет `answer`.
- **basic — основа.** MCQ только там, где соль в различении близких вариантов.
  Распределение правильных букв держать ровным.
- **Варьируй конструкцию вопроса.** Однотипное «Чем X отличается от Y» на всю
  колоду мешает и учёбе, и проверке на интерференцию.

### Уровни

- **junior** — что это и зачем, базовый синтаксис, поведение по умолчанию.
- **middle** — рантайм-поведение, типовые грабли, trade-offs, «почему ломается».
- **senior** — edge-кейсы, взаимодействие механизмов, поведение под нагрузкой
  и при отказах, внутренности, обоснование архитектурных решений.

## 5. Модель колоды: деки, теги, объём

### Деки — по домену, и только по домену

**Дек = `DevOps::<domain>`.** Никакой вложенности.

Причина: при импорте `.apkg` Anki матчит заметки по GUID и обновляет поля,
но **не переносит существующие карты в другой дек**. Дек-на-subtopic означал бы
150+ деков, где каждое переименование темы оставляет карту в старом деке навсегда.
Деки в Anki — единица планирования, а не навигации.

### Теги — вся навигация

- `topic::<subtopic>`
- `difficulty::junior` | `middle` | `senior`
- `source::theory` | `interview` | `web` | `core` — по тегу на каждый источник
- `situational`, `unverified`, `deprecated`

### Объём: потолка нет

Решение Ивана от 04.09.2026: **потолка на подтему, домен и колоду нет.**
Критерий один — сколько в теме есть разных качественных вопросов, столько
карт и пишем.

Что при этом не отменяется, потому что это про качество, а не про объём:

- **Каждая карта закрывает отдельный извлекаемый факт.** Рост объёма идёт
  за счёт расширения покрытия, а не дробления уже покрытого.
- **Интерференция — враг.** Проверка после каждого батча обязательна (раздел 8).
- **Планка — «премиальный экземпляр».** Точная формулировка, проверенный факт,
  `explanation` объясняет механизм.
- **Все три уровня закрываются в одном проходе по теме.**

Рычаг перегрузки — на стороне повторений: тег `difficulty::senior` саспендится
одной операцией, если поток станет неподъёмным.

### Механизм удаления

`.apkg` аддитивен: удаление карты из YAML **не удаляет её с устройства**.
Поэтому удаления через YAML не существует:

- Карта получает `deprecated: true`, продолжает собираться, получает тег
  `deprecated` и не попадает ни в один фильтр.
- Раз в несколько недель Иван чистит `tag:deprecated` в Anki. Только после этого
  карту можно убрать из YAML — id остаётся в `ids.lock` навсегда.
- `build/manifest.json` со списком id, тегов и хешей содержимого позволяет
  видеть diff между сборками.

## 6. Сборка и CI

### Идентификаторы (без этого пайплайн бессмыслен)

- **GUID заметки** = `genanki.guid_for(card["id"])` — зависит **только** от `id`.
  Правка текста GUID не меняет.
- **`model_id` и `deck_id` — константы**, выведенные детерминированно из имени.
  Никакого `random`: случайный id создаёт новый notetype и дек при каждом импорте.

### Что производит `build.py`

| файл | назначение |
|---|---|
| `build/devops.apkg` | колода для Anki |
| `build/drill.html` | фрагмент тренажёра для публикации как артефакт |
| `build/index.html` | самостоятельная страница тренажёра для GitHub Pages |
| `build/manifest.json` | id, guid, теги, хеш содержимого — источник для `plans/` |

Режимы: без аргументов — полная сборка; `--validate` — только проверки;
`--index [domain]` — индекс существующих карт.

### Модели заметок

Поля фиксированы: добавление поля позже — schema change при импорте на устройстве.

- **basic**: `Prompt`, `Answer`, `Explanation`, `Meta`
- **mcq**: `Prompt`, `Options`, `AnswerLetter`, `AnswerText`, `Explanation`, `Meta` —
  на обороте **буква И полный текст** правильного варианта, иначе запоминается
  позиция, а не факт.
- `Meta` = `id` карты мелким шрифтом, чтобы найти её в репозитории с телефона.

### Рендеринг

Поля Anki — это HTML, поэтому:

- markdown конвертируется в HTML на сборке;
- всё, что не разметка, **экранируется**: `<pending>`, `srcIP > dstIP`, `A && B`
  обязаны доехать как текст;
- блоки кода → `<pre><code>`, CSS задаёт моноширинный шрифт и перенос;
- CSS обязан иметь `.nightMode`-варианты — устройство почти всегда в тёмной теме.

### Валидация (жёсткий fail, красный CI)

1. Карта валидна по `schema.json`.
2. `subtopic` есть в `taxonomy.yaml` для своего `domain`.
3. `id` уникален по всему репозиторию.
4. `id` не переиспользует снятый id из `ids.lock`.
5. `difficulty`, `source`, `type` — из разрешённых значений.
6. `type: mcq` → 3–5 `options`, `answer` — буква из ключей. `basic` → без `options`.
7. `situational: true` → только `type: basic`.
8. Совпадение нормализованного `prompt` — fail. Похожесть выше 0.85 — warning.

### Автотесты (`tests/`, гоняются в CI)

- **Детерминизм GUID**: две сборки подряд дают одинаковый набор
  `(guid, notetype, deck, поля)`. Сравнивается **извлечённое содержимое**,
  а не хеш файла: `.apkg` — zip с sqlite, побайтово не воспроизводим.
- **Устойчивость GUID к правке** и **чувствительность к смене `id`**.
- **Рендеринг**: `<pending>` экранируется, fenced-блок даёт `<pre><code>`.
- **Теги**: `source: [theory, interview]` даёт два тега.

### CI

- Триггеры: push в `cards/**`, **`web/**`**, `taxonomy.yaml`, `schema.json`,
  `build.py`, `tests/**`, `requirements.txt`, сам workflow; и теги `v*`.
- Шаги: validate → pytest → build.
- На push в `main`: публикация тренажёра на GitHub Pages.
- На тег `v*`: `.apkg` как release asset. Релиз только по тегу.

> **Грабля, стоившая времени:** правка `web/drill.html` не запускала сборку,
> потому что `web/**` не было в триггерах. Пуш проходил, run не появлялся,
> страница оставалась прежней. Если изменение «не доехало» — проверяй сначала
> факт создания run, а не логи.

## 7. Источники контента

### Конспекты — через снапшот

Прямое чтение Google Docs коннектором на каждую тему не работает: доки
по ~250k символов не влезают в один ответ инструмента. Поэтому док один раз
выгружается в `sources/<domain>.md` и коммитится, а в `sources/manifest.json`
пишется `{doc_id, title, exported_at, sha256}`. Дальше вся генерация идёт
из файлов в репозитории. `source: theory`.

Конспекты есть только по `k8s` и `networks`. Остальные домены пишутся
по официальной документации, `source: core`.

### Провенанс: значение тега `source`

- `theory` — контент лёг из конспектов `sources/*.md`;
- `interview` — из файла собесовых вопросов;
- `web` — тема взята из веб-подборки, ответ написан по официальным докам;
- `core` — карта добавлена для полноты покрытия, вне перечисленного выше.

Список допустим, когда карта покрывает пересечение (`[theory, interview]`).

### Верификация

Вся генерация ставит `verified: false` → тег `unverified`. Флаг снимает только
Иван, после вычитки. Причина: ошибка в колоде дороже ошибки в конспекте —
она закрепляется повторениями.

Сомневаешься в факте (особенно senior edge-кейсы и номера версий) — проверь
по официальным докам. Не смог проверить — **не пиши карту**.

### Не подключать

**3000+ карт из Telethon-скрейпа — не используем.** Устарели, много дублей.

## 8. Процедура генерации

### Область покрытия — под собес, а не по конспектам

Конспекты в `sources/` — **якорь, а не потолок**: они задают стек, терминологию
и то, что Иван уже проходил. Что именно закрывать по subtopic, определяется тем,
**что реально спрашивают** на собесах junior/middle/senior. Темы нет в конспекте
или она раскрыта поверхностно — всё равно покрываешь полностью, по официальным
докам, с `source: core`.

### Порядок по каждой subtopic

1. **Наметь концепты темы** по трём уровням — это план покрытия, он страхует
   и от дыр, и от мусора «ради объёма». Показывать его отдельно **не нужно**:
   пиши карты сразу, отчитывайся результатом.
2. **Посмотри существующее**: `python build.py --index <domain>`. Не дублируй,
   продолжай нумерацию `id`. Пересечение с существующей картой — это не новая
   карта, а дополнение её `source`.
3. **Прочитай конспект**, если он есть: выровняй терминологию и примеры под стек
   Ивана (GCP, GitHub Actions, Terraform, Ansible, Cloudflare). Конспект устарел
   или противоречит докам — **не тиражируй ошибку, скажи**.
4. **Пиши карты.** Один концепт — одна карта. Для MCQ distractor'ы правдоподобные,
   а не очевидная чушь.
5. **Проверь факты** по официальным докам: версии, дефолты параметров, поведение
   при отказах.

### Обязательный аудит после батча

Не опция и не по настроению — три проверки:

```bash
# 1. интерференция: похожесть prompt, порог 0.62 (в CI боевой 0.85)
#    сравниваются только значимые слова: normalize_for_similarity в build.py
#    отбрасывает скелет вопроса, иначе всё тонет в парах «Чем X отличается от Y»
# 2. смешение алфавитов: латиница внутри кириллических слов
# 3. пересечение с другими доменами — особенно общие уроки
```

Что делать с находками:

- **Настоящая интерференция** — переписать одну из карт на другой стимул
  и другую цель извлечения, а не удалять факт.
- **Один концепт в двух контекстах** оставляют сознательно, если стимулы
  называют разные системы и практические выводы расходятся
  (`401`/`403` в HTTP и `Unauthorized`/`Forbidden` у apiserver).
- **Артефакт конструкции** — одинаковое начало вопроса при разном содержании —
  не интерференция, править не нужно.

### После закрытия домена

1. Дописать раздел в `plans/notes.yaml`: на чём держится домен, что нашли аудиты.
2. `python build.py && python tools/coverage.py` — карты покрытия перегенерируются.
3. Закоммитить вместе с картами.

## 9. Как это используется

**Основная поверхность — веб-тренажёр:** https://tsim0710.github.io/devops-anki/
Публичная страница без логина, обновляется автоматически при каждом пуше в `main`.
Выбор темы и уровня чипами, вопрос → ответ → знаю/не знаю, счёт и разбор ошибок
в конце подхода. Прогресс — в localStorage браузера, у каждого устройства свой.

Шаблон страницы — `web/drill.html`, карты вшиваются в неё на сборке тем же
рендерингом, что уходит в Anki, поэтому две поверхности не расходятся.

**Anki — вторая поверхность, для интервальных повторений.** `.apkg` собирается
всегда и лежит в релизе по тегу. Порядок: синк AnkiWeb → импорт → синк ещё раз.
Импорт на несинхронизированной коллекции даёт «one-way sync required» и теряет
накопленное на другой стороне.

Настройки импорта, проверенные по документации: «Импортировать прогресс обучения»
и «Импортировать конфигурации колод» — выключить; «Обновить записи» — **Всегда**
(источник правды git, а не коллекция); «Объединить типы записи» — выключено.

## 10. Чего НЕ делать

- Не меняй `id` существующей карты. Никогда.
- Не переиспользуй `id` из `ids.lock`.
- Не выдумывай subtopic мимо `taxonomy.yaml`.
- Не удаляй карты из YAML в обход `deprecated`.
- Не используй `>` для многострочных полей.
- Не генерируй `random` id для моделей и деков.
- Не копируй ответы из веб-подборок.
- Не подключай Telethon-карты.
- Не переводи технические термины на русский.
- Не ставь `verified: true` — это делает только Иван.
- Не пиши карту, факт для которой не смог проверить.
- Не тиражируй ошибку из конспекта, если она расходится с докой — скажи.
- Не пропускай аудит после батча.
- Не добавляй в коммиты строку соавторства и упоминания инструментов.
- Не правь `plans/*.md` руками — они генерируются.
