## 0. Что мы строим и зачем

Пайплайн, который превращает мою теорию и собесовые вопросы по DevOps в колоду Anki,
которую я гоняю с телефона, выбирая тему и сложность. Источник правды — git-репо с картами
в YAML. Сборка `.apkg` автоматическая через CI. Я — middle DevOps, готовлюсь к собесам;
цель двойная: и качать глубину, и освежать базу.

**Ты работаешь через Claude Code и пишешь прямо в репозиторий** (создаёшь/редактируешь файлы,
запускаешь сборку). Не выдавай YAML «на вставку» — коммить сам.

**Главный риск проекта — не техника, а объём.** Колода, которую забросили из-за долга
в 900 повторений, бесполезна. Всё, что написано ниже про лимиты и приоритеты, — не
пожелание, а несущая конструкция.

## 1. ПОРЯДОК РАБОТЫ В НОВОМ ЧАТЕ (строго)

Тема на старте **не важна**. Сначала — механизм, потом контент. Не начинай генерить карты
по темам, пока весь каркас не собран и не проверен end-to-end.

1. **Скаффолд репо** (структура в разделе 2).
2. **Сид** — 6 карт по probes в `cards/k8s.yaml`: разложены по junior/middle/senior,
   4 basic + 2 mcq. Это единственный контент на этом этапе — он нужен, чтобы проверить
   пайплайн, а не чтобы наполнить колоду.
3. **Автотесты** (`tests/`, гоняются в CI) — см. раздел 6.
4. **Ручная проверка end-to-end на живом Anki.** Я делаю её сам, ты готовишь инструкцию
   и ждёшь моего подтверждения. Проверяем ровно четыре вещи:
   - **a. Дублей нет.** Импортировал `.apkg` → импортировал ещё раз → число заметок не выросло.
   - **b. Правка доезжает.** Меняем `explanation` у карты → пересборка → импорт → текст на
     обороте обновился, интервал повторения сохранился.
   - **c. Смена difficulty заменяет тег, а не добавляет.** Меняем `difficulty: middle` →
     `senior` → пересборка → импорт → на карте должен остаться **только** `difficulty::senior`.
     Если остались оба — это ломает filtered decks, и мы чиним это до перехода к контенту
     (варианты: опции импорта в моей версии Anki, либо один тег `difficulty` с заменой,
     либо чистка тега вручную по расписанию). **Не проходи мимо этого пункта.**
   - **d. Смена subtopic доезжает.** Меняем `subtopic` у карты → импорт → тег `topic::` обновился.
     (Дек при этом не меняется — так и задумано, см. раздел 5.)
5. **Только после моего «ок» по п.4** — переход к наполнению по темам. На этом шаге запроси
   у меня источники (раздел 7).

## 2. Структура репозитория

```
devops-anki/
  CLAUDE.md                 # этот файл
  taxonomy.yaml             # домены -> разрешённые subtopic (контролируемый словарь)
  schema.json               # JSON Schema для валидации формы карты
  ids.lock                  # реестр всех id, когда-либо существовавших (append-only)
  cards/
    k8s/                    # один файл на subtopic: probes.yaml, pods.yaml, ...
    networks/
    linux.yaml
    docker.yaml
    cicd.yaml
    terraform.yaml
    ansible.yaml
    gcp.yaml
    cloudflare.yaml
    git.yaml
    observability.yaml
    security.yaml
  sources/                  # снапшоты исходников (раздел 7)
    manifest.json
    k8s.md
    networks.md
  build.py                  # cards/**/*.yaml -> build/devops.apkg
  tests/
    test_build.py
  requirements.txt          # genanki, pyyaml, jsonschema, markdown
  .github/workflows/build.yml
  build/                    # артефакты сборки (gitignore): devops.apkg, manifest.json
  README.md
```

**Правило дробления файлов (уточнено 04.09.2026).** Домен без потолка на число карт
неизбежно вырастает в неподъёмный файл: `cards/k8s.yaml` дошёл до 8300 строк, прежде чем
его разложили. Поэтому:

- **один файл на subtopic**: `cards/<domain>/<subtopic>.yaml`;
- новый домен раскладывается так **с первого батча**, а не когда станет больно;
- файл — это только удобство редактирования, на группировку в Anki он НЕ влияет:
  дек задаётся полем `domain`, тема — полем `subtopic`.

`build.py` собирает `cards/**/*.yaml` рекурсивно, поэтому **перекладывание карт между
файлами полностью безопасно**: GUID считается из `id`, а путь в него не входит.

## 3. Домены и subtopic

Домены (стартовый набор): `k8s, networks, linux, docker, cicd, terraform, ansible, gcp,
cloudflare, git, observability, security`.

- **Jenkins** — subtopic внутри `cicd` (наряду с `github-actions`, `gitlab-ci`, `argocd`), не домен.
- **Хостинг кода** (GitHub / GitLab / Bitbucket как платформы) — subtopic внутри `git`.
- Кандидаты на будущее: `databases`, `bash-scripting`, `messaging`. Не заводи пустые домены заранее.

**Контролируемый словарь subtopic.** Все допустимые subtopic каждого домена перечислены в
`taxonomy.yaml`. Ты НЕ придумываешь subtopic на лету — сверяешься со словарём. Нужна новая
subtopic — сперва добавь её в `taxonomy.yaml` (осознанно, единообразным kebab-case), потом
используй. CI обязан фейлить карту с subtopic не из словаря. Это защита от зоопарка тегов
(`probes` / `Probes` / `liveness-probe` как три разных набора).

**Переименование subtopic теперь безопасно** — subtopic это тег, а не дек (раздел 5).
Меняешь значение в `taxonomy.yaml` и в картах, тег на устройстве обновляется. `id` при этом
НЕ трогается никогда (раздел 4).

## 4. Схема карты (YAML)

Каждый файл в `cards/` — список карт. Одна карта:

```yaml
- id: k8s-probes-001        # вечный непрозрачный ключ; НИКОГДА не меняется и не переиспользуется
  domain: k8s
  subtopic: probes          # обязан быть в taxonomy.yaml
  difficulty: middle        # junior | middle | senior
  source: theory            # theory | interview | web | core (можно список: [theory, interview])
  type: basic               # basic | mcq (по умолчанию basic)
  situational: false        # true только для ситуационных собесовых карт (раздел 7)
  verified: false           # true ставлю Я после вычитки. Генерация всегда пишет false.
  deprecated: false         # true = карта выведена из оборота, но не удалена (раздел 5)
  prompt: |
    Текст вопроса. RU. Технические термины и код — EN (readinessProbe, endpoints).
    Markdown разрешён: **жирный**, списки, `инлайн-код` и блоки ```yaml ... ```
  options:                  # только для type: mcq, от 3 до 5 вариантов
    a: "..."
    b: "..."
    c: "..."
    d: "..."
  answer: |
    mcq -> одна буква из options.
    basic -> эталонный ответ (модельная формулировка, по которой я себя оцениваю).
  explanation: |
    ПОЧЕМУ ответ такой. Не пересказ ответа. Глубина растёт с difficulty.
  ref: "откуда карта: sources/k8s.md#M13-3, ссылка, или цитата вопроса для source: interview"
```

### Правила по `id` (важно, тут легко всё сломать)

- `id` — **вечный непрозрачный ключ**. Из него детерминированно считается GUID заметки,
  а GUID — единственное, что связывает карту в репо с историей повторений на телефоне.
- Формат при создании: `<domain>-<subtopic>-<NNN>`, но **после создания это просто строка**.
  Если карта переехала в другую subtopic — меняется поле `subtopic`, а `id` остаётся старым.
  **Несовпадение id и subtopic — норма, не повод для рефакторинга.**
- Смена `id` = потеря всей истории повторений по этой карте. Никогда.
- `id` удалённой карты не переиспользуется. Все когда-либо выданные id лежат в `ids.lock`,
  валидатор падает при попытке выдать id из реестра заново.

### Правила по YAML (проверено на PyYAML 6, грабли реальные)

- **Все многострочные поля — через `|` (literal), никогда через `>` (folded).**
  `>` склеивает строки в одну и ломает отступы внутри кода.
- Все строковые значения — либо в `|`, либо в кавычках. Неквотированный текст с двоеточием
  (`Что делает kubectl get po: разбор`) — это `ScannerError`.
- Осторожно с YAML 1.1: `no` → `False`, `on` → `True`, `off` → `False`. Такие значения только в кавычках.

### Жёсткие правила контента

- **Атомарность:** один *извлекаемый факт* на карту. Никаких «перечислите 5 отличий» одной
  картой — это 5 карт.
- **Но не дроби до интерференции.** «Что такое readinessProbe» / «Зачем нужен readinessProbe» /
  «Чем readinessProbe отличается от liveness» — это три почти одинаковых стимула, они мешают
  друг другу вспоминаться. Одна карта = один вопрос, на который есть ровно один правильный
  способ ответить. Если две карты можно перепутать при повторении — их надо слить или
  переформулировать так, чтобы вопросы явно разошлись.
- **Язык:** вопрос и пояснение — RU; термины, команды, код, YAML — EN. Не переводи термины.
- **explanation всегда отвечает на «почему»**, а не повторяет `answer`.
- **basic — основа.** MCQ — только там, где вся соль в различении близких вариантов
  (напр. liveness vs readiness при провале). Не делай MCQ ради MCQ. Держи распределение
  правильных букв ровным — иначе я запомню позицию, а не факт.

### Уровни сложности (рубрика)

- **junior** — что это и зачем, базовый синтаксис/команды, поведение по умолчанию. Чистый recall.
- **middle** — рантайм-поведение, типовые грабли, trade-offs, сравнение близких механизмов,
  «почему ломается».
- **senior** — edge-кейсы, взаимодействие механизмов, поведение под нагрузкой/при отказах,
  «что произойдёт при X во время Y», внутренности, обоснование архитектурных решений.

## 5. Модель колоды: деки, теги, бюджет

### Деки — по домену, и только по домену

**Дек = `DevOps::<domain>`.** Двенадцать деков, больше никакой вложенности.

Причина: при импорте `.apkg` Anki матчит заметки по GUID и обновляет поля, но **не переносит
уже существующие карты в другой дек**. Дек-на-subtopic означал бы 150+ деков, каждое
переименование темы оставляло бы карту в старом деке навсегда, а лимиты новых карт в день
настраивались бы в ста местах. Деки в Anki — единица планирования, а не навигации.

### Теги — вся навигация

- `topic::<subtopic>` — тема
- `difficulty::junior` | `difficulty::middle` | `difficulty::senior`
- `source::theory` | `source::interview` | `source::web` (по тегу на каждый источник в списке)
- `situational` — если `situational: true`
- `unverified` — если `verified: false`
- `deprecated` — если `deprecated: true`

### Как я этим пользуюсь

Тема + сложность — через filtered deck:
```
deck:DevOps::k8s tag:topic::probes tag:difficulty::middle -tag:deprecated
```
Домен целиком по уровню:
```
deck:DevOps::networks tag:difficulty::junior -tag:deprecated
```

**Рычаг объёма:** если поток повторений станет неподъёмным — я саспендю
`tag:difficulty::senior` одной операцией, колода сжимается почти вдвое, прогресс не теряется,
перед собесом возвращаю. Саспенд — состояние карты, импорт его не сбрасывает. **Но новые
карты приезжают активными**, поэтому после каждой крупной генерации я пересаспендю по тегу.

### Механизм удаления

`.apkg` — аддитивный формат: удаление карты из YAML **не удаляет её с телефона**.
Поэтому удаления через YAML не существует. Вместо этого:

- Карта, которую я больше не хочу учить, получает `deprecated: true`.
- Она продолжает собираться, но получает тег `deprecated` и **не** попадает ни в один мой
  фильтр (во всех запросах стоит `-tag:deprecated`).
- Раз в несколько недель я чищу `tag:deprecated` вручную в Anki. Только после этого карту
  можно физически убрать из YAML — id при этом остаётся в `ids.lock` навсегда.
- `build/manifest.json` (список всех id с их тегами и хешем контента) собирается каждой
  сборкой и позволяет увидеть diff между версиями.

### Объём: потолка нет

Решение Ивана от 04.09.2026, отменяет прежние лимиты: **потолка на подтему, домен
и колоду больше нет.** Критерий один — сколько в теме есть разных качественных вопросов,
столько карт и пишем. «Много не мало».

Что при этом НЕ отменяется, потому что это про качество, а не про объём:

- **Каждая карта закрывает отдельный извлекаемый факт.** Сорок карт, где половина —
  переформулировки одного и того же, хуже двадцати разных. Рост объёма идёт за счёт
  расширения покрытия, а не за счёт дробления уже покрытого.
- **Интерференция остаётся врагом.** Две карты, которые можно перепутать при повторении,
  мешают вспоминаться обе. Проверка на похожесть prompt — обязательный шаг после
  каждого батча, порог 0.62, а не только боевые 0.85 в CI.
- **Планка содержания — «премиальный экземпляр».** Карту пишем так, как будто по ней
  будет учиться человек, который хочет разобраться до конца: точная формулировка,
  проверенный факт, `explanation` объясняет механизм, а не пересказывает ответ.
- **Все три уровня закрываются в одном проходе по теме**, а не junior+middle сейчас
  и senior когда-нибудь.

Рычаг перегрузки на стороне повторений сохраняется: тег `difficulty::senior` саспендится
одной операцией, если поток станет неподъёмным.

## 6. Сборка (`build.py`) и CI

### Идентификаторы (без этого пайплайн бессмыслен)

- **GUID заметки** = `genanki.guid_for(card["id"])` — детерминированный, зависит **только**
  от `id`. Правка текста карты GUID не меняет.
- **`model_id` и `deck_id` — константы**, выведенные детерминированно из имени, например
  `(int(hashlib.sha1(f"model:{name}".encode()).hexdigest(), 16) % (1 << 30)) + (1 << 30)`.
  Никакого `random.randrange` (как в примерах genanki): случайный id на каждой сборке
  создаёт новый notetype и новый дек при каждом импорте.

### Модели заметок

Поля фиксируются **сейчас**: добавление поля позже — это schema change при импорте у меня
на устройстве. Поэтому `Meta` заводится сразу, даже если пока пустое.

- **basic**: `Prompt`, `Answer`, `Explanation`, `Meta`
  - Front: `{{Prompt}}`
  - Back: `{{FrontSide}}` + разделитель + `{{Answer}}` + `{{Explanation}}`
- **mcq**: `Prompt`, `Options`, `AnswerLetter`, `AnswerText`, `Explanation`, `Meta`
  - Front: `{{Prompt}}` + `{{Options}}`
  - Back: `{{FrontSide}}` + разделитель + **буква И полный текст правильного варианта** +
    `{{Explanation}}`. Одна буква на обороте недопустима — я запомню «ответ b», а не факт.
- `Meta` = `id` карты (мелким шрифтом внизу) — чтобы я мог найти карту в репо прямо с телефона.
- Сортировочное поле — `Prompt`.

### Рендеринг

Поля Anki — это HTML. Поэтому:

- `prompt` / `answer` / `explanation` / `options` пишутся в markdown и **конвертируются в HTML
  на сборке** (`markdown` с расширением `fenced_code`).
- Всё, что не разметка, **экранируется**: `<pending>`, `srcIP > dstIP`, `A && B` обязаны
  доехать до экрана как текст, а не как теги.
- Блоки кода → `<pre><code>`; CSS модели задаёт моноширинный шрифт, `white-space: pre-wrap`
  и горизонтальный скролл для длинных строк.
- CSS **обязан** иметь `.nightMode`-варианты для фона и текста кодовых блоков — телефон
  почти всегда в тёмной теме.

### Валидация (всё это — жёсткий fail, красный CI)

1. Карта валидна по `schema.json`.
2. `subtopic` есть в `taxonomy.yaml` для своего `domain`.
3. `id` уникален по всему репо.
4. `id` не является переиспользованием id из `ids.lock`, снятого с другой карты.
5. `difficulty`, `source`, `type` — из разрешённых значений.
6. `type: mcq` → 3–5 `options`, `answer` — буква из ключей `options`.
   `type: basic` → `options` отсутствует.
7. `situational: true` → только `type: basic`.
8. Совпадение нормализованного `prompt` у двух карт — fail. Высокая похожесть (>0.85) — warning
   со списком пар, чтобы я посмотрел на интерференцию.
9. Превышение потолка карт на subtopic/домен (раздел 5) — warning с числами, не fail.

### Автотесты (`tests/`, гоняются в CI)

- **Детерминизм GUID:** две сборки подряд дают одинаковый набор `(guid, notetype, deck, поля)`.
  Сравнивать нужно **извлечённое содержимое**, а не хеш файла: `.apkg` — это zip с sqlite,
  побайтово он не воспроизводим.
- **Устойчивость GUID к правке:** меняем `explanation` в фикстуре → GUID тот же.
- **Чувствительность GUID к id:** меняем `id` → GUID другой.
- **Рендеринг:** карта с `<pending>` и fenced-блоком даёт экранированный HTML с `<pre><code>`,
  а не съеденный тег и не схлопнутые переносы.
- **Теги:** карта с `source: [theory, interview]` даёт два тега `source::`.

### `.github/workflows/build.yml`

- Триггеры: push в `cards/**`, `taxonomy.yaml`, `schema.json`, `build.py`, `tests/**`; и теги `v*`.
- Шаги: setup Python → install deps → **validate (жёсткий fail)** → pytest → `build.py`.
- На push: `devops.apkg` и `manifest.json` как **artifact** (для проверки, что собралось).
- На тег `v*`: тот же `.apkg` как **release asset**. Релиз только по тегу — иначе через месяц
  в репо триста релизов.

## 7. Источники контента

### Теория — мои Google Docs, но через снапшот

Прямое чтение доков коннектором на каждую тему не работает: мои доки по k8s и networks —
по ~250k символов каждый, целиком в один ответ инструмента они не влезают.

Поэтому: **один раз выгружаем док в `sources/<domain>.md`** и коммитим. В `sources/manifest.json`
пишем `{doc_id, title, exported_at, sha256}`. Дальше вся генерация идёт из файлов в репо.
Это даёт воспроизводимость, нормальный `ref` (`sources/k8s.md#M13-3`) и возможность увидеть,
что в доке изменилось, когда я его правлю. `source: theory`.

### Файл собесовых вопросов

- Обычные фактические вопросы → атомарные карты, `source: interview`, оригинал в `ref`.
- **Максимально ситуационные** («у тебя упало X в проде, что делаешь») → standalone-карта,
  `situational: true`, не дроби на атомы. Таких карт держим мало и осознанно: развёрнутый
  ответ на 10 строк плохо ложится на самооценку Again/Good и тормозит сессию. Ориентир —
  не больше 5–7 на домен.
- Дерево ситуаций — **отложено**, сейчас не проектируем.

### Веб-подборки

Берём из них **только список тем** — что реально спрашивают. Ответы пишешь сам по авторитетным
источникам (официальные доки), чужие ответы не копируешь: в подборках их часто пишут неверно.
`source: web`.

### Провенанс: значение тега `source`

- `theory` — контент лёг из моих конспектов (`sources/*.md`);
- `interview` — из моего файла собесовых вопросов (реальные вопросы);
- `web` — тема взята из веб-подборки, ответ написан тобой по официальным докам;
- `core` — карта добавлена тобой для полноты покрытия темы, вне перечисленного выше.

Список допустим, когда карта покрывает пересечение (`[theory, interview]`).

### Не подключать

**3000+ карт из Telethon-скрейпа — НЕ используем.** Устарели, много дублей.

### Дедуп и порядок работы над темой

Перед генерацией в тему **всегда** сначала смотри существующие карты через
`python build.py --index <domain>` — он печатает `id / subtopic / difficulty / первые 80
символов prompt`. Читать все YAML домена целиком при 400 картах бессмысленно.

Если тема покрыта и теорией, и собесами — одна карта, в `source` перечисли оба
(`[theory, interview]`).

### Верификация

Вся генерация ставит `verified: false` → карта получает тег `unverified`. Я снимаю флаг
после вычитки. Причина: ошибка в Anki дороже ошибки в конспекте — её я закреплю повторениями.
Сомневаешься в факте (особенно senior edge-кейсы) — проверь по официальным докам, не выдумывай.
Не можешь проверить — не пиши карту.

## 8. Процедура генерации карт

### Область покрытия — под собес, а не по конспектам

Конспекты в `sources/` — **якорь, а не потолок**: они задают мой стек, терминологию и то,
что я уже проходил. Что именно нужно закрыть по subtopic, определяется тем, **что реально
спрашивают на собесах** junior/middle/senior по этой теме. Темы нет в конспекте или она
раскрыта поверхностно — всё равно покрываешь полностью, по официальным докам, с `source: core`.

### Порядок работы по каждой subtopic

1. **Карта концептов.** Сперва набросай список концептов темы, которые стоит проверить,
   разложив по трём уровням. Это план покрытия: по нему пишутся карты, он же страхует
   и от дыр, и от мусора «ради объёма». Карту концептов показывай мне до генерации.
2. **Существующие карты.** `python build.py --index <domain>` — посмотри, что уже есть.
   Не дублируй, продолжай нумерацию `id`. Пересечение с существующей картой — это не новая
   карта, а дополнение её `source`.
3. **Мои конспекты.** Прочитай `sources/<domain>.md` по теме: выровняй терминологию и примеры
   под мой стек (GCP, GitHub Actions, Terraform, Ansible, Cloudflare), учти, что я уже
   проходил. Если конспект устарел или противоречит докам — **не тиражируй ошибку, скажи мне**.
4. **Генерация.** Закрываешь карту концептов картами: один концепт — одна карта. Разброс
   по уровням: junior recall → middle поведение и грабли → senior edge и взаимодействие
   механизмов. Для MCQ distractor'ы должны быть правдоподобными (близкими, но неверными),
   а не очевидной чушью. `explanation` объясняет ПОЧЕМУ.
5. **Проверка фактов — критично.** Раз покрытие выходит за конспекты, много контента идёт
   из твоих знаний. Проверяй по официальным докам: senior edge-кейсы, номера версий, дефолты
   параметров, поведение при отказах. Не уверен — сверься; всё ещё не уверен — **не выдумывай,
   скажи мне**. Ложная карта хуже отсутствующей: её я закреплю повторениями.

### Как покрытие уживается с бюджетом

Бюджет из раздела 5 (~25 карт на subtopic, 1200–1500 на колоду) — потолок, а карта
концептов — план. Когда концептов на тему больше, чем влезает в бюджет:

- **не раздувай молча.** Покажи мне карту концептов, отметь, что не влезает, и предложи рез;
- режь по частоте на собесах, а не по «интересности»: сначала выпадает senior-экзотика,
  последним — middle-поведение и типовые грабли;
- лучше 20 карт, закрывающих 20 разных концептов, чем 40, где половина — переформулировки.

Разброс по уровням при горизонте 2–3 месяца: сначала слой junior+middle по всем subtopic
домена, senior — вторым проходом и только по темам, которые реально глубокие.

## 9. Как я это использую

1. CI собирает `.apkg` (artifact на push, release asset на тег).
2. Скачиваю: с компа — из релиза/артефакта; с телефона — из релиза (для этого репо
   должно быть публичным, иначе с телефона качается только через логин).
3. Импортирую в Anki.
4. **Железное правило: синк AnkiWeb до импорта и синк сразу после.** Импорт на устройстве,
   которое не синкалось, приводит к «one-way sync required» и потере того, что накопилось
   на другой стороне. Импортировать можно где угодно — но только на синхронизированной коллекции.
5. Учу через filtered decks (раздел 5). Картинок пока нет, только текст и код.

## 10. Чего НЕ делать

- Не генерь контент по темам, пока каркас не собран и я не подтвердил ручную проверку (раздел 1).
- Не выдумывай subtopic мимо `taxonomy.yaml`.
- Не меняй `id` существующей карты. Никогда.
- Не переиспользуй `id` из `ids.lock`.
- Не удаляй карты из YAML в обход `deprecated` (раздел 5).
- Не используй `>` для многострочных полей в YAML.
- Не генерируй `random` id для моделей и деков.
- Не копируй ответы из веб-подборок.
- Не подключай Telethon-карты.
- Не делай compound-карты и не переводи технические термины на русский.
- Не превышай бюджет карт молча — если тема просит больше, скажи и объясни.
- Не ставь `verified: true` сам.
- Не начинай генерацию темы без карты концептов и без `--index` по домену.
- Не тиражируй ошибку из моего конспекта, если она расходится с официальной докой — скажи мне.
- Не пиши карту, факт для которой не смог проверить.
