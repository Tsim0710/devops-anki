# M1. Архитектура кластера  

## **M1. Архитектура кластера**

**Одной фразой:** кластер = «мозг» (control plane — решает и хранит) + «руки» (worker nodes — запускают контейнеры), и вся связь идёт через одну дверь — kube-apiserver.

### **ð§  Ментальная модель**

Авиадиспетчерская. Вышка (control plane) не летает — держит карту «кому куда» и раздаёт указания через одну радиочастоту (apiserver). Пилоты (kubelet на узлах) исполняют и репортят статус назад. Никто не звонит мимо вышки и не лезет в её базу напрямую. etcd — это та самая база (единственный источник истины), apiserver — единственная дверь к ней. get любого ресурса = чтение записи из etcd, а НЕ опрос узлов.

### **Что важно знать**

  - **Зачем вообще оркестратор.** Docker запускает контейнер на *этой* машине — и на этом его ответственность кончается. Всё остальное без оркестратора делаешь руками: поднять упавшее, выбрать узел под нагрузку, переселить всё с умершего железа, выкатить версию без даунтайма, найти соседний сервис по имени, добавить реплик под пик. Kubernetes — это **не удобный запуск контейнеров, а петля, которая держит заявленное состояние на парке машин**. Формулировка для собеса: compose/ansible описывают, **что сделать сейчас**; куб описывает, **что должно быть верно всегда**, и сам это чинит.
  - **Control plane:** kube-apiserver (единственная дверь, всё через него) · etcd (key-value БД, единственный источник истины — всё состояние кластера тут) · kube-scheduler (решает, на какой узел сажать под — только решает и записывает, сам не запускает) · kube-controller-manager (пачка контроллеров, крутят reconcile spec→status).
  - **cloud-controller-manager** **(CCM)** — пятый компонент control plane, отдельный процесс/под, есть только в облаке. Внутри три контроллера: *node* — спрашивает облачный API, жива ли VM, проставляет node.spec.providerID и снимает стартовый taint node.cloudprovider.kubernetes.io/uninitialized (пока не снят — на узел не сядет ни один под) · *route* — прописывает маршруты до pod-подсетей в VPC · *service* — на Service type: LoadBalancer идёт в облако за настоящим балансировщиком. **Актор облачного LB — именно CCM**, не kube-proxy и не ingress-controller. **Почему вынесен:** чтобы код каждого облака не был вкомпилен в ядро куба и релизился своим циклом; в 1.31 in-tree cloud-провайдеры окончательно удалены → внешний CCM теперь единственный путь. На bare-metal (прод под Deckhouse) CCM нет вовсе → Service type: LoadBalancer вечно висит \<pending\>, пока не поставишь MetalLB или аналог.
  - **Worker node:** kubelet (агент: берёт spec у apiserver → просит containerd запустить контейнеры → следит за здоровьем → пишет status назад) · kube-proxy (программирует сетевые правила Service) · containerd (реально запускает контейнер — не Docker\!).
  - **spec.nodeName** **— шов между scheduler и kubelet.** Scheduler ничего не запускает, он делает **одну запись**: проставляет nodeName в объекте пода (через подресурс binding). Kubelet каждого узла watch'ит поды со **своим** nodeName и берёт в работу только их. Отсюда два следствия: под с руками прописанным nodeName стартует вообще без scheduler'а, а Pending — это по сути «под с пустым nodeName».
  - **Три способа, которыми под попадает на узел, и имя пода выдаёт способ:** *static pod* (\<компонент\>-\<нода\>: kubelet поднимает из файла на диске узла, scheduler не участвует) · *DaemonSet* (\<имя\>-\<1 хэш\>: по поду на каждый узел) · *Deployment* (\<имя\>-\<2 хэша\>: обычная нагрузка, scheduler размещает один раз).
  - **Курица-яйцо** (кто запустил apiserver, если всё запускается через apiserver?) решается static pod'ами: kubelet читает /etc/kubernetes/manifests/ напрямую и поднимает apiserver/etcd/scheduler/controller-manager БЕЗ участия apiserver. Так control plane и стартует с нуля.
  - **Mirror pod — зеркало static pod'а в API.** Static pod физически живёт файлом на узле, но kubelet заводит в apiserver его read-only копию: с ownerReferences на **Node** (не на контроллер) и аннотацией kubernetes.io/config.source: file. Поэтому kubectl delete pod kube-apiserver-\<нода\> «удаляет» под, а он возвращается за секунду с тем же именем — ты удалил зеркало, а источник лежит на диске. Правится только файлом в /etc/kubernetes/manifests/.
  - **Leader election: в HA-control-plane контроллеры работают в одиночку.** Запущено по нескольку kube-controller-manager и kube-scheduler, но активен **ровно один** (active-passive). Механика — объект Lease в kube-system (имена kube-controller-manager, kube-scheduler): лидер пишет себя в spec.holderIdentity и обновляет spec.renewTime; остальные ждут, пока spec.leaseDurationSeconds не истечёт без продления, и перехватывают. Без этого три контроллера на один Deployment создали бы три ReplicaSet'а. **Важно не перепутать акторов:** apiserver лидера **не выбирает** — он stateless, все реплики активны параллельно за балансировщиком; у etcd лидер свой и выбирается Raft'ом — это третий, независимый механизм.
  - **Managed (GKE/EKS) прячет control plane** — в kube-system его компонентов НЕ видно (спрятаны у провайдера); self-managed (kubeadm/kind) — весь control plane на виду.
  - **kubeconfig** = clusters + users + contexts. current-context решает, КУДА летит команда. Личность (кто ты для apiserver) зашита в клиентский серт: CN = username, O = groups. Отдельной таблицы юзеров в k8s нет.
  - **Каждый запрос к apiserver проходит три ступени:** authentication (кто ты) → authorization (RBAC: что тебе можно) → admission (валидно ли/мутация). На чтении admission обычно молчит, кусается на запись.
  - **M1.1 — mTLS до apiserver.** TLS делает ДВЕ работы: (1) шифрует канал + проверяет, что сервер настоящий (CA из kubeconfig проверяет серверный серт; клиентский серт для этого НЕ нужен); (2) mTLS — клиент предъявляет свой серт → это authentication. Данные шифруются **симметричным** ключом; **асимметрика** (серты/ключи) — только в рукопожатии (проверка личности + согласование симметричного ключа), потому что она медленная. Отсюда «гибридная криптосистема».

### **⭐ Бест-практис (golden path)**

  - **Держи** **kubectl** **в пределах ±1 минора от кластера** (version skew). Клиент 1.35 ↔ сервер 1.36 — внутри окна, ок.
  - **Для людей дефолт — OIDC/SSO** (короткоживущий токен от Google/Okta/Keycloak), а НЕ клиентские сертификаты. Причина: client-cert почти невозможно отозвать (в k8s нет встроенного CRL), а токен протухает сам за минуты. Client-cert ок для локального полигона; managed-облака (EKS) в kubeconfig используют exec-плагин (aws eks get-token → короткий токен) — ровно по этой причине.
  - **Для подов личность даётся не сертом, а токеном ServiceAccount** (JWT, смонтирован в под) — детали в M16.
  - **HA control plane (3 узла) — это про отказоустойчивость, а не про производительность.** Три мастера дают кворум etcd (переживает потерю одного) и горячий резерв контроллеров — но kube-controller-manager и kube-scheduler всё равно работают в одиночку через leader election, реконсайл втрое быстрее не станет. Горизонтально масштабируется только apiserver (stateless, все реплики активны). **Отступают** к одному мастеру осознанно — на лабах и dev-кластерах, где потеря состояния приемлема (kind ровно такой).

### **ð§ Команды-первого-выбора**

  - kubectl config get-contexts                 \# где я сейчас (\* = current). Грабля №1 — не тот контекст
  - kubectl cluster-info                        \# адреса apiserver и CoreDNS — куда вообще смотрит текущий kubeconfig
  - kubectl get nodes -o wide                   \# узлы: роли, версии, внутренние IP
  - kubectl version                             \# сверить СЕРВЕРНУЮ версию (принцип 11)
  - kubectl get pods -n kube-system -o wide     \# control plane + агенты живьём (колонка NODE многое говорит)
  - kubectl get pods -n kube-system -v=6        \# увидеть HTTPS GET к apiserver — «единственная дверь» вживую
  - kubectl get --raw='/readyz?verbose'         \# живое здоровье control plane покомпонентно (вместо componentstatuses)
  - kubectl get leases -n kube-system           \# кто сейчас лидер scheduler/controller-manager (колонка HOLDER)
  - kubectl auth can-i list pods                \# ступень authorization живьём (yes/no)
  - docker exec lab-control-plane ls /etc/kubernetes/manifests/   \# static pods на диске узла

  

### **⚠️ Грабли и как не наступить**

  - **«apply прошёл, а ничего не поменялось»** → почти всегда не тот current-context/namespace. В kubeconfig боевой флот (vast\_prod, clicka\_prod, EKS dev-eks) лежит рядом с kind-lab — одна невнимательная ktx крутит прод. Проверяй \* перед любой изменяющей командой.
  - **Искать компоненты control plane в** **kube-system** **на managed-кластере** (EKS/GKE) → их там нет, спрятаны у провайдера. Увидишь только coredns, kube-proxy/замену и CNI.
  - **Путать клиентскую и серверную версию** в kubectl version → под серверную подгоняются поля и API-группы.
  - **kubectl get componentstatuses** **пустой или с ошибкой** → прочитать это как «control plane сломан». API ComponentStatus **deprecated с 1.19** и ничего реально не измеряет — он ходит по захардкоженным адресам, которых в современной сборке может не быть. Живой ответ — kubectl get --raw='/readyz?verbose' (покомпонентно, включая etcd) плюс get pods -n kube-system.
  - **kubectl delete pod** **на компоненте control plane «не работает»** → под пересоздался за секунду с тем же именем. Это static pod: удалил mirror-объект, а kubelet поднял заново из файла. Лечится только правкой манифеста в /etc/kubernetes/manifests/ на самом узле — через API к нему не подступиться.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Компоненты control plane и что делает каждый?»** → apiserver (дверь) / etcd (истина) / scheduler (куда сажать) / controller-manager (reconcile). Узел: kubelet / kube-proxy / containerd.
  - **«Зачем куб, если есть docker-compose + ansible?»** → compose и ansible императивны: применил — и дальше состояние никто не держит, дрейф твоя проблема. Куб хранит намерение и крутит петлю, которая его удерживает: упал контейнер — поднят, умер узел — поды переехали, выкат идёт по одному без даунтайма. Плюс из коробки service discovery по именам и масштаб числом. Не «удобнее запускать», а «есть кому чинить в 4 утра».
  - **«Что будет, если упадёт etcd?»** → кластер теряет источник истины, apiserver без etcd не отвечает; без бэкапа — потеря всего состояния (M22).
  - **«Почему никто не ходит в etcd напрямую?»** → единая точка контроля: authn/authz/admission, валидация, консистентность — всё на apiserver. etcd — просто хранилище за дверью.
  - **«В HA три controller-manager — не создадут ли они три ReplicaSet на один Deployment?»** → нет. Leader election через Lease в kube-system: активен один, остальные ждут истечения leaseDurationSeconds. Проверяется одной командой get leases -n kube-system (колонка HOLDER). Добить: у apiserver наоборот — все реплики активны, он stateless; у etcd свой лидер по Raft. Три разных механизма, не путать.
  - **«Путь** **kubectl get pods****?»** → kubectl (kubeconfig → адрес apiserver + серт) → HTTPS → apiserver (authn → authz → admission) → чтение из etcd → ответ. kubelet НЕ участвует: статус в etcd уже лежит, kubelet пишет его заранее сам, по своей инициативе.

### **ð Связи**

  - Ведёт к: **M2** (kubelet, containerd/CRI, pause-контейнер), **M3** (reconcile spec/status, всё — объект API), **M10** (Service type: LoadBalancer заказывает именно CCM), **M16** (authn/authz/admission, kubeconfig-identity, ServiceAccount), **M22** (как поднимается control plane, static pods, etcd-бэкап).
  - Опирается на: курс по сетям (control plane / data plane; TLS/асимметрика-симметрика).
  - Сквозные темы: **№2** (etcd — истина, apiserver — дверь), **№7** (три ступени доступа), **№1** (kubelet reconcile-репортит status наверх).

### **ð Что должно остаться в голове через полгода**

  - **Всё через apiserver, истина — в etcd.** Никто не ходит в хранилище мимо двери. get = чтение записи, а не опрос узлов.
  - **Control plane решает и хранит; worker'ы запускают.** scheduler только решает, kubelet только исполняет и репортит.
  - **Имя пода выдаёт, кто его запустил** (static / DaemonSet / Deployment); static pod объясняет курицу-яйцо загрузки control plane.
  - **Первым делом —** **config get-contexts****.** Не тот контекст = молчаливый прод-инцидент.
  - **Твоя личность для apiserver зашита в серт/токен** (CN/O) и проверяется на КАЖДОМ запросе — это ступень authentication.

# M2. Контейнер под капотом и что делает kubelet  

## **M2. Контейнер под капотом и что делает kubelet**

**Одной фразой:** что физически запускает под на узле — процесс + namespaces + cgroups, поднятый CRI-рантаймом (containerd), которым дирижирует kubelet.

### **ð§  Ментальная модель**

Контейнер — **не мини-ВМ**, а обычный процесс Linux на **ядре хоста**, которому namespaces наврали про окружение (что он *видит*), а cgroups ограничили аппетит (сколько ему *можно*). kubelet сам ничего не запускает — он через CRI просит рантайм поднять контейнеры. Сеть пода держит отдельный **pause**-контейнер. Аналогия — съёмочный павильон: перегородки между площадками (namespaces) + счётчик с автоматом в щитке на каждую (cgroups), но здание-ядро одно на всех.

### **Что важно знать**

  - Контейнер = процесс + **namespaces** (изоляция: net/pid/mnt/uts/ipc/cgroup — «что вижу») + **cgroups** (лимиты — «сколько можно»). Общее ядро с хостом — вот почему это **не ВМ** (у ВМ своё второе ядро + эмуляция железа).
  - **Три разных «не root» — не путать акторов.** (1) **runAsNonRoot** **/** **runAsUser** — просто UID процесса; проверяет **kubelet** перед стартом. UID остаётся настоящим UID узла: runAsUser: 1000 внутри = 1000 снаружи, а UID 0 внутри = **тот самый root хоста**, потому что user namespace для подов по умолчанию выключен. (2) **pod.spec.hostUsers: false** — включает **user namespace** для пода: UID внутри маппится на непривилегированный диапазон снаружи, и root в контейнере перестаёт быть root'ом на узле. Фича beta, включается не везде — сверяй kubectl explain pod.spec.hostUsers на своём кластере. (3) **rootless-контейнеры** — это про **рантайм**: containerd/podman запущены от обычного юзера узла, не от root. В k8s-кластерах встречается редко (kubelet сам хочет привилегий), живёт в основном в CI и на десктопе. Три разных слоя, лечат разные вещи.
  - cgroups исполняют limits физически: строка YAML → число в файле ядра. limits.memory: 64Mi → memory.max=67108864; limits.cpu: 200m → cpu.max="20000 100000" (cgroup v2: квота/период в мкс = 0.2 ядра).
  - Два поведения при упоре в потолок принципиально разные: **memory limit → OOMKilled** (ядро убивает; видно в describe как Last State: Terminated, Reason: OOMKilled + растёт restartCount). **CPU limit → throttling** (притормаживают; в kubectl **не видно**, под Running/healthy, только в метриках).
  - Нет limits → в ядре max (безлимит) → всплеск/утечка бьёт по **всему узлу**. Дальше срабатывает kubelet-eviction (по node pressure) или kernel-OOM. Кого выселят первым решает **QoS**: BestEffort (нет requests/limits) → Burstable → Guaranteed (request==limit) — трогают последними.
  - **CRI** — gRPC-контракт между kubelet и рантаймом. kubelet **не запускает** контейнеры сам, он говорит «создай sandbox / подними вот это / дай статус».
  - **OCI — это три отдельные спецификации, и путать их дорого.** *image-spec* — как устроен образ (манифест, слои, конфиг) · *runtime-spec* — как из распакованного образа сделать процесс (её реализует runc) · *distribution-spec* — как registry отдаёт образ по HTTP (её говорят Docker Hub, Harbor, GAR, твой registry.clickadilla.com). Отсюда совместимость: docker build делает OCI-образ, любой OCI-совместимый рантайм его запустит, любой OCI-registry его отдаст — Docker в этой цепочке не обязателен нигде.
  - «Kubernetes выпилил Docker» = удалили **dockershim** (переходник, deprecated 1.20, удалён 1.24), а **не** containerd. Образы OCI (docker build) работают как раньше. Docker сам *использует* containerd под капотом; k8s теперь ходит в containerd напрямую.
  - Цепочка низа: kubelet → CRI → containerd → runc. runc создаёт namespaces+cgroups и делает exec процесса.
  - На узле рантайм — containerd, поэтому docker ps там пусто; смотрят через **crictl** (crictl ps — контейнеры, crictl pods — sandbox'ы = pause).
  - **pause-контейнер** держит **network namespace** пода: создаётся первым, умирает последним, поднимается **всегда** (даже при одном контейнере). Отсюда: общий IP на под (IP принадлежит pause), общий localhost, IP **не меняется** при рестарте рабочего контейнера.
  - Контейнеры **одного** пода общаются через localhost:\<port\>; **разные** поды — через Service/DNS (имя app внутри пода не резолвится — это уровень Service, M10/M11).
  - Образ = стопка read-only **слоёв** (content-addressable по хешу, переиспользуются между образами) + тонкий writable-слой поверх при запуске (copy-on-write). Ссылка: \<registry\>/\<repo\>:\<tag\>; без registry подставляется docker.io.
  - **Как containerd физически тянет образ — три этапа, три хранилища.** (1) **Resolve** — по ссылке repo:tag качает *манифест* (список слоёв с их дайджестами), а при мульти-архитектурном образе сначала *индекс* и выбирает вариант под linux/amd64. (2) **Content store** — скачивает сами слои как **сжатые blob'ы**, адресуемые по sha256, в /var/lib/containerd/.../content. Именно здесь работает дедупликация: слой с тем же хешем уже лежит → не качается вообще, сколько бы образов на него ни ссылались. (3) **Snapshotter** — распаковывает blob'ы в файловую систему и собирает из них стопку; дефолтный overlayfs монтирует слои как read-only lowerdir + writable upperdir для контейнера. **Актор — containerd, не kubelet**: kubelet только зовёт PullImage по CRI и ждёт. Практические следствия: образ на 800 МБ поверх общей базы занимает на диске десятки мегабайт, а не 800; crictl images показывает **размер образа**, а не занятое место; чистит всё это **kubelet** своим image GC по порогам заполнения диска, а не containerd сам по себе.
  - Pull-фейл: ErrImagePull (первая неудача) → ImagePullBackOff (пауза между ретраями, экспоненциальный backoff). **Причина всегда в** **describe** **→ Events → Message.**
  - **imagePullPolicy** — коварный неявный дефолт: тег :latest или без тега → policy Always (тянет каждый старт); конкретный тег → IfNotPresent (берёт из кеша).
  - **Механика** **imagePullSecrets** **— кто, что и где читает.** Креды лежат в Secret'е типа kubernetes.io/dockerconfigjson, единственный ключ — .dockerconfigjson (тот же формат, что \~/.docker/config.json). В поде это **ссылка по имени**: spec.imagePullSecrets\[\].name, либо ссылка унаследована от serviceAccountName (SA несёт свой список, kubelet их объединяет). Читает секрет **kubelet на узле**, до создания контейнера, и передаёт креды рантайму. **Секрет обязан лежать в том же namespace, что под** — kubelet физически не может забрать чужой (ему это запрещает NodeRestriction-admission, он видит только секреты подов своего узла). Отсюда самая частая ошибка при миграции реестра: секрет создан один раз в default, а поды живут в трёх других ns → 401 unauthorized во всех трёх.

### **⭐ Бест-практис (golden path)**

  - **imagePullSecret вешай на ServiceAccount namespace'а, не на каждый под** (дефолт). Один раз настроил SA → все поды тянут приватный registry без правки манифестов; меньше «забыл secret» при миграции реестра. Отступают (per-pod) — когда в одном namespace разные registry с разными кредами.
  - **Пинуй конкретные теги, ⭐ ещё лучше digest** **@sha256:...****, не** **:latest****.** Воспроизводимость: :latest = «у меня работает, в проде другой образ под тем же тегом». В CI: тег = версия/commit-sha. Отступают — локальная разработка.
  - **imagePullPolicy задавай осознанно**, не полагайся на неявный дефолт от формы тега.
  - **Периметр пода строй** **securityContext****'ом, а не погоней за rootless-рантаймом** (дефолт индустрии). runAsNonRoot + drop: ALL + readOnlyRootFilesystem дают 90% эффекта и работают на любом кластере (M18); rootless containerd и hostUsers: false — точечные инструменты под недоверенный код, и оба ломают часть привычных сценариев (hostPath, монтирование по UID, привилегированные агенты). **Отступают** в мультитенантных кластерах с чужим кодом — но там честнее отдельный кластер или Kata/gVisor, чем полумеры.

  - kubectl get pod \<name\> -o jsonpath='{.status.qosClass}'    \# QoS-класс пода (кого выселят первым)

### **⚠️ Грабли и как не наступить**

  - ImagePullBackOff после миграции реестра → приватный registry без/с неверным imagePullSecret (401 unauthorized). Читай Message в Events, не гадай: not found=опечатка тега (404), unauthorized=secret, toomanyrequests=rate limit Docker Hub, i/o timeout/no such host=нет сети до registry с узла.
  - **Секрет с кредами лежит в другом namespace** → 401, хотя get secret -A показывает, что он «есть». kubelet не ходит за секретами чужих ns. Лечится копией секрета в каждый ns (или ExternalSecrets/оператором, который их разложит) — не правкой пода.
  - **«На одном узле работает, на другом** **ImagePullBackOff****»** → образ уже лежал в кэше первого узла, и под стартовал **без всяких кредов**: при IfNotPresent kubelet не проверяет права на образ, который уже есть локально. Стоит поду переехать — приезжает правда. Отсюда же вывод для безопасности: кэш узла — не контроль доступа. Хочешь проверки на каждом старте — imagePullPolicy: Always.
  - **CPU-throttling невидим в** **kubectl**: приложение «тормозит без причины», под Running и healthy — искать только в метриках (container\_cpu\_cfs\_throttled\_seconds, M20).
  - :latest при IfNotPresent кэшируется и не обновляется; при Always тянет каждый старт (лишний трафик + зависимость от доступности registry).
  - На узле docker ps пусто — рантайм containerd, нужен crictl.
  - Под без requests = BestEffort = первый кандидат на выселение при memory pressure узла.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Контейнер — это что на самом деле?»** → процесс на общем ядре хоста + namespaces (изоляция, «что вижу») + cgroups (лимиты, «сколько можно»). Не лёгкая ВМ: у ВМ своё ядро и эмуляция железа.
  - **«Куб убрал Docker — наши образы из** **docker build** **сломаются?»** → нет. Удалили dockershim, containerd тот же самый, OCI-образы запускаются как ни в чём не бывало; на узле только docker ps → crictl ps.
  - **«Почему все контейнеры пода видят один** **localhost****?»** → общий network namespace, который физически держит pause-контейнер.
  - **«ImagePullBackOff — куда смотришь первым делом?»** → describe → Events → Message → класс ошибки (404 / 401 / rate limit / сеть).
  - **«Что нужно, чтобы под тянул образ из приватного реестра?»** → три вещи и ни одной лишней: Secret типа kubernetes.io/dockerconfigjson **в том же namespace**, ссылка на него в spec.imagePullSecrets или на ServiceAccount пода, сетевая доступность registry **с узла** (не с твоего ноута). Добить: читает секрет kubelet, не api-server и не контейнер; и проверить это можно только на новом узле — на старом образ может стоять в кэше и маскировать проблему.

### **ð Связи**

  - **Опирается на:** M1 (kubelet, api-server, «всё через дверь»), Docker; сети (network namespace — M13 сетей).
  - **Ведёт к:** M4 (Pod, probes, QoS-предпросмотр, CrashLoop), M7 (imagePullSecret, ConfigMap/Secret), M9 (CNI вешает IP пода на veth pause-контейнера), M13 (requests/limits, QoS, OOM vs throttle во всю ширину), M18 (периметр пода: securityContext, почему root в контейнере — это root узла).
  - **Сквозные темы:** №6 (requests/limits правят жизнью пода — cgroups это их исполнение), №5 (сетевая модель — общий netns пода), №2 (kubelet/рантайм действуют по spec из api-server).

### **ð Что должно остаться в голове через полгода**

  - Контейнер = процесс + namespaces («вижу») + cgroups («можно»); общее ядро → это **не** ВМ.
  - **memory limit → OOMKilled** (убьют, видно в describe); **CPU limit → throttling** (притормозят, в kubectl **не** видно).
  - «Убрали Docker» = убрали dockershim; containerd и OCI-образы живы; на узле — crictl.
  - **pause** держит netns пода → общий IP и localhost; IP переживает рестарт рабочего контейнера.
  - ImagePullBackOff: ответ **всегда** в describe → Events → Message.

# M3. Декларативная модель и API  

## **M3. Декларативная модель и API**

**Одной фразой:** ты описываешь *желаемое* (spec), контроллер на бесконечной петле сам тянет к нему *факт* (status) — а весь Kubernetes это набор объектов API за одной охраняемой дверью (api-server), хранящихся в etcd.

### **ð§  Ментальная модель**

**Термостат.** spec = температура, которую ты выставил (хочу 22°). status = что показывает термометр сейчас (18°). Reconciliation loop = сам термостат: бесконечно смотрит на разницу spec−status и подкручивает реальность, пока факт не догонит желаемое, потом держит. Открыл окно (дрейф) — снова греет. Ты не командуешь «сделай» — ты записываешь намерение, и кто-то обязан его удерживать. Отсюда растёт ВСЁ странное поведение куба: удалённый под воскресает, нельзя «просто поправить» под под контроллером, объект висит в Terminating.

### **Что важно знать**

  - **Императив vs декларатив.** create/scale/delete = глагол в моменте, исполнилось и забылось. apply = «пусть будет так», намерение записано в кластер и живёт. Разница не в синтаксисе, а в том, КТО держит ответственность за поддержание состояния.
  - **apply** **идемпотентен.** Повторяй сколько угодно → created один раз, дальше unchanged, без ошибок. create на втором прогоне падает already exists. Идемпотентность — фундамент GitOps (ArgoCD применяет одно и то же годами).
  - **Анатомия любого объекта:** apiVersion + kind (паспорт типа, по нему валидируют) · metadata (кто это: name/namespace/labels/uid/generation) · **spec** (желаемое, пишешь ТЫ) · **status** (факт, пишет СИСТЕМА, в манифесте не указывается — проигнорируется).
  - **spec/status — сердце.** Само поле replicas в схеме зовётся «number of **desired** pods». replicas: 0 ≠ не задано: ноль — это валидное явное желаемое «держи пусто» (так глушат сервис не удаляя).
  - **Живучесть пода = наличие живой петли выше него.** Удалил под под RS → воскрес (RS держит число). Удалил RS под Deployment → воскрес через новый RS (Deployment держит RS). Осиротил под → умер насовсем, петли нет. Магия самовосстановления — свойство КОНТРОЛЛЕРА, не пода.
  - **Воскрешённый под — НЕ тот же под.** Новое имя, новый uid, возраст с нуля. Контроллер верен ЧИСЛУ в spec, а не конкретным подам. Поды — расходники.
  - **Owner references** — «свидетельство о родстве» в metadata ребёнка (kind+uid владельца). Цепочка Deployment→RS→Pod прошита ссылками. Каскадное удаление ходит вниз по ним.
  - **--cascade****:** background (⭐дефолт: владельца сразу, детей в фоне) · foreground (сначала дети, родитель висит Terminating) · orphan (только владелец, дети остаются сиротами с обнулённым ownerReferences).
  - **Группы/версии API.** apps/v1 = группа apps, версия v1. Core-группа (Pod/Service/ConfigMap/Node) имеет ПУСТОЕ имя → просто v1, не core/v1. Зрелость: alpha→beta→v1. Поля переезжают между версиями (Ingress: extensions/v1beta1 → networking.k8s.io/v1 — сломало старые манифесты).
  - **generation vs observedGeneration** — spec/status в миниатюре. generation (metadata) растёт на +1 при каждом изменении spec (не status). observedGeneration (status) — какое поколение контроллер уже обработал. Равны → reconcile догнал. Так rollout status понимает, докатился ли деплой.

### **⭐ Бест-практис (golden path)**

  - **Декларативный** **apply** **из файлов в Git — индустриальный дефолт для прода, без вариантов.** Почему: воспроизводимость (состояние = текст, ревьюится в PR, откат через git revert), идемпотентность (нет дрейфа), аудируемость (история git, не чья-то память).
  - **Императив легитимен для:** обучение/разведка (kubectl run), одноразовые операции-глаголы по смыслу не-состояние (rollout restart, delete, cordon), генерация скелета (create ... -o yaml --dry-run=client → потом ведёшь декларативно). Гибрид «родил императивом → веду декларативно» очень частый.
  - **Анти-паттерн (бьют на ревью/собесе):** kubectl edit/kubectl scale на проде руками → манифест в git больше не отражает реальность → **configuration drift** → следующий apply из CI или ArgoCD молча откатит. Правишь состояние — правь файл, а не объект.
  - **Чтобы удалить насовсем — руби с самого верха цепочки владения.** Снизу (под) или из середины (RS) — вышестоящая петля отстроит заново.

### **ð§ Команды-первого-выбора**

kubectl apply -f web.yaml                    \# декларативно, идемпотентно

kubectl diff -f web.yaml                     \# что изменится ДО применения (страховка перед apply/в PR)

kubectl get deploy web -o yaml | less        \# увидеть spec И status одного объекта

kubectl explain deployment.spec.replicas     \# живая схема полей ТВОЕЙ версии кластера (вместо гугла)

kubectl api-resources                         \# карта всех типов: shortname, группа/версия, namespaced?

kubectl delete deploy web --cascade=orphan   \# удалить владельца, оставить детей сиротами

kubectl get deploy web -o jsonpath='{.metadata.generation}{" / "}{.status.observedGeneration}{"\\n"}'

  

### **⚠️ Грабли и как не наступить**

  - «Удаляю поды, а они лезут обратно» → рубишь не на том уровне цепочки; ищи владельца наверху (Deployment), меняй spec, а не воюй с фактом.
  - \--cascade=orphan сгоряча → «деплоя нет, а поды жрут ресурсы и шлют трафик», зомби, которых get deployment не покажет — ищешь по labels руками.
  - Осиротил поды → создал Deployment с тем же selector → он их **усыновил** по labels; если их больше чем replicas — лишние прибьёт (тема №3: связь через метки, не ссылки).
  - create на существующем объекте падает already exists → в скриптах/CI используй apply.
  - Правка status в манифесте игнорируется — его пишет только система.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Что происходит после** **kubectl apply****?»** → HTTPS в api-server → authn → authz(RBAC) → admission → валидация схемы → запись в etcd → контроллер видит новый/изменённый spec → reconcile тянет факт к желаемому → kubelet запускает контейнеры → пишет status обратно через api-server в etcd.
  - **«Чем apply отличается от create?»** → create = императивное разовое действие (падает на существующем); apply = декларативное «приведи к состоянию», идемпотентно, считает разницу live vs желаемое.
  - **«Реплик стало снова N после ручного scale — почему?»** → git = источник истины, reconcile (ArgoCD pull или CI apply) затёр дрейф. Различай: **drift** = состояние (факт уехал от желаемого), **reconcile** = механизм, который его лечит.
  - **«Где посмотреть, какие поля есть у ресурса?»** → kubectl explain \<res\>.spec --recursive, не гугл (это схема твоей версии).

### **ð Связи**

  - Опирается на: M1 (api-server как единственная дверь, etcd = источник истины), M2 (под эфемерен, смертен без петли над ним).
  - Ведёт к: M4 (почему голые поды не в прод), M5 (контроллеры = этот паттерн во всех формах), M6 (усыновление по labels — клей), M7/M23 (финализаторы, Terminating — отложено сюда), M21 (GitOps = reconcile для всего репозитория).
  - Сквозные темы: №1 (декларативность/reconcile), №2 (всё — объект API за api-server, etcd — истина), №4 (контроллер как универсальный паттерн), краем №7 (конвейер authn→authz→admission на входе в api-server).

### **ð Что должно остаться в голове через полгода**

  - **spec = желаемое (пишешь ты), status = факт (пишет система). Reconcile бесконечно тянет второе к первому. Термостат.**
  - **Не воюй с фактом — меняй желаемое.** Под воскресает, потому что над ним живая петля держит число из spec. Чтобы ушло насовсем — руби с вершины цепочки владения.
  - **apply** **идемпотентен и декларативен → фундамент GitOps.** Ручной edit/scale на проде = дрейф, который reconcile затрёт.
  - **Всё — объект API за одной дверью (api-server), лежащий в etcd.** Каждый запрос проходит authn→authz→admission→схему. Прямого лаза в etcd нет by design.
  - **kubectl explain** **и** **api-resources** **— вместо гугления полей.** Схема твоей версии кластера, живьём.

  
  

# M4. Pod — атом планирования  

## **M4. Pod — атом планирования**

**Одной фразой:** под — минимальная единица запуска в k8s (обёртка вокруг одного-нескольких контейнеров с общими сетью и volumes); внутри него kubelet следит за здоровьем контейнеров, а как под попадает в трафик и выживает — решают пробы и requests/limits.

### **ð§  Ментальная модель**

Два независимых уровня «воскрешения», разные хозяева. **kubelet** (на узле) рестартит *контейнеры внутри живого пода* по restartPolicy — тот же под, тот же IP, тот же узел. **ReplicaSet-контроллер** (control plane, watch по etcd) пересоздаёт *сам под-объект*, если он удалён/узел умер. kubelet не пересоздаёт поды, контроллер не рестартит контейнеры. Всё поведение пода — надстройка над этим разделением.

### **Что важно знать**

  - **Фаза (****status.phase****)** — грубый верхнеуровневый статус (Pending/Running/Succeeded/Failed/Unknown). RunningНЕ гарантирует готовность к трафику — за это отвечает condition Ready, считается из readiness-проб. Реальная жизнь пода — в status.conditions и status.containerStatuses, не в phase.
  - **restartPolicy** (на весь под, читает kubelet): Always (дефолт, для сервисов; Deployment всегда ставит его) / OnFailure (только при exit≠0, для Job) / Never.
  - **CrashLoopBackOff — это не ошибка, а состояние ожидания**: «контейнер циклически падает, kubelet держит паузу перед следующим рестартом». Backoff растёт экспоненциально 10→20→40→...→**300с потолок**. Причина падения — НЕ в имени статуса, а в логах/Events.
  - **Exit codes:** 1/произвольный — упало приложение (иди в логи); **137** = 128+9 SIGKILL (чаще OOMKilled); **143** = 128+15 SIGTERM (graceful shutdown).
  - **Три пробы, три РАЗНЫХ последствия** (это ядро модуля):
      
      - **liveness** «жив?» провал → **убить+рестарт** контейнера (тяжёлое, обратимое рестартом).
      - **readiness** «готов к трафику?» провал → **выкинуть из Endpoints** (ready=false), под ЖИВ, RESTARTS не растёт (мягкое).
      - **startup** «закончил долгий старт?» пока не прошла → замораживает liveness/readiness; прошла один раз → отключается навсегда.
  - **not-ready под физически в EndpointSlice, но с** **ready=false** → kube-proxy на него трафик не шлёт. Endpoint существует, но помечен «не лей».
  - **init-контейнеры**: выполняются последовательно ДО main, каждый до exit 0, иначе под висит Init:N/M. main не стартует ни разу, пока init не прошли. Делят volumes с main (передача через emptyDir).
  - **Нативный sidecar (1.36 stable)** = init-контейнер с restartPolicy: Always. Стартует ДО main, НЕ блокирует его (main идёт, как sidecar стал Ready), живёт параллельно, завершается ПОСЛЕ main. **Считается в** **READY N/M**(обычный init — нет).
  - **Мультиконтейнерные паттерны** (по направлению трафика): **sidecar** — помощник общего назначения (логи, mesh-прокси); **adapter** — нормализует ВЫХОД main для внешних (метрики→Prometheus); **ambassador** — проксирует обращения main НАРУЖУ через localhost (шардинг/failover спрятаны).
  - **requests** = бронь под размещение (scheduler ищет узел с этим объёмом); **limits** = потолок. **CPU\>limit → throttling** (тормозит, живёт); **memory\>limit → OOMKilled/137** (убивают, память несжимаема).
  - **QoS:** Guaranteed (оба ресурса CPU+память заданы у ВСЕХ контейнеров и по обоим requests==limits) / Burstable (что-то задано, но не дотягивает) / BestEffort (ничего). Решает, кого убьют первым при **node pressure**. Превышение СВОЕГО лимита → OOMKilled всегда, QoS не спасает (два разных механизма убийства\!).

### **⭐ Бест-практис (golden path)**

  - **liveness делай снисходительной, readiness можно строгой.** Цена ложной readiness = временно меньше трафика (обратимо). Цена ложной liveness = убитый здоровый под + риск каскада под нагрузкой. Сомневаешься, нужна ли liveness — часто НЕ нужна: голая readiness закрывает большинство. failureThreshold: 1+ короткий timeout на liveness = выстрел себе в ногу.
  - **Медленный старт + нужна быстрая реакция на зависание → startup-проба**, НЕ раздутый initialDelaySecondsу liveness (тот действует всю жизнь пода → неразрешимый компромисс старт-vs-реакция).
  - **Мультиконтейнерный под оправдан только при неразрывной связи** (общий жизненный цикл/узел/сеть/диск). Может быть отдельным Deployment — делай отдельным. Sidecar = «прокси без своего main бессмысленен», а не «положу рядом за компанию».
  - **Долгоживущий помощник (логи/прокси/метрики) → sidecar через** **initContainers****+****restartPolicy: Always**, не «второй обычный контейнер» (старый способ ломал Job'ы — под не завершался — и порядок старта — main слал в неподнятый прокси).
  - Продовый под без requests/limits = BestEffort = первый на выселение. Всегда задавай хотя бы requests.

### **⚠️ Грабли и как не наступить**

  - **Здоровый под циклически рестартится, в логах чисто** → агрессивная liveness убивает. Смотри describe→Events: Unhealthy + Killing: failed liveness probe, will be restarted. Убивает проба, не код.
  - **--previous** **вернул «unable to retrieve container logs»** → containerd подчистил лог при быстром CrashLoop. Не паникуй: describe (Last State) держит reason/exit code всегда, плюс централизованные логи (M20).
  - **«Running, а трафик не идёт / 502»** → readiness провалена, под ready=false, выпал из Endpoints. Или selector разъехался (M6).
  - **Sidecar-как-обычный-второй-контейнер в Job** → под никогда не завершается (main вышел, sidecar крутится). Лечение — нативный sidecar (init+Always).
  - **Регулярный рестарт с exit 137** → memory limit ниже реального аппетита ИЛИ утечка. describe→Last State: OOMKilled.
  - **Приложение «тормозит без ошибок»** → скрытый CPU-throttling (limit слишком низкий).

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Сервис в CrashLoopBackOff — твои шаги»**: (1) describe pod — Last State reason+exit code + Events (надёжно, направляет: приложение упало vs убито снаружи); (2) logs --previous — трейс перед смертью (сработало — золото); (3) живой logs/воспроизведение — запасной. Порядок = сначала надёжное, потом хрупкое.
  - **«liveness vs readiness разница»**: по последствию. liveness провал → рестарт; readiness провал → выпадение из трафика, под жив. Агрессивная liveness опаснее (убивает здоровое + каскад).
  - **«Зачем несколько контейнеров в поде»**: общие сеть/volumes (M2, pause-контейнер). Примеры: sidecar (лог-шиппер, mesh-прокси), adapter (метрики→Prometheus), ambassador (прокси к внешним по localhost).
  - **«Почему под Guaranteed, хотя память requests==limits?»** — ловушка: нужны ОБА ресурса (и CPU) равными. Упустил CPU → Burstable.

### **ð Связи**

  - Опирается на: M2 (контейнер, pause, общий netns; kubelet следит за здоровьем), M3 (spec/status, reconcile, watch — get -w увидел живьём).
  - Ведёт к: M5 (rolling update опирается на readiness — видел на readiness-демо: старый под держит трафик, пока новый не Ready), M6 (labels/Endpoints), M7 (CrashLoop из-за отсутствующего конфига/секрета), M10 (Endpoints/EndpointSlice, kube-proxy), M13 (requests/limits/QoS/eviction на глубину).
  - Сквозные темы: №1 (reconcile — kubelet держит контейнеры по restartPolicy), №4 (kubelet как контроллер здоровья), №6 (requests/limits/QoS — правят жизнью пода).

### **ð Что должно остаться в голове через полгода**

  - **kubelet рестартит контейнеры (по restartPolicy), ReplicaSet пересоздаёт под-объекты.** Два уровня, два хозяина.
  - **Три пробы = три последствия:** liveness→убить, readiness→вывести из трафика (под жив), startup→придержать старт. liveness снисходительной, readiness строгой.
  - **CrashLoopBackOff — это «жду перед рестартом», а не причина.** Причина — в describe→Last State (exit code) и логах. Дебаг: describe → logs --previous → живой logs.
  - **CPU\>limit тормозят (throttle), memory\>limit убивают (OOMKilled/137).** Свой лимит превысил — умрёшь независимо от QoS; QoS решает только при node pressure.
  - **Sidecar на 1.36 = init +** **restartPolicy: Always** (стартует до main, живёт с ним, считается в READY). Обычный init — завершается до main.

  
  

# M5. Контроллеры рабочих нагрузок  

## **M5. Контроллеры рабочих нагрузок**

**Одной фразой:** набор контроллеров, каждый крутит один и тот же reconcile-цикл (наблюдай→сравни→действуй), но под свою задачу — держать реплики, катить версии, сажать агентов на ноды или выполнять конечные задачи.

### **ð§  Ментальная модель**

Один паттерн — контроллер (код в цикле в kube-controller-manager) — обслуживает разные типы объектов. Deployment ≠ «держит поды», он **дирижёр над ReplicaSet'ами**: каждая версия = свой RS, активный держит реплики, старые лежат с replicas: 0 как точки отката. Отсюда всё: rolling update = плавная перекладка реплик со старого RS на новый, rollback = оживить старый RS (он готов, образ на нодах — потому мгновенно). Deployment/RS/DaemonSet/StatefulSet = сервисы, живут вечно (restartPolicy: Always); Job/CronJob = задачи, обязаны **завершиться** (OnFailure/Never).

### **Что важно знать**

  - **ReplicaSet** — тупой и надёжный: «держи N подов по шаблону». Одна версия, никакой истории. Напрямую не пишут.
  - **Deployment → ReplicaSet → Pod** — иерархия владения. Deployment управляет переходами версий, RS держит число реплик.
  - **Два RS во время выката**: старый гасится по мере готовности нового. Старый не удаляется — оседает в desired 0 = точка отката.
  - **rolling update окно**: maxSurge (сколько лишних сверх replicas) + maxUnavailable (сколько можно гасить). Инвариант: сумма подов ≤ replicas+maxSurge, доступных ≥ replicas−maxUnavailable.
  - **rollback мгновенный**, потому что старый RS + образ на нодах уже готовы — наката с нуля нет, только смена desired. Откат идёт по тому же rolling-окну.
  - **Ревизии только растут**: откат на ревизию 1 создаёт ревизию 3 с тем же содержимым, номер не переиспользуется.
  - **DaemonSet** — по поду на каждую подходящую ноду. Поля replicas НЕТ: число = число нод. Новая нода → под сам появляется. Для агентов (kube-proxy, CNI, node-exporter).
  - **DaemonSet + toleration** нужен, чтобы сесть и на control-plane (там taint NoSchedule). Системные DS несут operator: Exists (терпят любой taint).
  - **StatefulSet** — стабильные имена (pg-0/1/2) → стабильный PVC (volumeClaimTemplates, свой том каждому) + стабильный DNS (через headless-сервис) + порядок старта/гашения (OrderedReady). Для кластерных БД.
  - **Job** — конечная задача. completions (сколько успешных завершений всего) ≠ parallelism (сколько подов разом). backoffLimit — ретраи упавшего. Поды остаются Completed — это успех, не мусор.
  - **CronJob → Job → Pod** — штампует Job по крону. concurrencyPolicy (Allow/Forbid/Replace) + \*HistoryLimit.

### **⭐ Бест-практис (golden path)**

  - **Никогда не пиши голый ReplicaSet** — только Deployment (RS не умеет rolling update/rollback). Дефолт индустрии, исключений почти нет.
  - **Deployment для stateless, StatefulSet для stateful.** Не тащи БД в Deployment (потеряешь стабильный PVC/порядок), не тащи лендинг в StatefulSet (лишняя возня с identity).
  - **Агент на каждой ноде = DaemonSet**, не Deployment+anti-affinity. Нужен на мастере — добавь toleration.
  - **CronJob с побочными эффектами (бэкап/миграция/письма) →** **concurrencyPolicy: Forbid****.** Дефолт Allow — мина: долгие задачи накладываются, дерутся за ресурс.
  - **\*HistoryLimit** **на частых кронах обязателен** — иначе тысячи Completed-Job раздувают etcd (отдельная проблема от наложения\!).
  - **Версии держи в Git (GitOps, M21), не на** **--record****.** rollout history — аварийка, не система учёта.

### **ð§ Команды-первого-выбора**

kubectl get rs -l app=\<name\>                    \# два RS во время/после выката (старый в 0)

kubectl set image deployment/\<d\> \<c\>=\<img:tag\>  \# запустить rolling update

kubectl rollout status deployment/\<d\>           \# следить за выкатом

kubectl rollout history deployment/\<d\>          \# стопка ревизий

kubectl rollout undo deployment/\<d\>             \# откат на предыдущую (--to-revision=N — на конкретную)

kubectl get ds -A                               \# DaemonSet: DESIRED = число нод

kubectl get job \<j\> / kubectl get cj            \# статус Job / CronJob

kubectl get pods -l job-name=\<j\>                \# поды конкретного Job

  

### **⚠️ Грабли и как не наступить**

  - **Зависший rollout**: readiness-проба на неверный порт → новый под 0/1 навсегда → выкат не докручивается, старый RS не гасится. Смотреть: describe pod, сравнить порт пробы с портом приложения.
  - **Recreate****-стратегия** роняет сервис на время (гасит всё, потом поднимает) — только для несовместимых версий.
  - **CronJob** **Allow** **(дефолт)** + задача дольше интервала → лавина наложенных Job, дерутся за БД/ресурсы. → Forbid.
  - **etcd раздут Job-объектами** — даже с Forbid\! Наложение и накопление истории — РАЗНЫЕ проблемы. → \*HistoryLimit.
  - **restartPolicy: Always** **в Job** — API запретит (под с exit 0 рестартовал бы, completions не досчитались бы).
  - **Удалил StatefulSet — PVC остались** (и наоборот) — они живут отдельно.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Зачем StatefulSet, если Deployment умеет реплики?»** → стабильная identity: имя→PVC (свои данные каждому), имя→DNS (адресуют друг друга поимённо), порядок (bootstrap мастер→реплики). Deployment всё это не даёт.
  - **«Откатился на ревизию 1 — какой номер в history?»** → новый (следующий по счёту), не «снова 1». Ревизии только растут.
  - **«CronJob засрал кластер объектами»** → \*HistoryLimit, НЕ concurrencyPolicy (это про наложение во времени, другая боль).
  - **«DaemonSet не сел на control-plane»** → нет toleration на taint мастера. Дырка в мониторинге по control-plane.
  - **«controller vs объект»** → контроллер = код в цикле (один на тип), ReplicaSet = запись в etcd (за ней следит код). Два RS на выкате = два *объекта*, контроллер один.

### **ð Связи**

  - Опирается на: M3 (reconcile, spec/status), M4 (под, readiness — от неё зависит темп выката; restartPolicy).
  - Ведёт к: M6 (selector связывает Deployment↔поды и Service↔поды), M8 (volumeClaimTemplates StatefulSet), M10/M11 (headless-сервис, per-pod DNS), M14 (taints/tolerations под DaemonSet), M21 (GitOps вместо --record).
  - Сквозные темы: №4 (контроллер как универсальный паттерн — весь модуль), №1 (reconcile: desired vs actual на RS), №3 (selector — предвестник M6).

### **ð Что должно остаться в голове через полгода**

  - **Deployment = стопка ReplicaSet'ов** (история версий). Активный держит реплики, старые в 0 = мгновенный откат (образ на нодах готов).
  - **maxSurge/maxUnavailable** = окно «сколько лишних / сколько недоступных» при перекладке. Rolling = по одному без даунтайма; Recreate = с даунтаймом.
  - **DaemonSet: число = число нод, не задаёшь руками.** Агенты. Toleration чтоб покрыть мастер.
  - **StatefulSet: имя → PVC + DNS + порядок.** Stateful за него, stateless за Deployment.
  - **Job завершается (не Always), Cron штампует Job'ы.** Forbid против наложения, HistoryLimit против замусоривания etcd — РАЗНЫЕ поля под РАЗНЫЕ проблемы.

  
  

# M6. Labels, selectors, аннотации  

## **M6. Labels, selectors, аннотации**

**Одной фразой:** метки — то, по чему объекты ВЫБИРАЮТ друг друга (клей всего кластера); аннотации — данные, прицепленные к объекту для тулов и людей, по которым не ищут.

### **ð§  Ментальная модель**

Labels — это **индексируемые поисковые ключи**. Service, ReplicaSet, NetworkPolicy не держат жёстких ссылок на поды — они каждый тик спрашивают api-server «кто матчит мой selector?». Принадлежность не выдаётся при рождении, а **вычисляется в реальном времени** по меткам: разъехались метки — разъехалась принадлежность. Annotations живут рядом в metadata, но в этом поиске не участвуют вообще — их читают адресно (ingress-nginx свои ключи, cert-manager свои, человек — change-cause).

### **Что важно знать**

  - **Label vs annotation — водораздел в одном свойстве**: по label ИЩУТ (индексируется api-server'ом), по annotation — НЕТ. Отсюда всё остальное.
  - **Label — поисковый ключ**: ограничен по формату (значение ≤63 симв, узкий набор символов), короткий. Лакмус: «буду резать по этому -l/selector?» Да → label.
  - **Annotation — прицеп для чтения**: не индексируется, читается адресно тулом/человеком, может быть большой и произвольной (хоть JSON-блоб). Ingress-конфиг, kubernetes.io/change-cause, ссылки на тикеты.
  - **Selector Service — ТОЛЬКО equality** (app=web, env\!=prod). Deployment/ReplicaSet (matchExpressions) + kubectl -lумеют и set-based (in, notin, «метка существует»).
  - **Принадлежность = совпадение selector каждый тик.** Снял ключевую метку с пода под ReplicaSet → под выпал из выборки → RS видит недобор → поднимает замену. Добавил лишнюю метку → ничего, selector цел.
  - **Осиротевший под**: больной под жив, но выпал из selector'а → никто не рестартит/не обновляет/не удаляет при scale. Ничей.
  - **Снятие selector-метки бьёт в две цели разом**: под уходит и из-под ReplicaSet, и из Endpoints всех матчивших сервисов (снят с ротации И с трафика).
  - **Пустой Endpoints ≈ разъехавшийся selector** (или readiness, M4). Service жив, поды живы, трафика нет, в логах тихо.
  - **Selector Deployment иммутабелен** — сменить нельзя, только пересоздавать Deployment (иначе контроллер потеряет свои поды).
  - **Admission — третья ступень** (после authn/authz): **mutating** дописывает/меняет объект (дефолты, инъекция sidecar), **validating** только судит да/нет. Mutating идёт первым — судить надо финальную версию.
  - **Аннотация-триггер + mutating-webhook** — типовая связка: namespace c linkerd.io/inject=enabled → webhook дописывает sidecar в под.

### **⭐ Бест-практис (golden path)**

  - **Верхнеуровневую идентификацию — на** **app.kubernetes.io/\*** (name, instance, version, component, part-of, managed-by). Дефолт индустрии: Helm/Lens/ArgoCD/Prometheus знают эти ключи в лицо и группируют по ним из коробки. Свои произвольные метки для своих selector'ов живут рядом. Минимум полезного: name + part-of + managed-by.
  - **Заморозить больной под в проде** = снять РОВНО selector-метку (обычно app) → RS поднимет замену, под уйдёт из трафика и останется на вскрытие. Снимешь не ту метку — под останется под трафиком, смысл теряется.
  - **По этому выбираю → label; это просто данные для тула → annotation.** Не смотри на слово «политика»: NetworkPolicy *выбирает* поды по labels, а поведение ingress *настраивается* аннотациями.

### **ð§ Команды-первого-выбора**

kubectl get pods --show-labels                                   \# все метки, включая pod-template-hash

kubectl get pods -l 'env in (staging,prod)'                      \# set-based выборка

kubectl get pods -L app -L tier                                  \# метки как КОЛОНКИ (дежурство)

kubectl label pod \<p\> debug=true                                 \# навесить метку

kubectl label pod \<p\> app-                                       \# СНЯТЬ метку (осиротить / выдернуть из трафика)

kubectl get endpointslices -l kubernetes.io/service-name=\<svc\>   \# кто реально за сервисом

  

### **⚠️ Грабли и как не наступить**

  - **Опечатка в** **service.spec.selector** → пустой Endpoints → «сервис не отвечает», в логах тихо. Смотреть: сверить selector сервиса с метками пода (get pod --show-labels).
  - **Поменял метки у живого Deployment** → рассинхрон, осиротевшие поды под трафиком.
  - **Пытаешься сменить selector Deployment** → apply падает (поле иммутабельно). → пересоздавать.
  - **Аннотация ingress/cert-manager с опечаткой в ключе** → молча игнорируется. Никакой ошибки, просто «не сработало».

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Service есть, под здоров, трафика нет, Endpoints пуст»** → первым делом сверить svc.spec.selector с labels пода (+ readiness пода, M4). Тема №3 в чистом виде.
  - **«Навесил метку на под под Deployment — станет 3 или 4 пода?»** → 3: добавление метки не рвёт selector. А СНЯТИЕ ключевой метки → 4 (RS поднимет замену, старый осиротеет).
  - **«Под оброс контейнером, которого нет в манифесте — кто?»** → mutating admission webhook. Не validating: тот только судит да/нет, дописать не может.
  - **«Label или annotation?»** → лакмус «буду искать по этому?». По label ищут (индекс), по annotation — нет.

### **ð Связи**

  - Опирается на: M3 (reconcile, owner references), M5 (RS считает реплики по selector — предвестник этого модуля).
  - Ведёт к: M10 (Service→Endpoints, пустой Endpoints живьём), M14 (nodeSelector, метки узлов), M18 (NetworkPolicy выбирает поды по меткам), M23/M25 (admission-webhook, инъекция sidecar).
  - Сквозные темы: №3 (labels/selectors — клей, весь модуль), №1 (reconcile: принадлежность вычисляется каждый тик), №7 (admission — третья ступень доступа).

### **ð Что должно остаться в голове через полгода**

  - **Label — по чему ищут (индекс). Annotation — что прицеплено для чтения (не ищут).** Лакмус: «буду резать по -l?».
  - **Принадлежность к контроллеру/сервису вычисляется каждый тик по selector**, а не выдаётся при рождении. Разъехались метки — разъехалась принадлежность.
  - **Пустой Endpoints → в 90% случаев разъехавшийся selector** (или readiness).
  - **Верхнеуровневая идентификация →** **app.kubernetes.io/\***, чтобы экосистема видела систему из коробки.
  - **Mutating дописывает (может менять объект, инъектит sidecar). Validating судит (да/нет).** Mutating первым.

  
  

# M7. ConfigMap и Secret  

## **M7. ConfigMap и Secret**

**Одной фразой:** конфиг живёт отдельно от образа и доставляется в под двумя способами — переменными окружения (впаяны при старте, не обновляются) или файлами (kubelet обновляет на лету), а Secret — это не сейф, а маркер «обращаться осторожно».

### **ð§  Ментальная модель**

**Образ — неизменяемый артефакт, конфиг — переменная часть.** Один и тот же образ nginx:1.27 едет в dev, staging и prod → отличается только то, что подсунули снаружи. Отсюда два канала доставки, и разница между ними — не стилистическая, а **физическая**: env-переменная копируется в память процесса один раз при exec и в Linux неизменяема снаружи → обновить нечего. Файл лежит на диске узла → kubelet может его перезаписать. Всё поведение M7 выводится из этих двух предложений.

**Secret ничего не шифрует.** base64 — транспортная кодировка для бинарников, не защита. Secret — это *отдельный тип*, вокруг которого кластер ведёт себя осторожнее: tmpfs вместо диска, отдельные права в RBAC, опциональное шифрование в etcd.

### **Что важно знать**

  - **Два способа доставки** → env/envFrom (переменные) и volume (файлы). Выбор определяет всё дальнейшее поведение при обновлении.
  - **env не обновляется никогда** — значения разворачиваются kubelet'ом в момент **создания контейнера** и копируются в окружение процесса; окружение запущенного процесса снаружи неизменяемо → канала для обновления физически нет. Только пересоздание пода.
  - **volume обновляется** — kubelet держит watch на смонтированные ConfigMap/Secret и **перезаписывает файлы на диске узла** → задержка до \~минуты (sync-период kubelet'а), не мгновенно.
  - **Обновился файл ≠ приложение перечитало конфиг** — nginx держит конфиг в памяти с момента старта. kubelet свою работу сделал, приложение о новом файле не знает. Два разных слоя; половина «поменял ConfigMap, ничего не изменилось» живёт здесь.
  - **subPath** **не обновляется — НИКОГДА** — монтирует конкретный **инод**, а kubelet при обновлении **пересоздаёт** файл (atomic rename симлинка ..data) → bind-mount указывает на старый инод. Самая злая ловушка модуля: сбой отложен на месяцы.
  - **Структура смонтированного тома** — default.conf → симлинк на ..data → симлинк на timestamp-директорию. kubelet создаёт новую директорию и **атомарно перекидывает** **..data** → приложение никогда не видит полуобновлённый конфиг.
  - **Монтирование volume затирает директорию целиком** — файлы из образа в этом пути исчезают. Отсюда соблазн взять subPath → и попасть в предыдущий пункт.
  - **envFrom** **опасен** — все ключи CM становятся переменными как есть. Ключ PATH → снёс $PATH контейнеру. Ключи с точками/дефисами (app.name) **молча пропускаются** — не валидное имя env-переменной.
  - **Чем Secret реально отличается от ConfigMap** → монтируется в tmpfs (RAM, не на диск узла); kubelet тянет только Secret'ы подов **своего** узла (+ NodeRestriction-admission); **отдельный ресурс в RBAC** (get configmapsможно дать, get secrets — нет); может шифроваться at-rest через EncryptionConfiguration (по умолчанию — **не шифруется**).
  - **Типизированные Secret'ы** — kubernetes.io/dockerconfigjson (для imagePullSecrets), kubernetes.io/tls (для cert-manager/Ingress). Тип определяет, какие ключи обязательны.
  - **immutable: true** — защита от случайной правки + **kubelet перестаёт держать watch** → разгрузка api-server на больших кластерах. Паттерн: app-config-v1 → app-config-v2, деплой ссылается на новую версию → штатный rolling update.
  - **Финализатор** — строка в metadata.finalizers. Пока список непуст, api-server **не удаляет запись из etcd**, а только проставляет deletionTimestamp → объект висит в Terminating. Контроллер, поставивший строку, обязан сделать cleanup и снять её.
  - **ConfigMap финализатора НЕ имеет** — удалится под живым подом. Работающий под продолжит со старыми файлами, но **любой новый под встанет в** **ContainerCreating** **навсегда** → отложенная мина.
  - **PVC финализатор имеет** (kubernetes.io/pvc-protection) → удаление под живым подом виснет в Terminating, пока потребители не уйдут.

### **⭐ Бест-практис (golden path)**

  - **Скалярные настройки** (LOG\_LEVEL, PORT, фича-флаги, адреса сервисов) → **env** (дефолт, 12-factor). Рестарт при изменении — не баг, а фича: нужен **контролируемый rollout**, а не тихая подмена конфига под живым трафиком.
  - **Целые конфиг-файлы** (nginx.conf, application.yml, серты) → **volume** (дефолт). По переменным их не размазать.
  - **Секреты → volume, а не env** (дефолт). env-переменная утекает в крашдампы, в /proc/\<pid\>/environ (читает любой процесс контейнера), в child-процессы, в логгеры. Файл в tmpfs — уже. **Отступают**, когда приложение не умеет читать секрет из файла (таких много) → тогда env, осознанный размен.
  - **subPath** **— только для файлов, которые не меняются в рантайме** (дефолт). Нужен один файл И обновление → монтируй **директорию** в отдельный путь, подсовывай приложению через симлинк/include.
  - **Перечитать конфиг → checksum-аннотация в pod-template** (дефолт индустрии): checksum/config: {{ ... | sha256sum }} → изменился CM → изменилась спека пода → **штатный rolling update** механизмом из M5. Никакой магии. **Альтернатива** — Reloader (оператор), когда манифесты голые, не Helm. **Отступают** к volume+hot-reload только если конфиг обязан меняться **без** рестарта (флаги на живом трафике) — редкость.
  - **imagePullSecrets** **вешать на ServiceAccount**, а не в каждый под (дефолт) → автоматом для всех подов с этим SA.
  - **Зависший** **Terminating** **→ сначала поднять контроллер**, владеющий финализатором. Ручной kubectl patch ... finalizers: null — **крайняя мера**: пропускаешь cleanup → внешний ресурс (облачный диск, DNS-запись, LB) остаётся жить и капать деньгами.

### **ð§ Команды-первого-выбора**

kubectl create configmap app-config --from-literal=LOG\_LEVEL=debug   \# быстрый CM из литерала

kubectl create configmap nginx-conf --from-file=nginx.conf           \# CM из файла (ключ = имя файла)

kubectl get secret db-cred -o jsonpath='{.data.password}' | base64 -d \# вот тебе всё «шифрование»

kubectl describe pod \<name\>                    \# FailedMount / CreateContainerConfigError → Events

kubectl exec \<pod\> -- ls -la /etc/nginx/conf.d \# увидеть симлинки ..data → timestamp-директория

kubectl get \<res\> \<name\> -o yaml | grep -A3 finalizers   \# кто держит объект в Terminating

kubectl rollout restart deployment/\<name\>      \# единственный способ подхватить новый env

  

### **⚠️ Грабли и как не наступить**

  - **ContainerCreating** **навсегда** → ссылка на несуществующий ConfigMap/Secret. describe pod → FailedMount: configmap "X" not found. **logs** **бесполезен — контейнера не существует.** Не запустился → describe; запустился и умер → logs --previous.
  - **Протухший TLS-серт через два месяца** → Secret с сертом смонтирован через subPath, cert-manager перевыпустил, в поде лежит старый. Приложение **не падает** — тихо отдаёт клиентам невалидный серт. Узнаёшь от клиента, не от мониторинга.
  - **Опечатка в ключе** → configMapKeyRef.key не найден → под не стартует (CreateContainerConfigError). Но с optional: true под **стартует**, переменной просто нет → приложение падает на nil. Тихий отказ хуже громкого.
  - **«Поменял ConfigMap — ничего не изменилось»** → три разные причины, один симптом: (а) это env → нужен рестарт; (б) это subPath → нужен рестарт; (в) файл обновился, но приложение не перечитало.
  - **Секрет в env утёк** → крашдамп пишет environ в Sentry/Loki; /proc/1/environ читает любой процесс в контейнере.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«ConfigMap как env и как файл — разница при обновлении?»** → env впаян в процесс при старте, окружение неизменяемо снаружи → только пересоздание пода. Файл kubelet перезаписывает по watch с задержкой \~до минуты. **Всегда добавляй третьим пунктом:** приложение всё равно должно перечитать — kubelet отвечает за файл, не за поведение процесса.
  - **«Secret защищён?»** → нет. base64 — кодировка, не шифрование. Реальная защита = tmpfs + отдельные RBAC-права + шифрование etcd (EncryptionConfiguration), и всё это надо **включить**. Secret — это маркер «обращаться осторожно», а не сейф.
  - **«Объект висит в** **Terminating****»** → финализатор в metadata.finalizers + контроллер, который обязан его снять, умер/удалён. api-server держит запись в etcd, пока список непуст. Чинить: поднять контроллер, не патчить руками.
  - **«Как задеплоить смену конфига так, чтобы приложение её увидело?»** → checksum-аннотация в pod-template → изменение спеки → rolling update. Показываешь, что понимаешь: механизм — не «магия ConfigMap», а обычный Deployment-реконсайл из M5.

### **ð Связи**

  - **Опирается на:** M2 (imagePullSecrets, приватный реестр), M3 (spec/status, финализаторы, deletionTimestamp), M4 (CrashLoopBackOff из-за отсутствующего конфига), M5 (rolling update как механизм подхвата конфига).
  - **Ведёт к:** M8 (volumes/PVC, pvc-protection-финализатор), M16 (RBAC на secrets, SA-токен), M18 (External Secrets, Vault, шифрование etcd), M21 (SOPS/sealed-secrets в GitOps, checksum в Helm-чартах), M23 (финализаторы операторов, зависшие namespace).
  - **Сквозные темы:** №1 (декларативность — изменение спеки триггерит reconcile), №2 (всё — объект в etcd, финализатор живёт в metadata), №7 (identity и RBAC — почему Secret отдельный ресурс).

### **ð Что должно остаться в голове через полгода**

  - **env — впаян при старте, не обновляется. volume — обновляется kubelet'ом с задержкой.** **subPath** **— не обновляется никогда.** Три состояния, из них выводится 90% отладки конфигов.
  - **Обновился файл ≠ приложение перечитало.** kubelet отвечает за диск, не за процесс. Хочешь гарантию — **checksum-аннотация → rolling update**.
  - **Secret не шифрует.** base64 — кодировка. Защита = tmpfs + RBAC + шифрование etcd, и её надо включить.
  - **ContainerCreating** **+** **FailedMount** **= ссылка на несуществующий CM/Secret.** Смотришь describe, не logs — контейнера ещё нет.
  - **Финализатор** — строка в metadata.finalizers, пока непуста → объект не удаляется из etcd, висит в Terminating. Причина зависания почти всегда — **мёртвый контроллер**, который должен её снять.

  
  

# M8. Storage — тома, PV, PVC  

## **M8. Storage — тома, PV, PVC**

**Одной фразой:** данные переживают под только тогда, когда у тома **свой жизненный цикл** — отдельный объект API (PVC), а не потроха пода.

### **ð§  Ментальная модель**

**Ресторан.** PVC — **ордер** («хочу 10Gi, RWO») → пишет разработчик, лежит рядом с приложением. StorageClass — **кухня и техкарта** (provisioner, parameters, reclaimPolicy) → пишет админ. PV — **блюдо на тарелке**, реальный том с координатами → создаёт провижинер сам. Под — тот, кто ест. Разработчик **не знает**, что под ним — GCE PD, EBS или директория узла. Меняешь облако → меняешь StorageClass → манифесты приложения не трогаешь. Ради этого вся конструкция из трёх объектов. WaitForFirstConsumer = «не начинаем готовить, пока гость не сел за стол — иначе остынет не на том столе».

### **Что важно знать**

  - **emptyDir** **живёт по UID пода** — kubelet создаёт /var/lib/kubelet/pods/\<pod-UID\>/volumes/...; под удалён → директория стёрта. Переживает **рестарт контейнера**, но НЕ пересоздание пода — даже на том же узле с тем же манифестом.
  - **spec.volumes** **— это не том, а рецепт** → kubelet штампует новый экземпляр под каждый под. Классическая ошибка: вешать владение томом на Deployment/узел.
  - **Три уровня томов пода:** emptyDir (кэш/обмен между контейнерами; medium: Memory → tmpfs, **считается в memory limit** → M13) · hostPath (опасен — приколачивает под к узлу, / + write = дыра в узел; легитимен только у DaemonSet-агентов) · projected (склейка CM/Secret/SA-токена — так монтируется SA-токен пода, M16).
  - **Динамический провижининг:** PVC → **external-provisioner из** **StorageClass** (контроллер, watch'ит PVC — тема №4) создаёт реальный том и объект PV → **PV-контроллер** (в kube-controller-manager) матчит и ставит Bound. **kubelet тут ни при чём** — он включается позже, на attach/mount, уже на своём узле.
  - **volumeBindingMode: WaitForFirstConsumer** — провижинер ждёт пода → scheduler сначала выбирает узел → том создаётся **в правильной зоне/на правильном узле**. Без него классика облака: диск в зоне -a, под уехал в -b, attach невозможен никогда.
  - → **PVC в** **Pending** **без пода — это НОРМА, а не поломка.** Отличать по Events: WaitForFirstConsumer (штатно) vs ProvisioningFailed / нет свободного PV / zone mismatch.
  - **accessModes: RWO** **= один УЗЕЛ, а не один под\!** Три пода на **одном** узле спокойно пишут в один RWO-том (куб не мешает — а ФС побьётся). Поды на **разных** узлах → Multi-Attach error. Эксклюзивность одного пода даёт только **ReadWriteOncePod** **(RWOP)**, с 1.22.
  - **Корень RWO — природа блочного устройства:** ext4/xfs **не кластерные**, держат кэш метаданных в памяти узла и считают себя единственным хозяином → два узла на запись = каша за минуты. RWX умеют только **файловые** хранилища (NFS, Filestore, EFS, CephFS), где сервер сам разруливает конкурентный доступ. В kind (local-path) RWX нет.
  - **reclaimPolicy: Delete** **(дефолт динамики\!)** — удаление PVC каскадно сносит PV и **реальный диск с данными**. Retain → PV остаётся в Released, данные восстановимы.
  - **kubernetes.io/pvc-protection** — финализатор висит на PVC **с рождения**, не появляется при удалении. delete pvc при живом поде → Terminating + deletionTimestamp, запись **не стёрта из etcd**, пока список finalizers не опустеет. Ремень безопасности от случайного сноса.
  - **volumeClaimTemplates** **у StatefulSet** — не volumes, а **шаблон, штампующий отдельный PVC на каждую реплику**. Имя детерминировано: \<имя-тома\>-\<имя-пода\> (data-db-0) → пересозданный db-0 находит **свой** диск. Вот главный смысл StatefulSet, а не порядок старта.
  - **Удаление StatefulSet НЕ удаляет PVC** — намеренно (снёс базу по ошибке → данные ещё есть). Обратная сторона: осиротевшие PVC копятся молча и **капает биллинг**.
  - **subPath** — bind-mount конкретного inode в обход симлинков ..data → обновление ConfigMap **не доедет никогда**. Приложение при этом **не падает** — тихо работает на протухшем конфиге/серте. Громкого отказа не будет — в этом подлость.

### **⭐ Бест-практис (golden path)**

  - **Динамика через** **StorageClass** **— дефолт.** Статические PV руками — только когда диск уже существует и он один (legacy-NFS, конкретный LUN).
  - **Stateful → StatefulSet +** **volumeClaimTemplates** — один PVC на реплику, никакого шеринга тома. Deployment с PVC допустим **только при** **replicas: 1** и тогда обязательно strategy: Recreate → иначе RollingUpdate поднимет второй под, тот полезет за тем же RWO-томом → **Multi-Attach**. Тихая мина: на одном узле проскочит, в проде развалится.
  - **WaitForFirstConsumer** **— дефолт для облака.** Immediate — только для RWX-файловых хранилищ, которым зона безразлична.
  - **reclaimPolicy: Retain** **для всего, что жалко** — прод-БД всегда. Delete — кэш и скретч. Цена Retain: Released PV не переиспользуется автоматически → чистишь руками.
  - **hostPath** **в приложении — красный флаг.** Нужен быстрый локальный диск → local PV (со scheduling-awareness), а не hostPath.
  - **PVC ≠ бэкап. Снапшот CSI тоже ≠ бэкап** — лежит в том же аккаунте/регионе. Бэкап = выгрузка наружу (Velero, дампы БД).
  - **Консенсуса нет: БД в кубе vs managed.** Managed (Cloud SQL/RDS) снимает бэкапы, failover, апгрейды → для профиля Clickadilla это дефолт. В кубе — когда нужен контроль/мультиклауд, и тогда **только через зрелый оператор** (CloudNativePG, Percona): оператор даёт failover и бэкапы, которых у голого StatefulSet нет из коробки.

### **ð§ Команды-первого-выбора**

kubectl get pvc                             \# Bound или Pending?

kubectl describe pvc \<name\>                 \# Pending → причина в Events (WFFC = норма\!); Used By; Finalizers

### **⚠️ Грабли и как не наступить**

  - **Multi-Attach error for volume** → RWO-том тянут **два узла**. Причина: Deployment+PVC с RollingUpdate → смотреть strategy; или под завис на упавшем узле и том не отцепился.
  - **PVC** **Pending** → три разных зверя, различаются **только по Events**: WaitForFirstConsumer (норма, ждёт под) · ProvisioningFailed (провижинер/квота/права) · нет подходящего PV (статика) · zone mismatch (облако). **Не гадать — читать Events.**
  - **delete pvc** **съел данные** → reclaimPolicy: Delete каскадно снёс PV и реальный том. Умирает не «связь», а **физический диск по команде политики**.
  - **Осиротевшие PVC** после delete statefulset → куб их намеренно не трогает → молча капает счёт за диски.
  - **allowVolumeExpansion: false** (как в kind\!) → PVC не расширить вообще. В облаке обычно true, но **только вверх**.
  - **hostPath** приколотил под к узлу → узел умер, под не переедет.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Три пода пишут в один RWO-PVC — что будет?»** → На **одном узле** всё работает (куб не мешает, ФС побьётся сама). На **разных** — Multi-Attach. «Once» = **узел**, не под. Эксклюзивность пода = RWOP.
  - **«Коллега снёс StatefulSet и PVC — когда погибли данные?»** → На **втором** шаге. delete sts данные не трогает (PVC остаётся, apply вернул бы всё). Убил reclaimPolicy: Delete: PVC исчез → PV в Released → провижинер удалил диск. При Retain — восстановимо. Бонус: удали он PVC **первым** (не убрав под), pvc-protection подвесил бы его в Terminating и спас. **Порядок команд расстегнул ремень безопасности.**
  - **«Объект висит в** **Terminating****»** → Финализатор не «сломался». Сломался **тот, кто должен его снять**: контроллер упал / оператор удалён вместе с CRD / webhook недоступен. Чинишь **контроллер**, не объект. Ручное снятие (patch finalizers: null) — крайняя мера → осиротишь реальный ресурс (диск останется, счёт пойдёт).
  - **«Зачем StatefulSet, если Deployment умеет реплики?»** → Не ради порядка старта, а ради связки **имя пода ↔ его личный PVC** (data-db-0), которая переживает пересоздание пода и удаление самого StatefulSet.

### **ð Связи**

  - **Опирается на:** M3 (spec/status, финализаторы, owner refs), M4 (жизненный цикл пода), M5 (StatefulSet, podManagementPolicy: OrderedReady), M7 (монтирование, subPath, симлинки ..data).
  - **Ведёт к:** M13 (emptyDir: Memory считается в memory limit; PVC → Pending при планировании), M14 (WFFC и выбор узла, zone affinity), M17 (квоты на storage), M22 (бэкапы, drain и отцепление томов).
  - **Сквозные темы:** №1 (reconcile: провижинер тянет реальность к spec PVC), №2 (всё — объект API; PV/PVC/SC — три отдельных записи в etcd), №4 (провижинер и PV-контроллер — тот же паттерн «наблюдай → сравни → действуй»), №6 (emptyDir в RAM ест лимит памяти).

### **ð Что должно остаться в голове через полгода**

  - **emptyDir** **умирает вместе с подом (UID).** Нужна персистентность → нужен объект с отдельным жизненным циклом → PVC.
  - **RWO = один УЗЕЛ, не один под.** Симптом нарушения — Multi-Attach error. Эксклюзивность пода — RWOP. RWX только на файловых хранилищах.
  - **reclaimPolicy: Delete** **— дефолт динамики и убийца прод-данных.** Всё, что жалко → Retain.
  - **PVC** **Pending** **— читай Events, а не гадай.** WaitForFirstConsumer — это норма, а не поломка.
  - **Финализатор = протокол удаления, а не баг.** Вечный Terminating → чини **контроллер**, который должен его снять.

  
  

# M9. Сетевая модель и CNI  

## **M9. Сетевая модель и CNI**

**Одной фразой:** Kubernetes сеть подов не делает — он выдвигает требование «каждому поду свой IP, под→под **без NAT**» и делегирует исполнение CNI; а CNI — это **два разных механизма**(короткоживущий бинарь на узле + вечный DaemonSet), которые все склеивают в один.

### **ð§  Ментальная модель**

**Узел — это роутер, под — компьютер, воткнутый в него патч-кордом.** Патч-корд — veth-пара (один конец в netns пода, второй на узле). Узел роутит по таблице маршрутов. Всё. Кубернетесного тут — только **автоматизация**: поды рождаются десятками в минуту, руками ip link add не наделаешься. **Ключевое отличие от Docker:** там контейнер сидит **за NAT** (MASQUERADE на выходе, IP подменяется на хостовый, снаружи его адрес никому не известен) → отсюда -p 8080:80 и вся боль. Куб NAT **запретил** → отсюда растёт вся сложность CNI: чтобы NAT'а не было, IP подов должны **не пересекаться** между узлами и быть **достижимы** маршрутами.

### **Что важно знать**

  - **Сеть между узлами Kubernetes НЕ создаёт** — это **предусловие**. VPC / свитч в стойке / docker-бридж в kind (172.18.0.0/16). Куб строит сеть подов (10.244.0.0/16) **поверх** уже существующей сети узлов. Два разных слоя: **node CIDR** vs **pod CIDR**.
  - **«Объединение в кластер» ≠ сеть** → kubeadm join — это логическая регистрация (kubelet приходит по HTTPS в apiserver → появляется объект Node в etcd). Физическую связность даёт сеть, которая была **до** куба.
  - **podCIDR** **нарезает не CNI**, а **node-ipam-controller** в kube-controller-manager (--allocate-node-cidrs=true, --cluster-cidr=10.244.0.0/16) → режет на /24 → **пишет кусок в объект** **Node** (.spec.podCIDR). CNI на узле пул не выдумывает — **читает выданное control plane**.
  - **CNI-плагин — короткоживущий БИНАРЬ на диске узла** (/opt/cni/bin/ptp, host-local), **не под и не демон**. Зовёт его **containerd** (не kubelet\!) при создании **каждого** пода. Отработал → **умер**.
  - **Четыре шага плагина** — (1) взять свободный IP из podCIDR **своего** узла (IPAM host-local, учёт файлами в /var/lib/cni/networks/) → (2) создать veth-пару → (3) повесить IP + default route **внутри** пода → (4) прописать локальный маршрут **на узле** (10.244.1.3 dev veth6ca... scope host).
  - **Порядок создания — containerd первый, CNI второй:** kubelet → CRI RunPodSandbox → containerd создаёт **pause с ПУСТЫМ netns** → containerd читает /etc/cni/net.d/\*.conflist → запускает бинарь с командой ADD → плагин наполняет netns → containerd стартует рабочие контейнеры **в тот же netns** (сеть уже готова) → kubelet пишет status.podIP. **pause netns ДЕРЖИТ, а не выдаёт IP.**
  - **CNI-агент — DaemonSet** (kindnet, calico-node, cilium-agent). **Три работы:** кладёт бинарь и конфиг на узел через hostPath · **watch'ит объекты** **Node** · прописывает маршруты к podCIDR **чужих** узлов.
  - **Агент смотрит за УЗЛАМИ, а не за подами** → маршрут 10.244.2.0/24 via 172.18.0.2 — **одна строка на весь узел**, а не по строке на под. Иначе при 10 000 подов было бы 10 000 маршрутов на каждом узле. Узлу-1 достаточно доставить пакет **до узла-2** — дальше узел-2 разберётся своими локальными /32-маршрутами от плагина. **Ради этого** **podCIDR** **и нарезают по узлам.**
  - **Два способа доставки между узлами:** **native routing** — пакет летит **как есть**, сеть **должна знать**маршруты к pod CIDR (BGP / route-таблицы VPC / плоский L2). Calico (BGP), Cilium, kindnet. **Overlay (VXLAN)** — pod-пакет **заворачивают в UDP** между узлами (:8472), физической сети **всё равно**, что внутри. Flannel (дефолт), Calico в IPIP/VXLAN.
  - **Overlay платит MTU: +50 байт обёртки** → внутрь влезает **1450**, а не 1500. CNI обязан выставить подам mtu 1450.
  - **ptp** **vs** **bridge** — в kind моста (cni0) **нет**: veth втыкается **прямо в узел**, на узле **/32****-маршрут на каждый под**, шлюз 10.244.1.1/32 повешен **на каждом** veth-конце (конфликта нет — L2-домена, где бы они столкнулись, не существует). В bridge-режиме (как docker0) — все veth в мосту, один маршрут на всю локальную подсеть.
  - **hostNetwork: true** — под **без своего netns**, живёт прямо в сетевом стеке узла (видит его eth0, маршруты, iptables). Так живут kube-proxy и CNI-агенты — из своего netns они бы не смогли править хозяйство узла.

### **⭐ Бест-практис (golden path)**

  - **Консенсуса «один CNI на всех» нет — выбирают по сети.** ⭐ Практический дефолт в облаке — **Cilium**(eBPF, native routing, L3–L7 policy, замена kube-proxy) или **Calico**; **Flannel** — только если нужен простейший overlay и не нужны NetworkPolicy. **Отступают** к overlay всегда, когда **сеть не позволяет** роутинг pod CIDR (нет BGP, нельзя править route-таблицы VPC, узлы в разных L2-сегментах).
  - **Native routing предпочтительнее overlay, если сеть позволяет** — нет оверхеда инкапсуляции, нет MTU-мины, tcpdump показывает настоящие pod-адреса (дебажится в разы легче).
  - **MTU задавать явно, не полагаться на автодетект** — особенно при VPN/туннеле поверх (там оверхед складывается: VXLAN 50 + WireGuard 60+). Формула: MTU пода = MTU физического интерфейса − оверхед туннеля.
  - **Не смешивать два CNI** в одном кластере — конфликт конфигов в /etc/cni/net.d/ (containerd берёт **первый по алфавиту**) → недетерминированная сеть.
  - **Pod CIDR не должен пересекаться с VPC-подсетью** — планировать заранее, потом менять = пересоздавать кластер.

### **⚠️ Грабли и как не наступить**

  - **MTU — «тихий убийца».** Overlay забыл ужать MTU (или сверху лёг VPN) → ping идёт, TCP-хендшейк проходит, **большие ответы виснут намертво** (файл, крупный JSON, git clone). Под Running, healthy, в логах чисто. **Тот же класс тихого отказа, что** **subPath** **в M7.** Проверка: ping -M do -s 1472.
  - **Мёртвый CNI-агент — ОТЛОЖЕННЫЙ отказ, не громкий.** Уже прописанные veth и маршруты **остаются в ядре** → всё работает. Ломается **при смене топологии**: добавили узел → маршрута к его podCIDR**не появится никогда** → поды двух узлов не видят друг друга при полном здоровье с обеих сторон.
  - **ContainerCreating** **навсегда** → агент **ни разу не отработал**: конфига в /etc/cni/net.d/ нет → containerd не может создать sandbox. **Отличать от предыдущего:** «умер после работы» vs «не отработал никогда».
  - **Pod CIDR пересёкся с VPC-подсетью** → часть трафика уходит в никуда, разбор на неделю.
  - **Ждать** **bridge****-топологии там, где** **ptp** → ищешь cni0, его нет; ищешь маршрут на /24 локальных подов, а там /32 на каждый veth.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Что делает CNI?»** → Куб сеть подов **не реализует** — требует «уникальный IP + под→под без NAT» и делегирует. Физически это **два механизма**: **плагин** — бинарь на диске, зовёт **containerd** на каждый под, делает IP + veth + маршруты, **умирает**; **агент** — DaemonSet, кладёт бинарь/конфиг на узел и **watch'ит** **Node**, прописывая маршруты к чужим podCIDR. **Добить:** агент смотрит за **узлами**, не за подами — **одна строка маршрута на узел**, иначе таблицы не масштабируются. podCIDR нарезает **node-ipam-controller**, не CNI.
  - **«Как отличить overlay от routing за 10 секунд?»** → tcpdump -ni eth0 на узле: **голые pod-адреса** в пакете → routing, NAT'а нет. **172.18.0.3.8472 \> 172.18.0.2.8472 UDP** → VXLAN, pod-пакет внутри. Косвенно: **MTU пода 1450 → почти наверняка overlay**; TTL упал на 2 → пакет прошёл два роутера (узлы) в открытую.
  - **«Под-к-поду не ходит, оба здоровы»** → (1) жив ли CNI-агент на **обоих** узлах → (2) есть ли на узле-А маршрут к podCIDR узла-Б (ip route) → (3) **MTU** (ping -M do) → (4) NetworkPolicy (M18) → (5) не пересеклись ли pod CIDR с VPC.
  - **«Чем сеть пода отличается от докеровской?»** → Docker: контейнер **за NAT** (MASQUERADE), его IP снаружи не существует → нужен проброс портов. K8s: **NAT запрещён**, pod IP — полноправный адрес, маршрутизируется как есть; под видит свой IP таким же, каким его видят другие.

### **ð Связи**

  - **Опирается на:** M2 (netns, pause держит netns; containerd/CRI), M1 (kubelet — агент узла; kube-controller-manager), **курс по сетям** (veth, bridge, таблицы маршрутов, VXLAN/инкапсуляция, MTU, NAT).
  - **Ведёт к:** M10 (Service — **виртуальный** IP поверх этой плоской сети; kube-proxy и iptables), M11 (DNS поверх Service), M18 (NetworkPolicy — нужен CNI с enforcement, kindnet/flannel **не умеют**), M24 (Cilium/eBPF — замена kube-proxy, identity-based вместо IP-based).
  - **Сквозные темы:** **№5** (плоская сеть — весь модуль), №1 (агент — reconcile: watch Node → сверить → прописать маршрут), №4 (CNI-агент = тот же паттерн контроллера), №2 (podCIDR живёт в объекте Node в etcd — CNI его **читает**, а не выдумывает).

### **ð Что должно остаться в голове через полгода**

  - **Куб сеть подов не делает — он запрещает NAT и делегирует CNI.** Сеть **между узлами** — предусловие (VPC/свитч), не работа куба.
  - **CNI — это ДВЕ разные вещи:** **бинарь** на диске (зовёт **containerd** на каждый под → IP + veth + локальный маршрут → умирает) и **DaemonSet-агент** (кладёт бинарь на узел + watch'ит **Node** → маршруты к чужим podCIDR).
  - **Агент маршрутизирует УЗЛЫ, а не поды:** одна строка 10.244.2.0/24 via \<IP узла\> на весь соседний узел. Ради этого podCIDR и режут по узлам.
  - **Overlay vs routing:** VXLAN заворачивает pod-пакет в UDP (сети всё равно, что внутри) ценой **−50 байт MTU**; routing шлёт как есть, но **сеть обязана знать маршруты**. tcpdump на eth0 узла отвечает за 10 секунд.
  - **MTU — тихий убийца:** ping идёт, хендшейк идёт, **большие ответы виснут**. ping -M do -s 1472 — диагноз в одну строку.

  
  

# M10. Service и kube-proxy  

## **M10. Service и kube-proxy**

**Одной фразой:** Service — это стабильная точка входа поверх эфемерных подов; физически это **не машина, а три разделённых слоя** — объявление в etcd (Service), производный список живых подов (EndpointSlice) и правила DNAT в ядре каждого узла (kube-proxy), — и ClusterIP при этом **не существует ни на одном интерфейсе**.

### **ð§  Ментальная модель**

**Pod IP — это как PID процесса: эфемерная величина.** Под пересоздался → новый IP; rolling update → все IP сменились; HPA отскейлил → IP появились и исчезли. Ты **никогда** не пишешь DB\_HOST=10.244.1.7. Ты пишешь DB\_HOST=postgres — и это работает годами, переживая любые пересоздания. **Service = единственная стабильная вещь в кластере, где всё остальное эфемерно.** А «балансировщик» внутри — это не машина и не процесс: это **правило подмены адреса в ядре**, которое пишет kube-proxy и исполняет netfilter. ClusterIP умирает в первом же хопе.

### **Что важно знать**

  - **Три слоя, ни один не «балансировщик»:** **Service** — объявление в etcd («VIP + selector»), ничего не исполняет · **EndpointSlice** — производный список «кто матчит selector **И** Ready», пересчитывает endpointslice-controller · **kube-proxy** — watch'ит оба объекта → пишет правила DNAT в ядро **своего** узла.
  - **Service НЕ хранит список подов** — хранит только selector (условие). Список — отдельный объект, постоянно пересчитывается. → Пустой EndpointSlice = **не поломка Service**, а разъехавшийся selector или упавшая readiness (тема №3).
  - **ClusterIP не существует физически** — его нет ни на одном интерфейсе (ip addr пуст на всех узлах), нет маршрута к нему. Это **не адрес, а имя правила** в таблице nat. Живёт ровно до прохождения netfilter на узле-отправителе.
  - **kube-proxy трафик через себя НЕ пускает** — имя врёт, он не прокси. Он **пишет правила и уходит**, пакеты гоняет ядро. Тот же паттерн, что CNI-агент (M9): watch → привести ядро в соответствие.
  - **Путь пакета** **curl ClusterIP****:** connect на VIP → veth → ядро узла, таблица nat → правило kube-proxy: **DNAT** VIP → реальный pod IP (монеткой) → **VIP УМЕР**, dst переписан → обычная маршрутизация M9 → сосед → под. Обратно: **conntrack** помнит подмену и переписывает source обратно на VIP (иначе приложение отбросит ответ).
  - **В** **tcpdump** **на** **eth0** **узла ClusterIP НЕ виден** — там уже podIP → podIP. Подмена случилась внутри узла, до выхода в сеть.
  - **Балансировка распределённая:** правила лежат в ядре **каждого** узла полной копией (все эндпоинты, локальные и удалённые). Решение «к какому поду» принимает **узел-отправитель**, у себя. **Центрального балансировщика нет** → нечему падать, нечему быть бутылочным горлышком.
  - **Балансировка — тупая монетка на СОЕДИНЕНИЕ, не на запрос.** iptables: statistic mode random probabilityкаскадом (1/N → 1/(N-1) → … → безусловно). Никакого round-robin, нагрузки, памяти. **DNAT происходит один раз при установке коннекта**, дальше conntrack гонит по нему все пакеты.
  - → **Persistent-соединения не балансируются ВООБЩЕ** (gRPC, HTTP/2, WebSocket, пул к БД, Kafka). Один коннект = один под навсегда. Отскейлил до 10 реплик → трафик всё равно в один под. L4 не видит границ запросов внутри TCP-потока → нужен **L7** (headless+client-LB / Envoy / mesh M25).
  - **Типы Service — надстройки над ClusterIP, не замены:** **ClusterIP** — внутрикластерный (95% сервисов: apiserver 10.96.0.1, CoreDNS 10.96.0.10, все твои бэкенды) · **NodePort** — + порт 30000–32767 на **каждом** узле · **LoadBalancer** — + облачный LB (создаёт cloud-controller-manager) · **Headless** (clusterIP: None) — **отказ** от VIP.
  - **LoadBalancer на bare-metal/kind виснет** **EXTERNAL-IP: \<pending\>** **навсегда** — не поломка, а **просить некого**(нет облака → нет того, кто создаст LB). Лечится MetalLB.
  - **Один LB = один сервис = одна плата** → 20 лендингов = 20 облачных LB = 20 счетов. **Из этой боли родился Ingress** (M12): один вход + L7-роутинг по домену/пути.
  - **Headless** → DNS-имя резолвится **не в VIP, а в список всех pod IP** сразу; kube-proxy не при делах. Для **поимённого** доступа к подам (pg-0, pg-1) — стабильная identity StatefulSet (M5/M8), запись в мастер, а не в случайную реплику.
  - **Три сети кластера** (видно в KUBE-SERVICES): node CIDR 172.18.0.0/16 · pod CIDR 10.244.0.0/16 · **service CIDR** **10.96.0.0/16** (из него нарезаются ClusterIP).

### **⭐ Бест-практис (golden path)**

  - **Внутри кластера — всегда ClusterIP + DNS-имя, никогда pod IP.** Дефолт без вариантов: pod IP эфемерен, DNS-имя стабильно.
  - **Наружу — не NodePort в проде.** ⭐ Дефолт: **Ingress** (M12) за одним LoadBalancer для HTTP(S). NodePort — для отладки/on-prem без ingress-контроллера; LoadBalancer напрямую — для не-HTTP (TCP/UDP) или одиночного сервиса.
  - **gRPC/HTTP2 за ClusterIP — осознанно выбирай балансировку.** ⭐ Дёшево: **headless + client-side LB**(gRPC умеет из коробки). Дороже: L7-прокси/mesh. Не полагайся на kube-proxy — он тут не балансирует.
  - **LoadBalancer** **в** **pending** **на голом железе → MetalLB**, а не «ждать, пока поднимется».

### **ð§ Команды-первого-выбора**

kubectl get svc web                              \# TYPE, CLUSTER-IP, PORT

kubectl get endpointslices -l kubernetes.io/service-name=web -o wide   \# кто РЕАЛЬНО за сервисом (пусто = разъехался selector/readiness)

kubectl get svc web -o jsonpath='{.spec.selector}{"\\n"}'   \# условие выборки подов

### **⚠️ Грабли и как не наступить**

  - **«Service есть, под Running, трафика нет» →** **get endpointslices** **ПЕРВЫМ.** Пусто → (1) selector разъехался с метками пода (M6) → (2) под не Ready (readiness, M4) → (3) неверный targetPort. Три слоя — три места разрыва.
  - **gRPC/HTTP2 не размазывается по репликам** → kube-proxy балансирует **коннекты, а не запросы**; persistent-соединение живёт на одном поде. Скейлинг не помогает. → headless+client-LB / L7 / mesh.
  - **LoadBalancer** **навсегда** **\<pending\>** → нет облачного провайдера (bare-metal/kind). Не сломано — **некому создать LB**. → MetalLB.
  - **NodePort открыл порт наружу шире, чем думали** → порт слушают **все** узлы; часто дыра в периметре.
  - **kube-proxy умер** → уже записанные правила **остаются в ядре, работают**; ломается только **обновление**(отскейлил — правила старые, трафик на мёртвые IP). Отложенный отказ, как CNI-агент M9.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«ClusterIP'а нет ни на одном интерфейсе, но curl работает — как?»** → это не адрес, а **триггер правила DNAT** в ядре узла-отправителя. Пакет перехватывается в таблице nat, dst переписывается на реальный pod IP, ClusterIP умирает в первом хопе. kube-proxy эти правила **пишет**, но трафик через себя не пускает.
  - **«Отскейлил gRPC до 10 реплик, грузит один под — почему?»** → DNAT один раз на коннект, дальше conntrack. Persistent-соединение = один под навсегда. L4 не видит запросов в потоке. → headless+client-side LB (дёшево) / mesh (дорого).
  - **«Зачем вообще ClusterIP, если у подов есть IP?»** → pod IP эфемерен (пересоздание/rollout/HPA сменят его). Service — единственный стабильный адрес. 95% сервисов кластера — ClusterIP (включая apiserver и CoreDNS).
  - **«LoadBalancer висит pending»** → нет cloud-controller-manager (не облако). MetalLB на bare-metal.
  - **«NodePort vs LoadBalancer vs Ingress?»** → NodePort: порт на всех узлах, уродливо/небезопасно. LoadBalancer: облачный LB, но 1 сервис = 1 счёт. Ingress: один вход + L7-роутинг, дешевле для многих HTTP-сервисов.

### **ð Связи**

  - **Опирается на:** M9 (плоская сеть подов — DNAT переписывает на pod IP, дальше обычная маршрутизация; kube-proxy в hostNetwork), M6 (selector — клей Service↔Pod), M4 (readiness — условие попадания в EndpointSlice), M3 (Service/EndpointSlice — объекты в etcd, reconcile), M5/M8 (headless + StatefulSet identity).
  - **Ведёт к:** M11 (DNS — откуда под знает, что web = ClusterIP; CoreDNS сам ClusterIP-сервис), M12 (Ingress — из боли «LB на каждый сервис»), M18 (NetworkPolicy поверх этой модели), M24 (Cilium/eBPF — замена kube-proxy, без iptables).
  - **Сквозные темы:** №5 (сеть — VIP поверх плоской сети), №3 (selector→EndpointSlice — клей), №1/№4 (kube-proxy и endpointslice-controller — reconcile: watch → привести в соответствие), №2 (всё — объекты в etcd; service CIDR живёт там же).

### **ð Что должно остаться в голове через полгода**

  - **Service — не машина, а три слоя:** объявление (Service, etcd) → производный список (EndpointSlice: selector И Ready) → правила DNAT в ядре каждого узла (kube-proxy). Ни один не «балансировщик».
  - **ClusterIP не существует.** Умирает в первом хопе — DNAT в таблице nat узла-отправителя переписывает его на реальный pod IP. В сеть уходит podIP, не VIP.
  - **Балансировка — распределённая (правила в ядре каждого узла) и тупая (монетка на КОННЕКТ).** → persistent-соединения (gRPC/HTTP2/пул к БД) не балансируются вообще; нужен L7.
  - **ClusterIP — основной тип (95% сервисов), не бесполезный.** Смысл — стабильный адрес поверх эфемерных pod IP. Остальные типы — надстройки для входа извне.
  - **Отладка: «трафика нет» →** **get endpointslices****.** Пусто = selector / readiness / targetPort. LoadBalancer pending = нет облака.

  
  

# M11. DNS в кластере (CoreDNS)  

## **M11. DNS в кластере (CoreDNS)**

**Одной фразой:** имя сервиса превращается в ClusterIP отдельным слоем — DNS; резолвер пода прописан kubelet'ом в /etc/resolv.conf, короткие имена работают через search-суффиксы, а сам CoreDNS — обычный под, спрятанный за стабильным ClusterIP.

### **ð§  Ментальная модель**

**Разведи два вопроса, которые все склеивают:** «как имя → IP» (это **DNS**, отдельный сервер, отвечает на запрос) и «как пакет → под» (это **маршрутизация + kube-proxy** из M9/M10, работает только с IP). Маршрутизация про имена не знает вообще. Сначала DNS переводит имя в ClusterIP, и **только потом** включается вся машинерия M10 (DNAT). Три слоя в цепочке curl web: **DNS-имя** (web) → **ClusterIP** (10.96.151.148) → **под** (реальный, через DNAT).

### **Что важно знать**

  - **resolv.conf пода прописывает kubelet** при создании — nameserver 10.96.0.10 + search \<ns\>.svc.cluster.local svc.cluster.local cluster.local + options ndots:5. Под не «узнаёт» резолвер сам — ему его выдали.
  - **nameserver 10.96.0.10** **— это ClusterIP сервиса** **kube-dns** (из service CIDR, всегда .10). → DNS-запрос пода идёт на ClusterIP → **DNAT из M10** → реальный под CoreDNS. Резолвер сам сидит за Service.
  - **FQDN сервиса:** \<service\>.\<namespace\>.svc.cluster.local. Короткое имя web резолвится **только** потому, что \<ns\>.svc.cluster.local стоит в search.
  - **search** **перебирается по очереди** — резолвер дописывает суффиксы: web.default.svc... → web.svc... → web.cluster.local. Первый суффикс = **namespace ПОДА-отправителя**.
  - → **Межнеймспейсный резолв коротким именем НЕ работает.** Под в staging пишет curl payments → резолвер подставляет payments.staging... → NXDOMAIN, хотя сервис в prod. Лечение: FQDN payments.prod.svc.cluster.local. Классика «в staging ок, в prod нет».
  - **DNS-имя относительно того, кто спрашивает** — не глобальное. Тот же короткий payments из разных namespace резолвится в разное (или в никуда). Склейка слоёв: имя неявно привязано к namespace пода.
  - **CoreDNS — обычный под** (Deployment в kube-system, обычно 2 реплики). **watch'ит Service и EndpointSlice**через api-server (тема №4, тот же паттерн, что kube-proxy) → держит карту «имя → ClusterIP». Создал Service → CoreDNS знает через секунду.
  - **CoreDNS сам за стабильным ClusterIP** **10.96.0.10** — потому что его поды эфемерны (та же проблема, что у всех подов, M10). Прописывать подам pod IP резолвера нельзя — сломается при пересоздании CoreDNS. → та же логика Service, что везде.
  - **CoreDNS упал → резолв встал по ВСЕМУ кластеру** — приложения не находят БД, друг друга, внешние адреса. Симптом мутный («таймауты повсюду», поды Running/healthy), корень один. Критичная точка, мониторят отдельно.
  - **ndots:5** **— тихий убийца производительности.** Правило: если точек в имени **меньше** ndots — сперва перебирай search-суффиксы, абсолютное имя пробуй последним. → внешний api.stripe.com (2 точки) даёт **4 запроса** к CoreDNS (3 мусорных NXDOMAIN + 1 реальный) на КАЖДЫЙ вызов. На нагруженном сервисе с внешними API — гробит CoreDNS + латентность каждому запросу.

### **⭐ Бест-практис (golden path)**

  - **Внутри кластера — обращайся по имени сервиса, не по ClusterIP.** ClusterIP тоже стабилен, но имя читаемо и не зависит от пересоздания сервиса. В своём namespace — короткое имя, в чужой — FQDN.
  - **Кросс-namespace — всегда FQDN** \<svc\>.\<ns\>.svc.cluster.local. Не полагайся на search, пиши явно.
  - **Внешние домены из подов с высокой частотой → FQDN с точкой на конце** (api.stripe.com.) или **NodeLocal DNSCache**. Точка = «абсолютное имя, не перебирай search» → 1 запрос вместо 4. ⭐ Дефолт для нагруженных кластеров с внешними вызовами (RTB/реклама).
  - **CoreDNS — мониторить как критичный компонент** (latency, errors, SERVFAIL). Его падение выглядит как «сломалось всё сразу», а не как «сломался DNS».

### **ð§ Команды-первого-выбора**

kubectl exec \<pod\> -- cat /etc/resolv.conf                 \# nameserver + search + ndots — откуда резолв

kubectl exec \<pod\> -- nslookup web                         \# короткое имя → FQDN + ClusterIP (search-магия)

kubectl exec \<pod\> -- nslookup web.default.svc.cluster.local  \# явный FQDN

kubectl get svc -n kube-system kube-dns                    \# ClusterIP резолвера (10.96.0.10)

kubectl get pods -n kube-system -l k8s-app=kube-dns        \# сами поды CoreDNS

kubectl logs -n kube-system -l k8s-app=kube-dns            \# логи резолвера при мутных таймаутах

  

### **⚠️ Грабли и как не наступить**

  - **curl \<svc\>** **из другого namespace → NXDOMAIN** → короткое имя резолвится в namespace ПОДА. Лечение: FQDN \<svc\>.\<ns\>.svc.cluster.local. Симптом «в одном окружении работает, в другом нет».
  - **CoreDNS упал → «сломалось всё»** без явной ошибки: таймауты к БД/сервисам/внешним адресам, поды при этом healthy. Смотреть: поды и логи CoreDNS в kube-system.
  - **Тормоза на внешних вызовах / перегруз CoreDNS** → ndots:5 плодит по 4 запроса на внешнее имя. Лечение: FQDN с точкой на конце / NodeLocal DNSCache.
  - **Старый IP после пересоздания сервиса** → DNS-кэш (TTL) в приложении/резолвере отдаёт устаревший ClusterIP. Обычно ClusterIP стабилен, но при delete/create сервиса он меняется.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Под из staging не видит сервис в prod по короткому имени — почему?»** → search начинается с namespace пода (staging.svc...), до prod коротким именем не дотянуться. FQDN \<svc\>.prod.svc.cluster.local.
  - **«Откуда под знает адрес DNS-сервера?»** → kubelet прописал nameserver 10.96.0.10 в /etc/resolv.conf. Это ClusterIP сервиса kube-dns, за ним — поды CoreDNS. Резолвер сам за Service, потому что его поды эфемерны.
  - **«CoreDNS — что это и как ломается?»** → обычный под в kube-system, watch'ит Service/EndpointSlice, отдаёт «имя → ClusterIP». Падение = резолв встал по всему кластеру, симптом размазанный.
  - **«Почему приложение делает кучу лишних DNS-запросов?»** → ndots:5 + короткое внешнее имя → перебор search-суффиксов. FQDN с точкой на конце.

### **ð Связи**

  - **Опирается на:** M10 (Service/ClusterIP — DNS резолвит имя в ClusterIP; kube-dns сам ClusterIP-сервис; DNAT доставляет запрос к поду CoreDNS), M6 (selector → EndpointSlice, за которым следит CoreDNS), M3 (CoreDNS — контроллер-watcher), **курс по сетям** (DNS, resolv.conf, search-домены, ndots, TTL/кэш).
  - **Ведёт к:** M12 (Ingress резолвит внешние имена → на Service по DNS-имени внутри), M5 (headless + per-pod DNS pg-0.\<svc\>... для StatefulSet), M18 (NetworkPolicy может резать доступ к CoreDNS → резолв ломается), M20 (мониторинг CoreDNS).
  - **Сквозные темы:** №5 (DNS — слой поверх плоской сети и Service), №2 (CoreDNS читает объекты из etcd через api-server), №4 (CoreDNS — reconcile-watcher Service/EndpointSlice), №3 (резолвит по selector-производному EndpointSlice).

### **ð Что должно остаться в голове через полгода**

  - **Имя → IP (DNS) и IP → под (маршрутизация) — РАЗНЫЕ слои.** DNS про имена, kube-proxy про адреса. Сначала резолв, потом DNAT.
  - **resolv.conf пода =** **nameserver 10.96.0.10** **(ClusterIP kube-dns) +** **search \<ns\>.svc.cluster.local** **+** **ndots:5**, всё прописал kubelet.
  - **Короткое имя резолвится в namespace ПОДА** (первый суффикс search). Кросс-namespace → **FQDN** **\<svc\>.\<ns\>.svc.cluster.local**.
  - **CoreDNS — обычный под, сам за стабильным ClusterIP.** Упал → резолв встал по всему кластеру, симптом мутный.
  - **ndots:5** → внешние короткие имена плодят лишние запросы. FQDN с точкой на конце спасает.

  
  

# M12. Ingress и ingress-controller  

## **M12. Ingress и ingress-controller**

**Одной фразой:** Ingress — это **правило-объект** в etcd (host/path → сервис + TLS), а ingress-controller — **под-исполнитель** (внутри него живой nginx), который watch'ит эти правила и рендерит из них свой конфиг; один вход + L7-роутинг по домену вместо LoadBalancer на каждый сервис.

### **ð§  Ментальная модель**

**Стикер на доске vs охранник на входе.** Ingress — бумажка «пускать web.local к сервису web», лежит в etcd, **ничего не слушает**. ingress-controller — под, который эту доску читает и **реально открывает дверь**: держит порт, парсит HTTP, роутит. Написал стикер, а охранника не наняли (контроллер не установлен / ingressClassName не его) → правило есть, get ingress показывает, ADDRESS пустой, трафика нет. Трафик течёт **сквозь под контроллера**, а объект висит **сбоку** — не хоп, а справочник.

### **Что важно знать**

  - **Два слоя, называть явно** → Ingress (правило, желаемое, spec пишешь ты) — отдельно от **ingress-controller** (под-исполнитель, reconcile). Тот же паттерн watch→привести-в-соответствие, что kube-proxy (ядро) и CoreDNS (карта имён); контроллер программирует **своё** хозяйство — nginx.conf внутри себя.
  - **Экономика — зачем Ingress вообще** → Service type: LoadBalancer даёт 1 LB на сервис = N счетов. HTTP умеет мультиплексировать по заголовку Host → **один вход обслуживает N доменов**. Ingress **не заменяет** LB, а **амортизирует**: один LB → один контроллер → N правил.
  - **ingressClassName: nginx** → маркер «это правило моё». Контроллеров может быть несколько, каждый watch'ит все Ingress, берёт в работу только свой класс. **Не совпало → правило молча игнорируется** (ADDRESS пустой). Старый способ — аннотация kubernetes.io/ingress.class (deprecated, но на живых кластерах ещё встречается).
  - **ADDRESS** **в объекте — это** **status****, не** **spec** → его пишет **контроллер** (отчёт «на этих IP я доступен»), а не человек. Спека/статус из M3 живьём. **Пустой** **ADDRESS** **= диагностический сигнал**: правило никто не подхватил.
  - **Один nginx, N доменов → N** **server****-блоков** → **один Ingress = один** **server****-блок**. Контроллер рендерит все правила в один конфиг + reload. Это **обычный механизм виртуальных хостов nginx**, не магия куба — куб добавил только автогенерацию конфига из объектов API вместо человека с vim.
  - **В upstream идёт pod IP напрямую, НЕ ClusterIP** → контроллер watch'ит EndpointSlice, кладёт реальные адреса подов в upstream. Service — только справочник (по какому selector искать). **DNAT из M10 в этом пути не участвует.** Следствие: балансирует **сам nginx** (round-robin по **запросам**), а не ядро (монетка по коннектам) → **gRPC/HTTP2 за Ingress размазывается нормально**, в отличие от голого ClusterIP.
  - **Обновление upstream на лету** → под пересоздался (новый IP) → endpointslice-controller обновил слайс → ingress-контроллер увидел через watch → обновил список бэкендов **через Lua-модуль БЕЗ reload nginx** (иначе частые деплои рвали бы соединения). Reload только при смене структуры конфига (новый Ingress, смена аннотаций).
  - **readiness управляет ротацией** → не-Ready под **есть** в EndpointSlice, но с conditions.ready: false → контроллер (как kube-proxy) читает флаг и **не берёт в upstream**. Не «нет записи» (это был бы разъехавшийся selector), а «есть, но не лей». Механизм rolling update без даунтайма: новый под → ready:false → прошёл пробу → флаг переключился → попал в upstream.
  - **spec** **vs аннотации (тема M6)** → spec — стандартизированное (host/path/backend/TLS); **аннотации** — всё специфичное для контроллера (proxy-body-size, таймауты, rewrite, canary-веса). У nginx свои ключи, у traefik свои. **Опечатка в ключе аннотации → молчаливое игнорирование.**
  - **TLS терминируется ДВАЖДЫ и это два независимых серта** → браузер --TLS(серт CF)--\> CF --TLS(твой LE-серт)--\> ingress-nginx --HTTP--\> под. Для ingress-nginx **клиент — это CF**, не браузер; браузер твой LE-серт **никогда не видит**. Внутри кластера (контроллер → под лендинга) TLS **нет** — голый HTTP. Итого шифрованных участков **два**.
  - **SNI выбирает серт,** **Host** **выбирает бэкенд** → рукопожатие TLS начинается ДО HTTP-заголовка, но клиент в ClientHello **открытым текстом** пишет домен (SNI). nginx читает SNI → находит server-блок → предъявляет его серт. Домен участвует **дважды**: SNI (серт) → потом Host (бэкенд). Без SNI 30 HTTPS-доменов на одном IP невозможны (до 2003 — по IP на сайт).
  - **Коды ошибок как индикатор слоя** → **кто нарисовал страницу — тот дожил**; код говорит, где споткнулся. **502** = правило нашлось, контроллер пошёл к бэкенду и не смог → рвётся **ниже** контроллера (эндпоинты/порт/приложение). **404** = правило **не нашлось** (нет server-блока под этот Host/path) → рвётся **на уровне правила** (опечатка host, не тот ingressClassName, домена нет). **Fake Certificate в браузере** = контроллер не нашёл server-блок под SNI → предъявил self-signed заглушку.

### **⭐ Бест-практис (golden path)**

  - **Наружу для HTTP(S) — Ingress за одним LB, не LoadBalancer-на-сервис** (дефолт). NodePort/LoadBalancer напрямую — для не-HTTP (TCP/UDP) или одиночного сервиса.
  - **Один Ingress на приложение** (дефолт). Собирать несколько хостов в один объект — только когда домены реально одного приложения с **одинаковыми аннотациями** (как tc-advertising3 с 6 хостами). Причина: аннотации общие на весь объект + радиус поражения (опечатка роняет все хосты объекта) + RBAC/владение.
  - **За Cloudflare в режиме Flexible (CF→origin по HTTP) →** **ssl-redirect: false** обязателен: иначе контроллер видит HTTP → шлёт 301 на HTTPS → CF снова HTTP → **петля** **ERR\_TOO\_MANY\_REDIRECTS**. В **Full (strict)** (CF→origin по HTTPS) ssl-redirect можно вернуть в true — он молчит, т.к. HTTP до контроллера не доходит.
  - **Gateway API — куда уходит индустрия** (на понимание): Ingress запихивал всё в аннотации → непереносимо, не типизировано, одна роль на всё. Gateway API режет на GatewayClass (контроллер) + Gateway (порты + TLS — владеет **платформа**) + HTTPRoute (host/path→backend — владеет **разработчик**), редиректы/таймауты/canary — **типизированными полями**. RBAC режется по границе ролей. Будущий стандарт, но Ingress живёт ещё годы.

### **ð§ Команды-первого-выбора**

kubectl get ingress                          \# HOSTS, CLASS, ADDRESS (пустой = никто не подхватил)

kubectl describe ingress \<name\>              \# правило целиком: host→backend, TLS, аннотации, Events

kubectl get ingressclass                     \# какие классы есть (какой контроллер за что)

kubectl get pods -n ingress-nginx            \# сам под-исполнитель (в отдельном namespace)

kubectl get endpointslices -l kubernetes.io/service-name=\<svc\>   \# что реально уедет в upstream

\# на bare-metal LoadBalancer-сервисы висят \<pending\> — некому создать LB (норма, см. M10)

  

### **⚠️ Грабли и как не наступить**

  - **Ingress** **есть, на 80 никто не слушает** → контроллер не установлен ИЛИ ingressClassName не его. ADDRESS пустой — первый сигнал.
  - **502 от nginx** → правило нашлось, бэкенд недостижим. Порядок: get endpointslices (пусто/не-Ready?) → сверить порт Ingress с портом Service (Nuxt на 3000, а в манифесте 80) → логи пода приложения (отвечает 500/рвёт коннект).
  - **404 от nginx / Fake Certificate** → правило **не** нашлось. Смотреть объект Ingress (опечатка host, ingressClassName, pathType), НЕ эндпоинты. traceroute бесполезен — это L7, пакеты давно доехали.
  - **ERR\_TOO\_MANY\_REDIRECTS** **за CF** → несовпадение: браузер по HTTPS, origin получает HTTP + ssl-redirect: true. Лечить false (Flexible) или Full strict.
  - **Опечатка в ключе аннотации** → молча игнорируется, никакой ошибки.
  - **cm-acme-http-solver висит дни/недели** → ACME-челлендж не завершился (CF перехватывает HTTP-80 до solver'а) → серт однажды протухнет. Диагностика: get certificate/order/challenge → describe challenge.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Ingress есть, роутинга нет»** → объект vs исполнитель: есть ли контроллер, его ли ingressClassName, пустой ли ADDRESS.
  - **«502 vs 404 от Ingress»** → кто дожил до отрисовки страницы. 502 — правило нашлось, бэкенд лёг (копай ниже контроллера). 404 — правило не нашлось (копай в объект Ingress).
  - **«Как 30 HTTPS-доменов на одном IP выбирают серт, если TLS раньше HTTP?»** → SNI: домен в ClientHello открытым текстом до шифрования → выбор server-блока и серта. Потом Host → выбор бэкенда.
  - **«Зачем Ingress, если есть LoadBalancer-сервис?»** → 1 LB на сервис = N счетов; Ingress = 1 вход + L7-роутинг по Host/path за одним LB.
  - **«Ingress vs ingress-controller»** → правило-объект (etcd) vs под-исполнитель (reconcile). Тема №4.
  - **«Чем Gateway API лучше Ingress»** (3 фразы) → Ingress прятал всё в непереносимые нетипизированные аннотации; Gateway API выносит в типизированные поля и разделяет роли (платформа: Gateway+TLS, разработчик: HTTPRoute). Будущий стандарт, Ingress ещё живёт.

### **ð Связи**

  - **Опирается на:** M10 (Service/EndpointSlice, ClusterIP, LoadBalancer \<pending\> на bare-metal, балансировка на коннект), M6 (selector→EndpointSlice, label vs annotation), M4 (readiness → ready:false в слайсе), M3 (spec vs status — ADDRESS это status; reconcile), M7 (TLS-серт это **ФАЙЛ** → Secret/volume, не env), сети M12 (L7-балансировка, X-Forwarded-For), сети M9 (TLS/mTLS, SNI).
  - **Ведёт к:** чекпоинт Ф4, M16 (RBAC — Forbidden у ivan.tsimbalist на cluster scope/endpointslices живьём), M18 (NetworkPolicy перед контроллером), M23 (cert-manager как оператор: CR→status→логи; admission-webhook), M25 (mesh gateway vs Ingress, Gateway API).
  - **Сквозные темы:** №4 (контроллер = watch→reconcile — весь модуль), №5 (L7-слой поверх плоской сети и Service), №3 (selector→EndpointSlice→upstream), №2 (Ingress — объект в etcd), №7 (RBAC-границы, роли в Gateway API).

### **ð Что должно остаться в голове через полгода**

  - **Ingress = правило (etcd), ingress-controller = под-исполнитель (живой nginx, reconcile).** Пустой ADDRESS → никто не подхватил (нет контроллера / не тот класс). Трафик течёт сквозь под контроллера, объект — сбоку.
  - **В upstream идёт pod IP напрямую (из EndpointSlice), не ClusterIP.** Балансирует сам nginx по запросам → gRPC размазывается. readiness ready:false держит под вне ротации.
  - **502 vs 404 = индикатор слоя.** Кто нарисовал страницу — тот дожил. 502 — бэкенд лёг (ниже контроллера). 404/Fake Cert — правило не нашлось (в объекте Ingress).
  - **TLS терминируется дважды за CF, два независимых серта.** SNI (открытым текстом до шифрования) выбирает серт, Host выбирает бэкенд. Серт — ФАЙЛ в Secret, не env.
  - **ssl-redirect: false** **за CF Flexible — не костыль, а необходимость** (иначе петля редиректов от несовпадения HTTPS-браузер / HTTP-origin). Gateway API — будущая замена Ingress: типизированные поля + разделение ролей.

  
  

# M13. Scheduler, requests/limits, QoS  

## **M13. Scheduler, requests/limits, QoS**

**Одной фразой:** два числа в одном YAML-блоке исполняются тремя разными компонентами в трёх разных местах — requests это бронь у scheduler'а и вес при драке, limits это потолок в cgroup, а QoS — лишь очередь на выселение при беде на узле.

### **ð§  Ментальная модель**

**Бухгалтерия и факт живут независимо, и никто их не сверяет.** Scheduler ведёт учёт **броней** (requests) и не смотрит на реальное потребление никогда. Ядро исполняет **потолки** (limits) и не знает ни про узел, ни про QoS. kubelet следит за **фактом на узле** и при беде выселяет — вот только здесь появляется QoS. Аналогия: requests — бронь столика в ресторане (место держат, даже если ты не пришёл), limits — потолок счёта (превысил по еде — выгонят), QoS — порядок, в котором выставляют гостей, если зал внезапно горит.

**Принцип eviction в одну строку — выселяют того, кто наврал сильнее всего:** метрика ранжирования это фактическое потребление − собственный request. Всё остальное (три класса QoS) выводится отсюда.

### **Что важно знать**

  - **requests** **— не «сколько нужно приложению», а бронь** — scheduler вычитает это число из allocatable узла и записывает в учёт; реальное потребление не проверяет никто.
  - **Scheduler НИКОГДА не смотрит на реальное потребление** — узел может быть забит по броням и пуст по факту (и наоборот) → Pending с Insufficient memory при top в 30% — норма, а не противоречие.
  - **capacity** **vs** **allocatable** — capacity − kube-reserved − system-reserved − eviction-threshold = allocatable; scheduler раздаёт **только** **allocatable**. Обе резервации по умолчанию **пустые** → в kind и голом kubeadm capacity == allocatable.
  - **Память несжимаема, CPU сжимаем** — время можно нарезать порциями, байты отобрать нельзя → отсюда вся разница в поведении.
  - **Превысил** **limits.memory** **→ OOMKilled немедленно** — ядро, cgroup memory.max, exit 137, никакого grace-периода. Убивается **контейнер**, не под → kubelet рестартит по restartPolicy.
  - **Превысил** **limits.cpu** **→ throttling** — под Running, 1/1, RESTARTS 0, логи чистые. **В** **kubectl** **не видно вообще**, только cpu.stat / метрика container\_cpu\_cfs\_throttled\_seconds\_total.
  - **limits.cpu: 200m** **→** **cpu.max = "20000 100000"** — каждые 100 мс отпускается 20 мс CPU-времени; израсходовал раньше — ждёшь следующего окна. Потолок работает **всегда**, даже на пустом узле.
  - **requests.cpu** **работает и в рантайме** — cpu.weight в cgroup, доля **при конкуренции** (500m vs 100m → время делится 5:1). Свободен узел — под с requests.cpu: 100m съест хоть 4 ядра.
  - **1 CPU** **= один логический процессор** (ядро/гипертред/vCPU), m = тысячная доля → 2500m легально, потому что меряется **время**, а не куски железа.
  - **QoS — это ТОЛЬКО очередь на eviction при node pressure** — **Guaranteed** (у всех контейнеров заданы CPU **и** память, и по обоим requests == limits) → **Burstable** (задано хоть что-то, но не равно) → **BestEffort** (не задано ничего, выселяют первым).
  - **Guaranteed НЕ спасает от OOMKilled по своему лимиту** — ядро про QoS не знает, оно видит одно число в memory.max. QoS живёт только в механизме kubelet.
  - **Под, потребляющий МЕНЬШЕ своего** **request****, выселяют последним** — даже если он Burstable; превышение отрицательное → должником не является.
  - **emptyDir: {medium: Memory}** **= tmpfs** — страницы списываются в **ту же memory cgroup**, что и процесс → файл на 800Mi при limits.memory: 1Gi убивает под, хотя приложение ест 300Mi. Без sizeLimit tmpfs получает **половину RAM узла**.
  - **Scheduler работает в две фазы** — **filtering** (предикаты, да/нет: ресурсы, nodeSelector, taints, hostPort, зона тома) → **scoring** (баллы 0–100: LeastAllocated, ImageLocality, PodTopologySpread, affinity). Pending бывает **только от filtering** — скоринг отвергнуть узел не может.
  - **pods: 110** — четвёртое измерение учёта, жёсткий потолок числа подов на узел независимо от свободных ресурсов.

### **⭐ Бест-практис (golden path)**

  - **requests** **на оба ресурса — всегда (дефолт, без вариантов)** — без них под BestEffort → первый на выселение, и HPA не работает в принципе (M15).
  - **limits.memory** **— всегда (дефолт)** — единственная защита узла от утечки. Ставить с запасом **\~20–50%** над реальным пиком, не впритык.
  - **limits.memory \!= requests.memory** **для обычных сервисов** — равенство даёт Guaranteed, но убивает при первом всплеске. Guaranteed — осознанный выбор для критичного (БД, брокеры), **не дефолт**.
  - **limits.cpu** **— консенсуса НЕТ, спор живой.** Против (Tim Hockin/Google, Zalando, Datadog): троттлинг — рукотворная деградация, cpu.weight уже защищает соседей, без лимита под берёт простаивающее время бесплатно. За: предсказуемость и capacity planning. **Ставить точно** — мультитенантный кластер с чужими нагрузками, batch рядом с latency-критичным, нагрузочное тестирование.
  - **Числа брать из метрик, не из ощущений** — requests ≈ p50–p75 реального за неделю, limits.memory ≈ пик + запас. Инструмент — **VPA в режиме** **recommender** (только советует, ничего не трогает, M15).
  - **kube-reserved** **/** **system-reserved** **выставлять явно** — managed-облака прописывают сами, **голый kubeadm приедет без них** → сумма requests доедет до 100% физической памяти.
  - **medium: Memory** **— только под мелкое и осознанное** (кэш, сокеты, /dev/shm), **всегда** с sizeLimit, и limits.memory считать как «аппетит приложения + размер tmpfs».

### **ð§ Команды-первого-выбора**

kubectl describe node \<node\> | grep -A 12 "Capacity:"        \# capacity vs allocatable — есть ли вычет

kubectl describe node \<node\> | grep -A 8 "Allocated resources"  \# БРОНИ — то, что видит scheduler

kubectl top node \<node\>                                       \# ФАКТ — то, что видит kubelet (два разных мира)

kubectl get pod \<p\> -o jsonpath='{.status.qosClass}'          \# QoS-класс

kubectl exec \<p\> -- cat /sys/fs/cgroup/cpu.max                \# "20000 100000" = limits.cpu 200m

kubectl exec \<p\> -- cat /sys/fs/cgroup/cpu.stat              \# nr\_throttled + throttled\_usec — троттлинг живьём

kubectl describe pod \<p\> | grep -A 5 "State:"                \# Reason: OOMKilled, Exit Code: 137

kubectl get events --field-selector reason=FailedScheduling  \# почему Pending

  

### **⚠️ Грабли и как не наступить**

  - **«Приложение тормозит, ошибок нет, поды здоровы»** → CPU throttling — kubectl не покажет ничего → смотреть cpu.stat / container\_cpu\_cfs\_throttled\_seconds\_total. Особенно JVM/Go/Node: потоков больше, чем квота, все вместе досиживают период.
  - **Регулярный OOMKilled без утечки** → limits.memory == requests.memory + всплеск, ИЛИ tmpfs//dev/shm внутри того же лимита.
  - **CrashLoopBackOff****, логи пустые, падает мгновенно** → emptyDir: {medium: Memory} переживает рестарт **контейнера** (живёт по UID пода) → новый контейнер стартует в cgroup, где память уже занята с прошлой жизни.
  - **Pending** **+** **Insufficient memory****, а** **top** **показывает 30%** → **не противоречие** → идти в Allocated resources, не в top; лечить завышенные requests соседей, а не докупать память.
  - **Узлы «падают по очереди»** → kube-reserved/system-reserved не заданы → сумма requests = 100% физической → kubelet голодает → Node NotReady → поды переезжают → каскад на соседей.
  - **Новый под садится на перегруженный узел и убивает чужие** → scheduler видит свободные брони, не видит факт → node pressure → выселяют **не новичка**, а самого большого должника.
  - **--previous** **на поде с** **RESTARTS: 0** → previous terminated container not found — предыдущего инстанса не существует → смотреть обычный kubectl logs.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«CPU throttle vs OOMKilled — почему разница принципиальна?»** → сжимаемый vs несжимаемый ресурс: время нарезается порциями, байты отобрать нельзя, только вместе с процессом. Троттлинг тихий (бьёт по p99), OOM громкий (exit 137).
  - **«Спасёт ли Guaranteed от OOMKilled?»** → **нет.** Guaranteed живёт только в eviction по node pressure (kubelet). Свой limits.memory исполняет ядро, оно про QoS не знает вообще. Добить: Guaranteed не «защищён», он просто математически не может стать должником.
  - **«Как scheduler выбирает узел?»** → filtering (булево: влезают ли requests, taints, nodeSelector) → scoring (0–100: LeastAllocated, ImageLocality, topology spread). Считает **брони**, не факт. Pending — только от filtering.
  - **«Кого выселят первым?»** → по превышению над собственным request. BestEffort всегда первый (бронь ноль → всё сверх). Под, сидящий в своей броне, — последний, даже будучи Burstable.
  - **«Стоит ли ставить** **limits.cpu****?»** → честный ответ: консенсуса нет, назвать обе позиции. limits.memory — да, всегда.

### **ð Связи**

  - **Опирается на:** M2 (cgroups, memory.max/cpu.max — теперь видны живьём), M4 (restartPolicy, CrashLoop, QoS-предпросмотр), M8 (emptyDir, том живёт по UID пода).
  - **Ведёт к:** M14 (filtering во всю ширину — taints/affinity/topology spread), M15 (HPA не работает без requests; VPA recommender; Cluster Autoscaler реагирует на нескедулящийся под), M17 (LimitRange + ResourceQuota как принудительные дефолты), M19 (диагностика Pending/OOM/Evicted), M20 (метрика троттлинга, metrics-server для top).
  - **Сквозные темы:** №6 (requests/limits правят жизнью пода — ядро модуля), №1 (scheduler как контроллер: смотрит spec → действует), №2 (Node.status.allocatable — обычная запись в etcd, из неё вся бухгалтерия).

### **ð Что должно остаться в голове через полгода**

  - **Scheduler считает брони (****requests****), kubelet смотрит факт, ядро исполняет потолки (****limits****) — три независимых механизма, между ними нет сверки.** Pending при пустом top — отсюда.
  - **Превысил свой** **limits.memory** **→ OOMKilled при любом QoS.** QoS работает **только** когда плохо узлу целиком, и означает лишь порядок в очереди.
  - **Выселяют того, кто наврал сильнее** — метрика это потребление − request, а не абсолютные цифры и не «красивый» YAML.
  - **limits.cpu** **режет всегда, даже на пустом узле** — троттлинг невидим в kubectl, ищется только в метриках; limits.memory ставить обязательно, limits.cpu — спорно.
  - **requests** **с потолка = главный источник боли:** завысил → кластер забит по бумагам и пуст по факту; занизил → выселяют первым. Числа брать из метрик.

  
  

# M14. Управление размещением подов  

## **M14. Управление размещением подов**

**Одной фразой:** набор ручек, которыми ты вмешиваешься в выбор узла scheduler'ом — притянуть, оттолкнуть, развести, приоритизировать; всё сводится к паре «жёстко/мягко» и к вопросу «кто на что смотрит».

### **ð§  Ментальная модель**

Scheduler делает два этапа: **filtering** (кто вообще подходит — булево) → **scoring** (кто лучше — 0–100). Все ручки модуля — это вмешательство либо в filtering (сделать узел невозможным/обязательным), либо в scoring (сделать желательным/нежелательным). Одна идея — **вилка «жёстко/мягко»** — повторяется в каждой ручке под разными историческими именами. И сквозное разведение: **scheduler всегда считает брони (requests), никогда факт** — размещение это «математика мест», а не реальная загрузка.

### **Что важно знать**

  - **Две группы правил.** *Нода ↔ под* (смотрят на метки **узла**): nodeSelector, node affinity, taints/tolerations. *Под ↔ под* (смотрят на метки **других подов**): pod affinity, pod anti-affinity, topology spread.
  - **nodeSelector** — притянуть к узлу с меткой, только точное =, только жёстко → нет узла → Pending.
  - **node affinity** — улучшенный nodeSelector: (1) мягкость (preferred) + (2) богатые операторы In/NotIn/Exists/DoesNotExist/Gt/Lt. Единственная причина его существования поверх nodeSelector.
  - **taint на узле, toleration на поде** — узел отталкивает, под терпит. NoSchedule/NoExecute → filtering; PreferNoSchedule → scoring. NoExecute ещё и **выгоняет** уже живущие поды без toleration.
  - **Toleration РАЗРЕШАЕТ, но не ПРИТЯГИВАЕТ** → для эксклюзива («только эти поды на этих узлах») нужен taint+toleration (кого пускать) **плюс** nodeSelector/affinity (куда загонять).
  - **pod anti-affinity** — «развести реплики по узлам». required + реплик \> узлов → лишние висят Pending. Golden path для «раскидай» — preferred или topology spread, не required.
  - **topology spread** — раскидать N подов **равномерно** по доменам. Поля: maxSkew (допустимая **разница** между доменами, НЕ потолок на домен), topologyKey (метка узла, по значению которой группируем домены), whenUnsatisfiable (DoNotSchedule=жёстко / ScheduleAnyway=мягко), labelSelector.
  - **skew считается по НАЛИЧИЮ узла с меткой, а не по «влезает ли под».** Забитый/недоступный узел выкидывается из *filtering*, но остаётся в *подсчёте skew* как домен с 0 → может дать Pending при DoNotSchedule.
  - **PriorityClass + preemption** — не «куда», а «кого подвинуть». Высокий priority + не влезает **по броням** → scheduler выселяет поды с меньшим priority, чтобы освободить **брони**. Preemption считает requests, не факт.
  - **Переезда живых подов не бывает.** Под прибит к узлу на всю жизнь; «переехать» = контроллер убил старый и создал новый. Ребаланс — только при пересоздании.

### **⭐ Бест-практис (golden path)**

  - **«Раскидай реплики по узлам/зонам» → topology spread с** **ScheduleAnyway** (дефолт), либо preferred anti-affinity. DoNotSchedule/required — только когда неравномерность недопустима в принципе (жёсткая зональная отказоустойчивость), и тогда держат запас доменов ≥ реплик.
  - **«Только эти поды на выделенных узлах» → taint узлов + toleration подов И** **nodeSelector****/affinity одновременно.** Один toleration не загоняет — часть подов расселится по обычным узлам.
  - **Запоминать не имена, а поведение:** «этот вариант роняет под в Pending, если условие не выполнить?» Да → жёсткий; нет → мягкий. Имя (required/NoSchedule/DoNotSchedule) вторично.

### **ð§ Команды-первого-выбора**

kubectl label node \<node\> disktype=ssd            \# повесить метку на узел (под nodeSelector/affinity)

kubectl get nodes --show-labels                    \# какие метки на узлах есть

kubectl taint node \<node\> dedicated=rtb:NoSchedule \# оттолкнуть поды без toleration

kubectl describe node \<node\> | grep Taints         \# какие taint'ы на узле

kubectl get pods -o wide                            \# на какие узлы реально сели поды

kubectl describe pod \<name\> | grep -A5 Events       \# FailedScheduling → почему не сел

  

### **⚠️ Грабли и как не наступить**

  - **required** **anti-affinity + реплик больше, чем узлов** → лишние реплики вечно Pending. Добавил реплику под нагрузку — не стартует.
  - **DoNotSchedule** **+ узел выпал/забился** → перекос не выровнять → новые реплики зависают, хотя место в кластере формально есть.
  - **maxSkew** **прочитан как «потолок на домен»** → неверный прогноз посадки. Это **разница** между доменами: 1-1-1 → 2-1-1 это перекос 1, ок.
  - **taint+toleration без nodeSelector** → поды расселились шире выделенных узлов (toleration не притягивает).
  - **Ждать от topology spread реакции на новый узел** → не дождёшься, spread пассивен, живые поды не двигает (в отличие от DaemonSet).

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Под** **Pending****, узлы вроде свободны — причины?»** → taint без toleration / nodeSelector без подходящего узла / required anti-affinity или DoNotSchedule не может развести / не хватает **requests** (M13). Проверять describe pod → Events → FailedScheduling.
  - **«Чем topology spread отличается от DaemonSet?»** → DaemonSet **активен** (watch'ит Nodes, на каждый узел свой под, реагирует на приход/уход узла); spread **пассивен** (правило только при посадке, число подов задаёт replicas, живые не мигрирует).
  - **«Preempt vs evict — кто смотрит на реальную загрузку?»** → evict (kubelet, node pressure, **факт**). Preempt (scheduler, priority, **брони**). Ловушка: приклеить preemption к «реальной памяти».
  - **«В момент посадки scheduler смотрит на брони или факт?»** → только брони; факт (OOM/eviction) — это уже надзор за живым подом (ядро/kubelet), 24/7, отдельный мир.

### **ð Связи**

  - Опирается на: M13 (filtering/scoring, requests/брони, QoS), M6 (labels/selectors — на них стоят все правила), M5 (DaemonSet, Deployment-контроллер пересоздаёт поды), M8 (RWO при переезде на другой узел).
  - Ведёт к: M15 (Cluster Autoscaler добавляет узел, когда под не влезает по броням), M22 (drain/cordon + PodDisruptionBudget при апгрейдах), M18 (SecurityContext/capabilities — ядерный слой рядом).
  - Сквозные темы: №3 (labels/selectors как клей), №4 (контроллер как паттерн — DaemonSet reconcile), №6 (requests/scheduler правят жизнью пода).

### **ð Что должно остаться в голове через полгода**

  - **Вилка «жёстко/мягко» — одна на всё, три костюма:** required/preferred, NoSchedule/PreferNoSchedule, DoNotSchedule/ScheduleAnyway. Вопрос всегда один: роняет в Pending или садится?
  - **taint на узле, toleration на поде; toleration разрешает, но не притягивает** → для эксклюзива нужен ещё nodeSelector/affinity.
  - **maxSkew** **= разница между доменами, не потолок; домен считается по наличию узла с меткой, даже если под туда не влезает.**
  - **Переезда живых подов не бывает** — весь ребаланс идёт через пересоздание контроллером. DaemonSet активен (гоняется за узлами), topology spread пассивен (ждёт посадки).
  - **Preemption считает брони и живёт в scheduler** — это верхняя половина мира (requests), а не нижняя (факт: OOM/eviction).

  
  

# M15. Автоскейлинг  

## **M15. Автоскейлинг**

**Одной фразой:** три независимых контроллера на разных слоях — **HPA** крутит число подов, **VPA** крутит размер пода, **Cluster Autoscaler** крутит количество узлов, и все трое принимают решения по **броням**, а не по факту.

### **ð§  Ментальная модель**

Каждый из трёх — обычный **reconcile-контроллер** (сквозная тема №4): наблюдает → сравнивает с желаемым → подкручивает. Разница только в том, **какую ручку он крутит**. Ключ к пониманию — задать два вопроса: *«на каком слое живёт?»* (поды или железо) и *«смотрит на брони или на факт?»*. Ответ на второй одинаковый у всех троих — **на брони**, и именно отсюда растут все «необъяснимые» инциденты: узлы по top пустые, а поды Pending и CA докидывает железо.

### **Что важно знать**

  - **HPA** → правит spec.replicas воркладу по ссылке scaleTargetRef — прямая ссылка **по имени**, не через labels (селектору тут негде сломаться).
  - **Формула HPA** — желаемые = ceil(текущие × утилизация / цель) — **пропорция, не инкремент**: 3 реплики при 90% и цели 50% дают сразу 6, а не 4.
  - **Утилизация считается как** **факт / requests.cpu** — без requests знаменателя нет → HPA по утилизации физически неработоспособен.
  - **Цепочка метрик** — cgroup в ядре → **cAdvisor** внутри kubelet → **metrics-server** (агрегирует, держит в памяти, ничего не пишет на диск) → **Metrics API** в api-server → HPA-контроллер. kubectl top пьёт из того же крана.
  - **\<unknown\>** **в TARGETS** → проблема **источника метрик**, а не выборки объектов — либо нет metrics-server, либо нет requests.cpu.
  - **Асимметрия HPA** — вверх мгновенно, вниз через **стабилизационное окно** (по умолчанию 300 с) — защита от флаппинга.
  - **VPA** → правит requests/limits самого пода, применяет **пересозданием пода**; режимы Off (только рекомендации) / Initial / Auto.
  - **HPA и VPA на одной метрике дерутся** — VPA двигает requests, то есть **знаменатель формулы HPA** → утилизация в глазах HPA скачет при неизменном факте → маятник с рестартами.
  - **Cluster Autoscaler** → триггерится **Pending****-подами**, а не загрузкой узлов; докинет узел даже когда узлы по факту пустые, если разобраны брони.
  - **Симуляция посадки** — перед заказом узла CA виртуально сажает Pending-под на шаблон будущего узла (allocatable, labels, taints) и заказывает, **только если под поместится**; иначе пишет pod didn't trigger scale-up.
  - **Scale-down у CA медленный и обвешан блокерами** — PDB, поды без контроллера, anti-affinity, safe-to-evict: "false", emptyDir, порог утилизации (\~50% по броням).
  - **KEDA** → не заменяет HPA, а **кормит его** через External Metrics API — даёт правильный сигнал (длина очереди / лаг вместо косвенного CPU) и **scale-to-zero**, которого голый HPA не умеет.

### **⭐ Бест-практис (golden path)**

  - **requests** **обязательны на всём, что скейлится** — дефолт. Без них не работают ни HPA, ни осмысленная посадка, ни CA. Отступают только на заведомо одноразовых Job'ах.
  - **VPA в** **updateMode: "Off"** **как источник цифр для** **requests** — дефолт в проде. VPA считает рекомендации, человек переносит их в манифест. Полный Auto берут редко — из-за рестартов подов и конфликта с HPA.
  - **HPA и VPA — только на разные ресурсы** (HPA по CPU, VPA по памяти) либо не вместе вообще. Отступление от этого — гарантированный флаппинг.
  - **Скейлить воркеры очередей через KEDA, а не через CPU** — дефолт для I/O-bound нагрузок: CPU у такого воркера не растёт при завале очереди, сигнал ложный.
  - **PDB на всё, что переживает scale-down и апгрейды** — но осознанно: minAvailable: 1 при 1 реплике намертво замораживает узел.

### **ð§ Команды-первого-выбора**

kubectl autoscale deployment web --cpu-percent=50 --min=2 --max=10   \# создать HPA императивно

kubectl get hpa -w                          \# TARGETS: факт/цель + REPLICAS в динамике

kubectl describe hpa web                    \# события масштабирования + причина \<unknown\>

kubectl top nodes                           \# пробник: жив ли источник метрик (метрики vs requests)

kubectl get pod \<p\> -o jsonpath='{.spec.containers\[\*\].resources.requests}'   \# есть ли знаменатель

kubectl describe vpa \<name\>                 \# рекомендации VPA (lowerBound/target/upperBound)

kubectl -n kube-system logs -l app=cluster-autoscaler | grep -i "scale"      \# почему узел не приехал

  

### **⚠️ Грабли и как не наступить**

  - **HPA стоит, нагрузка есть, реплики не растут;** **TARGETS: \<unknown\>/50%** → нет metrics-server **или** нет requests.cpu → развести одной командой kubectl top nodes.
  - **Реплики скачут туда-сюда каждую минуту** → HPA и VPA сидят на одном ресурсе → VPA двигает знаменатель → развести по ресурсам или VPA в Off.
  - **Поды** **Pending****, CA настроен, узлы не приезжают** → искать в логах CA pod didn't trigger scale-up → под не помещается в шаблон узла по ресурсам / нет нужной метки / есть taint без toleration.
  - **Полупустые узлы не удаляются, счёт капает** → PDB блокирует выселение / голые поды без контроллера / safe-to-evict: "false" / узел выше порога утилизации **по броням**.
  - **«Узлы же пустые по** **top****, зачем CA докинул железо»** → CA и scheduler считают **брони**; top показывает факт. Смотреть describe node → Allocated resources.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«HPA добавляет реплики по одной?»** → Нет, пропорционально: ceil(текущие × факт/цель). При скачке 10× прыгнет к max за один шаг.
  - **«Почему HPA не работает без requests?»** → Он считает не абсолютную нагрузку, а **утилизацию** — долю от брони. Нет брони → нет знаменателя → \<unknown\>.
  - **«Что триггерит Cluster Autoscaler?»** → Pending-поды по броням, а не загрузка узлов. Ловушка вопроса — в слове «загрузка».
  - **«Зачем KEDA, если есть HPA?»** → Правильный сигнал для I/O-bound воркеров (длина очереди) + scale-to-zero. KEDA не заменяет HPA, а поставляет ему метрику.

### **ð Связи**

  - Опирается на: **M13** (requests/limits, QoS, брони vs факт), **M14** (кто где сядет, PDB, preempt vs evict), **M5** (Deployment/ReplicaSet как объект скейла), **M3** (reconcile-петля).
  - Ведёт к: **M17** (LimitRange/ResourceQuota как дефолты для requests), **M20** (metrics-server, Prometheus, метрика throttling), **M22** (drain/PDB при апгрейдах), **M23** (KEDA и VPA — живые операторы с CRD).
  - Сквозные темы: **№4** (контроллер как универсальный паттерн), **№6** (requests/limits правят всей жизнью пода), **№1** (декларативность: ты задаёшь min/max, контроллер держит).

### **ð Что должно остаться в голове через полгода**

  - **Три слоя, три ручки:** HPA — число подов, VPA — размер пода, CA — количество узлов. Первые два двигают поды, третий двигает железо через API облака.
  - **Все трое считают брони, не факт.** Это же корень Pending при пустом top и корень «CA докинул узел на пустом кластере».
  - **Нет** **requests** **→ нет автоскейла.** HPA делит на них; CA по ним симулирует посадку; scheduler по ним фильтрует.
  - **HPA пропорционален, не инкрементален** — ceil(текущие × факт/цель), вверх мгновенно, вниз через окно стабилизации.
  - **HPA + VPA на одной метрике = флаппинг**, потому что VPA двигает знаменатель формулы HPA. Прод-дефолт: VPA в recommendationOnly.

  
  

# M16. RBAC и identity  

## **M16. RBAC и identity**

**Одной фразой:** каждый запрос к api-server проходит три независимые ступени (**кто ты → что тебе можно → валидно ли**), причём права не хранятся на человеке — они возникают только когда отдельный объект-**Binding** связал список правил (**Role**) с твоим именем или группой.

### **ð§  Ментальная модель**

**Права — не свойство субъекта, а совпадение строки.** У api-server нет карточки «Иван: можно A, B, C». При каждом запросе он берёт три строки, извлечённые из предъявленного документа (имя + группы), и перебирает **все** биндинги кластера: встречается ли хоть одна из них в subjects? Нашёл → идёт по roleRef смотреть, разрешает ли роль этот глагол на этот ресурс. Не нашёл → 403.

Отсюда вся асимметрия: **ServiceAccount — объект в etcd, а пользователь — нет.** Человек приходит с сертификатом, подписанным внешним CA; кластер узнаёт о нём в момент запроса и забывает после. Хранить нечего — поэтому kubectl get users не существует.

### **Что важно знать**

  - **Три ступени, три разных механизма и три разных отказа** — **authentication** (КТО, серт/токен/OIDC → 401) → **authorization** (ЧТО можно, RBAC → 403 Forbidden) → **admission** (ВАЛИДНО ли, webhooks → ошибка от конкретного контроллера). Forbidden означает, что первая ступень **прошла**: api-server тебя опознал и потому смог отказать адресно.
  - **Имя приходит из документа, а не из базы** — api-server проверяет **подпись** серта доверенным CA и **читает поле** **CN** как username, O как groups. Аналогия — паспорт: пограничник не звонит в реестр, он проверяет подлинность и читает страницу.
  - **system:authenticated** — группа, которую api-server дописывает сам всем, кто прошёл authentication. В сертификате её нет.
  - **Слово** **User** **в тексте отказа — не тип объекта**, а строка, прочитанная из серта и живущая только на время обработки запроса. Следствие: юзера **нельзя удалить** (нечего), нельзя получить список всех, отзыв доступа = снести биндинги или ротировать CA.
  - **Права разложены на две части** — **Role/ClusterRole** содержит rules (что можно, кому — не сказано); **RoleBinding/ClusterRoleBinding** содержит subjects (кому) и roleRef (какая роль). Role без Binding — мёртвый груз, Binding на несуществующую Role — ноль прав.
  - **Три вопроса:** **что** можно → Role · **кому** → subjects биндинга · **где** → тип биндинга и его namespace. Область задаёт **биндинг**, не роль.
  - **Три комбинации** — Role+RoleBinding (один ns) · ClusterRole+ClusterRoleBinding (везде) · **ClusterRole****+****RoleBinding** (права кластерной роли, но только в ns этого биндинга — самый частый приём). Обратной комбинации **не существует**: Role+ClusterRoleBinding api-server отвергнет.
  - **ClusterRole умеет то, что Role не может в принципе** — права на **cluster-scope** ресурсы (nodes, pv, storageclasses, namespaces) и на **nonResourceURLs** (/healthz, /metrics, /version). Отсюда: get pods работает, get nodes — Forbidden.
  - **Модель разрешающая** — объекта «запретить» не существует. Нет разрешения = запрещено. «Отобрать право» = удалить биндинг.
  - **subjects** **бывает трёх видов** — User и Group (просто строки, объектов за ними нет) и ServiceAccount (реальная запись в etcd).
  - **ServiceAccount — identity для процесса в поде.** Под без явного serviceAccountName получает default своего namespace; kubelet монтирует токен в /var/run/secrets/kubernetes.io/serviceaccount/ (token + ca.crt + namespace). Приложение шлёт его как Authorization: Bearer.
  - **Имя SA — жёсткий формат** system:serviceaccount:\<ns\>:\<имя\>. Дальше **тот же самый RBAC** — отдельной системы прав для подов нет.
  - **Один SA — сколько угодно подов.** Ссылка **по имени** (spec.serviceAccountName), не по меткам → разъехаться селектору негде. Правильная единица — **приложение**, а не под.
  - **Опасность** **default** **SA — не в правах** (их у него нет), а в том, что токен смонтирован всем подряд, и в соблазне повесить на него биндинг «для удобства» → права получат **все** поды namespace.
  - **base64** **в Secret — кодировка, не шифрование.** Декодируется одной командой, ключа нет. Сам факт помещения данных в Secret безопасности **не добавляет**.
  - **Реальная защита секретов размазана по четырём независимым слоям** — RBAC на get/list secrets (основной) · шифрование at-rest в etcd (по умолчанию **выключено**) · монтирование в **tmpfs**, а не на диск узла · совместимость с внешним инструментарием.
  - **list secrets** **= чтение всех секретов namespace** — list возвращает объекты целиком вместе с data. Поэтому в осмысленных ролях секреты выносят отдельно и не покрывают маской \*.
  - **type** **у Secret не декоративен** — kubernetes.io/tls (сюда пишет cert-manager) · kubernetes.io/dockerconfigjson (imagePullSecrets) · kubernetes.io/service-account-token · Opaque (дефолт). Куб ищет секреты **нужного типа** в нужных местах.

### **⭐ Бест-практис (golden path)**

  - **ClusterRole + RoleBinding — рабочий дефолт.** Роль пишется один раз, область задаётся типом биндинга. Своя Role — только под права, осмысленные ровно в одном namespace. Чаще всего писать вообще ничего не нужно: в кластере уже лежат view, edit, admin, cluster-admin.
  - **Права вешать на группу, а не на человека.** Админ выдаёт devs один раз и штампует серты с O=devs — иначе каждый новый сотрудник требует новых объектов.
  - **Отдельный SA на каждое приложение**, которому нужен API. На default **никогда** не вешать биндинги.
  - **automountServiceAccountToken: false** для всех, кому API не нужен — это большинство подов. Взломали контейнер → нет валидного токена к api-server.
  - **Секреты доставлять файлом, а не env** — env наследуется всеми дочерними процессами, утекает в /proc/\<pid\>/environ, краш-дампы, отладочные ручки и логи фреймворков при старте. Файл читается один раз и не расползается.
  - **Секреты не хранить в Git** → **SOPS** (шифрование значений в файле) · **sealed-secrets** (расшифровать может только контроллер в кластере) · **External Secrets Operator / Vault** (секрет вообще вне кластера).
  - **Шифрование at-rest включать явно** (EncryptionConfiguration) — managed-облака обычно ставят сами, голый kubeadm приедет без него, и бэкап etcd унесёт все секреты открытым текстом.

### **ð§ Команды-первого-выбора**

kubectl auth whoami                            \# кто я для api-server: Username + Groups (любой метод authn)

kubectl auth can-i --list                      \# ПОЛНАЯ карта моих прав в этом ns — итог, а не биндинги

kubectl auth can-i list endpointslices         \# точечная проверка: yes/no

kubectl auth can-i get secrets --all-namespaces

kubectl auth can-i list cm -n demo --as=system:serviceaccount:demo:my-app   \# права чужого SA

kubectl get pod \<p\> -o jsonpath='{.spec.serviceAccountName}'   \# под чьей identity бежит под

kubectl get secret \<s\> -o jsonpath='{.data.password}' | base64 -d           \# вот тебе "шифрование"

  

### **⚠️ Грабли и как не наступить**

  - **Forbidden** **— читать текст целиком, там все четыре параметра решения** → cannot list resource "X" in API group "Y" in the namespace "Z". Чаще всего спотыкается не на «кто», а на **apiGroup**, которую в роль не вписали.
  - **Роль отстала от версии куба** → endpoints (core-группа) есть, endpointslices (discovery.k8s.io) нет → отказ выглядит как политика безопасности, а на деле просто **не перечислили новую группу**. Обходной путь для диагностики — старый kubectl get endpoints.
  - **Голая** **\*** **в выводе** **can-i --list** **— это НЕ «всё вообще»**, а все ресурсы **core**-группы. Права выданы по группам API, каждая отдельной строкой (\*.apps, \*.batch, \*.networking.k8s.io).
  - **Role написали, Binding забыли** → прав нет, а объект в кластере есть и выглядит рабочим. Самая частая точка отказа в цепочке.
  - **Binding создали не в том namespace** → вторая по частоте.
  - **ClusterRoleBinding** **вместо** **RoleBinding** → права выданы глобально там, где хотели один namespace.
  - **Secret без нормального RBAC = ConfigMap с лишним шагом** — и наоборот, ConfigMap под жёстким RBAC закрыт от чтения через API ровно так же. Разница живёт **вне** RBAC (etcd, tmpfs, describe, экосистема).
  - **kubectl describe** **показывает ConfigMap целиком и скрывает содержимое Secret** — идеальный RBAC не спасёт от слитого скриншота.
  - **Кластер под платформой (Deckhouse и т.п.)** → RBAC задаётся её CRD (ClusterAuthorizationRule с уровнями User/Editor/Admin/ClusterAdmin), а обычные Role/Binding **генерируются**. Править сгенерированное бесполезно — затрёт при reconcile. Просить надо изменение в CRD платформы.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Как api-server понимает, кто к нему пришёл?»** → mTLS, проверка подписи серта доверенным CA, чтение CN как username и O как groups. Объекта User в кластере нет — имя приезжает в документе при каждом запросе, а не хранится.
  - **«Role vs ClusterRole — кроме зоны действия?»** → ClusterRole умеет cluster-scope ресурсы и nonResourceURLs, чего Role не может в принципе; ClusterRole переиспользуема, Role невидима снаружи своего ns. На практике почти всегда пишут ClusterRole, а область задают **типом биндинга**.
  - **«Под падает с** **forbidden** **— как дебажишь?»** → три шага: какой SA у пода → есть ли Role с нужным verb+resource+apiGroup → есть ли Binding, связывающий SA с ролью **в правильном namespace**. Проверка без гаданий: auth can-i --as=system:serviceaccount:\<ns\>:\<sa\>.
  - **«Почему Secret не защищён?»** → base64 = кодировка, декодируется одной командой. Защита — RBAC + шифрование at-rest (по умолчанию выключено) + tmpfs. Тип объекта сам по себе не добавляет ничего.
  - **«Как отозвать доступ у уволившегося?»** → удалить биндинги; серт на руках продолжит проходить authentication до истечения срока. Это известная слабость сертификатной аутентификации → в больших конторах **OIDC**, где отзыв работает по-настоящему.

### **ð Связи**

  - **Опирается на:** M1 (kubeconfig, контексты, «всё через одну дверь»), **M1.1** (TLS/mTLS до api-server, CN=username, O=groups — прямая опора), M3 (всё — объект API в etcd), M7 (ConfigMap/Secret, доставка env vs файл).
  - **Ведёт к:** M17 (namespace как единица RBAC, мультитенантность), M18 (третья ступень — admission, PSS, OPA/Kyverno; secret-менеджмент), M20 (кто ходит в API за метриками), M22 (PKI, ротация сертов, bootstrap-токены), M23 (операторы под своим SA, admission webhooks).
  - **Сквозные темы:** **№7** (identity и трёхступенчатый контроль — ядро модуля), №2 (всё — объект API; Role/Binding/SA — обычные записи в etcd), №3 (клей — но здесь **по имени**, а не по меткам: roleRef и serviceAccountName жёсткие ссылки).

### **ð Что должно остаться в голове через полгода**

  - **Три ступени: authn (КТО,** **401****) → authz (ЧТО,** **403****) → admission (ВАЛИДНО, ошибка webhook).** Forbidden = первую ступень **прошёл**.
  - **Права не висят на человеке.** Они возникают только там, где Binding связал Role с именем или группой. Нет Binding — нет прав, независимо от того, сколько ролей написано.
  - **Role = что. Binding = кому и где.** Область задаёт **тип биндинга**, а не роль.
  - **ClusterRole + RoleBinding — рабочий дефолт:** кластерная роль, запертая в один namespace.
  - **Объекта User не существует, ServiceAccount существует.** Имя человека приезжает в сертификате, имя SA лежит в etcd. Отсюда: юзера нельзя удалить, SA можно.
  - **base64 ≠ защита.** Секрет защищён ровно настолько, насколько ограничен list secrets, зашифрован etcd и не утёк через describe.

  
  

# M17. Namespaces, квоты, мультитенантность  

## **M17. Namespaces, квоты, мультитенантность**

**Одной фразой:** namespace — это область имён, RBAC и квот, но **не** изоляция; тенант получается только когда на ns навешены четыре слоя разом.

### **ð§  Ментальная модель**

Namespace — не песочница, а **папка с ярлыком**. Он даёт три области (имена, RBAC, квоты) и не даёт четырёх изоляций (сеть, узлы, DNS-видимость, ресурсы сами по себе). Всё, что выглядит как «изоляция команд», собирается вручную из четырёх объектов: **Namespace + RoleBinding + ResourceQuota/LimitRange + NetworkPolicy**. Убери любой — дырка. И даже собранное целиком это **мягкая** изоляция: защита от ошибки, а не от злого умысла.

### **Что важно знать**

  - **Namespace даёт ровно три вещи** — область имён (Deployment/web в prod и в staging — разные объекты) → область действия RoleBinding → область счёта Quota/LimitRange.
  - **Namespace НЕ даёт** — сетевой изоляции (плоская сеть про ns не знает → NetworkPolicy, M18) → изоляции узлов (общее ядро, общий page cache) → скрытия DNS (любой под резолвит любой сервис по FQDN) → ограничения ресурсов само по себе.
  - **Что вне namespace вообще** — Node, PersistentVolume, StorageClass, ClusterRole/Binding, CRD, Namespace, IngressClass, PriorityClass. Проверка — kubectl api-resources --namespaced=false.
  - **Ingress: host — глобален, backend — локален.** Ingress-controller вотчит **все** ns и склеивает их в один nginx.conf → два Ingress с одним host в разных ns конфликтуют, побеждает **старший по** **creationTimestamp**, младший молча игнорится (warning в логах контроллера). При этом backend.service.name резолвится строго в своём ns.
  - **ResourceQuota** — суммарный потолок на ns, считает **брони** (requests), а не факт. Три группы: compute (requests.cpu, limits.memory) → storage (persistentvolumeclaims, requests.storage) → object count (pods, count/deployments.apps, services.loadbalancers).
  - **Квота проверяется на admission, а не на scheduling** — превысил → объект **не создаётся вовсе** (403 exceeded quota), не Pending. Deployment при этом создаётся нормально, а поды — нет.
  - **ð¥ Квота на compute-ресурс делает** **requests** **обязательным полем для всех подов ns.** Отсутствие requests — это не «ноль», а «неизвестно», admission не может посчитать → отказ must specify requests.cpu. Иначе квота обходилась бы тривиально.
  - **LimitRange** — правила на **каждый** объект: defaultRequest (дефолтные requests) → default (дефолтные limits) → min/max (границы). Типы — Container, Pod, PersistentVolumeClaim.
  - **Порядок фаз** — 1) defaulting в api-server → 2) mutating admission (LimitRanger дописывает) → 3) validating (LimitRanger сверяет min/max) → 4) validating (Quota считает сумму).
  - **ð¥ Defaulting: указан** **limits****, не указан** **requests** **→** **requests = limits****.** Происходит **до** LimitRanger → defaultRequest не применится, поле уже занято. Побочно: requests == limits по обоим ресурсам = QoS **Guaranteed** случайно.
  - **Обратный случай ломается:** указан только requests: 1Gi, LimitRanger ставит default.limits: 512Mi не глядя → валидация падает на инварианте requests \<= limits. **Mutating не думает, validating не прощает.**
  - **Мягкая vs жёсткая мультитенантность** — мягкая (ns+RBAC+квоты+netpol) не держит: общее ядро (container escape) → шумного соседа по disk IOPS / сети / page cache (квота их не считает) → общие CoreDNS/ingress/CNI → etcd. Жёсткая = отдельный кластер либо node pool + taints + sandboxed runtime (gVisor/Kata).

### **⭐ Бест-практис (golden path)**

  - **Quota и LimitRange ставятся только парой — дефолт.** Квота без LimitRange физически ломает ns (поды без resources не создаются); LimitRange без квоты — вежливость без потолка. Отступают в двух случаях: системные ns (kube-system — квота не даст отскейлиться CoreDNS) и однокомандный кластер, где квота = лишняя бюрократия.
  - **limits** **без** **requests** **— антипаттерн.** Пиши оба явно либо ни одного и положись на LimitRange. Иначе получаешь бронь размером с лимит: узел выглядит забитым при потреблении 3%, квота ns схлопывается кратно.
  - **Namespace заводится декларативно из Git, а не** **kubectl create ns** — Kustomize-оверлей / Helm-чарт «tenant», где ns + Quota + LimitRange + RoleBinding + NetworkPolicy лежат одним пакетом и катятся ArgoCD (M21). Руками кто-нибудь обязательно забудет квоту, и узнаешь об этом в инциденте.
  - **Квотировать** **services.loadbalancers** **и** **services.nodeports** — недооценённое: один тенант выедает пул NodePort или плодит облачные LB на тысячи долларов.
  - **Ограничение host'ов для Ingress — только политикой** (Kyverno/Gatekeeper: «в ns team-a разрешены \*.team-a.example.com»). RBAC ограничивает, *куда* Ingress может отправить, но не *что* он может заявить.

### **ð§ Команды-первого-выбора**

kubectl api-resources --namespaced=false        \# что вообще живёт вне namespace

kubectl describe quota -n team-rtb              \# Used vs Hard построчно

kubectl describe limitrange -n team-rtb         \# какие дефолты подставятся

kubectl describe rs -n team-rtb                 \# FailedCreate — ошибка квоты живёт ЗДЕСЬ, не на подах

kubectl get events -n team-rtb --sort-by=.lastTimestamp

kubectl get ns \<name\> -o yaml                   \# при Terminating — status.conditions назовёт зависшую API-группу

kubectl describe node \<node\> | grep -A 12 "Capacity:"          \# Capacity vs Allocatable = резервы узла

kubectl describe node \<node\> | grep -A 8 "Allocated resources" \# брони по узлу (не факт\!)

  

### **⚠️ Грабли и как не наступить**

  - **Deployment есть, подов ноль, на подах нет событий** → квота требует requests, а LimitRange не поставлен → смотреть describe rs (FailedCreate), не describe pod. **Нет объекта — нет и его событий, иди к владельцу.**
  - **Указал только** **limits** → requests скопировался из него → бронь в разы больше нужной, узлы «забиты» при простое, QoS внезапно Guaranteed.
  - **Указал только** **requests** **в ns с LimitRange** → default.limits подставился ниже → отказ на инварианте requests \<= limits.
  - **Квота выставлена задним числом на живой ns** → существующие поды целы, но любой rolling update ломается: maxSurge создаёт под сверх потолка.
  - **Namespace висит в** **Terminating** → финализатор kubernetes не может дочистить ресурс: мёртвый admission-webhook или CRD от снесённого оператора. get ns -o yaml → status.conditions назовёт группу.
  - **capacity == allocatable** **на узле** → нет kube-reserved/system-reserved → поды бронируют всё до последнего байта → kubelet/containerd под OOM killer → узел NotReady → поды переезжают на такие же забитые соседи → **каскад**.
  - **Два Ingress с одним host в разных ns** → младший молча игнорируется, объект в get ingress есть, ADDRESS проставлен, а трафик идёт к чужому приложению.
  - **Квота на** **kube-system** → CoreDNS не отскейлится при росте кластера. Не ставить.
  - **Думали, ns изолирует сеть** → поды свободно ходят между ns (M18).

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Зачем LimitRange, если есть ResourceQuota?»** → разные оси: Quota — сумма на ns (потолок), LimitRange — правила на каждый объект (дефолты + min/max). И главное: квота без LimitRange физически ломает ns, делая requests обязательным полем.
  - **«Deployment создан, подов нет, событий нет — действия?»** → диагностика на уровень владельца: describe rs → FailedCreate. Три причины: квота → admission-webhook отклоняет → RBAC у controller-manager.
  - **«Как изолировать команды в одном кластере?»** → назвать четыре слоя (ns + RBAC + Quota/LimitRange + NetworkPolicy), затем **честно про границу**: это мягкая изоляция от ошибки. Против недоверенного кода — отдельные кластеры или node pool + taints + gVisor/Kata. Тот, кто говорит «namespace изолирует» — не работал с мультитенантностью.
  - **«Под с** **limits.cpu: 2** **и без requests — сколько забронирует?»** → два ядра. Defaulting в api-server копирует limits в requests до всякого LimitRange.

### **ð Связи**

  - Опирается на: M16 (RoleBinding живёт в ns — namespace как область authz), M13 (requests/limits, QoS, allocatable), M3 (фазы обработки запроса, финализаторы), M12 (ingress-controller вотчит все ns).
  - Ведёт к: M18 (NetworkPolicy закрывает сетевую дырку ns; admission как третья ступень), M21 (namespace как единица GitOps), M22 (allocatable и каскад при отказе узла), M19 (диагностика на уровень владельца).
  - Сквозные темы: №7 (три ступени authn/authz/**admission** — квота и LimitRange живут именно в admission), №6 (requests/limits правят всем), №2 (всё — объект API), №1 (декларативное заведение тенанта).

### **ð Что должно остаться в голове через полгода**

  - **Namespace — область имён, RBAC и квот. Не изоляция.** Сеть, ядро и DNS про него не знают.
  - **Quota и LimitRange работают только в паре.** Квота на compute делает requests обязательным полем; LimitRange его проставляет за разработчика.
  - **limits** **без** **requests** **= бронь размером с лимит** (defaulting в api-server, до LimitRanger). Пиши оба или ни одного.
  - **Ошибка квоты живёт в** **describe rs****, а не в подах** — потому что подов не существует. Нет объекта — иди к владельцу.
  - **Мягкая мультитенантность защищает от ошибки, не от злого умысла.** Жёсткая — только отдельный кластер или sandboxed runtime.

  
  

# M18. Периметр пода: политики и supply chain  

## **M18. Периметр пода: политики и supply chain**

**Одной фразой:** три независимых периметра вокруг пода — что ему можно в **ядре узла** (SecurityContext/PSS), с кем ему можно **говорить по сети** (NetworkPolicy) и что вообще **пустят в кластер** (admission + supply chain).

### **ð§  Ментальная модель**

Контейнер — это **обычный процесс на узле**, а не ВМ → ядро одно на всех, и root внутри контейнера это тот же root снаружи. Отсюда весь модуль: три забора вокруг этого процесса. **Первый забор — ядро** (от чьего имени бежит, что может, куда пишет). **Второй забор — сеть** (плоская и открытая по умолчанию, NetworkPolicy — единственный штатный способ её порезать). **Третий забор — вход в кластер** (admission: объект вообще пустят или нет).

Ключ ко всему модулю: **у каждого забора свой актор и свой момент**. Ядро — на старте процесса. CNI-агент — на каждом пакете. Admission — один раз, при записи в etcd.

### **Что важно знать**

  - **Контейнер = процесс + namespaces + cgroups** — ВМ нет, ядро общее → UID 0 внутри = UID 0 на узле (user namespace по умолчанию **выключен**)
  - **root** **— не флаг, а набор capabilities** — ядро разбило всемогущество на \~40 кусков (CAP\_NET\_ADMIN, CAP\_SYS\_ADMIN, CAP\_NET\_BIND\_SERVICE), runtime по умолчанию даёт урезанный набор
  - **securityContext** **живёт на двух уровнях** — pod.spec.securityContext (на все контейнеры) и containers\[\].securityContext (перекрывает подовый)
  - **runAsNonRoot: true** **ничего не меняет** — это **проверка**, а не подстановка. Актор — **kubelet**, момент — старт контейнера, симптом отказа — CreateContainerConfigError
  - **drop: \["ALL"\]** **ломает порты \<1024** — нужен CAP\_NET\_BIND\_SERVICE → дефолт: не возвращать capability, а слушать 8080 и переложить маппинг на Service
  - **readOnlyRootFilesystem: true** **ломает всё, что пишет на диск** → лечится не отключением поля, а emptyDir, смонтированным ровно в нужную точку (/tmp, /var/cache/nginx, /var/run)
  - **Pod Security Standards** — три готовых профиля: Privileged (всё можно) → Baseline (нет privileged/hostNetwork/hostPath, но root можно) → Restricted (= golden path целиком)
  - **Pod Security Admission применяется лейблами на namespace** — pod-security.kubernetes.io/enforce|warn|audit → прямая стыковка с M17. Заменил PodSecurityPolicy, выпиленный в 1.25
  - **Сеть по умолчанию полностью открыта** — namespace изолирует API и RBAC, но **не сеть**; любой под достучится до любого пода в любом ns
  - **NetworkPolicy — whitelist** — слова deny в ней нет вообще. Пока под не выбран ни одной политикой — он открыт; как только выбран — разрешено только явно перечисленное
  - **Ingress и Egress независимы** — политика на входящий никак не трогает исходящий
  - **Селекторы NetworkPolicy — по МЕТКАМ, не по IP** → под пересоздался, IP сменился, правило работает
  - **Применяет NetworkPolicy CNI-агент** (felix у Calico, cilium-agent) — api-server принимает объект **всегда**, независимо от CNI → CNI без поддержки policy даёт **тихий отказ**: объект есть, enforcement нет
  - **Admission — третья ступень темы №7** — mutating меняет объект, validating пропускает или режет, порядок **жёсткий: все mutating → все validating**
  - **defaulting** **в api-server происходит ДО mutating admission** — поэтому limits без requests → requests = limits ещё до LimitRange
  - **Webhook — способ операторов влезать в чужие поды** — sidecar Istio/Linkerd дописывается **mutating webhook'ом**; регистрация через MutatingWebhookConfiguration/ValidatingWebhookConfiguration
  - **failurePolicy: Fail** **+ недоступный webhook = паралич** — api-server отклоняет все подпадающие запросы → в namespace нельзя создать ничего, включая под самого webhook'а

### **⭐ Бест-практис (golden path)**

  - **Базовый** **securityContext** **на каждый прикладной контейнер** — **дефолт индустрии**, каждое поле рубит один шаг типовой цепочки атаки (RCE → эскалация → запись на диск → выход на узел): runAsNonRoot: true + runAsUser: \<UID\> + allowPrivilegeEscalation: false + readOnlyRootFilesystem: true + capabilities.drop: \["ALL"\] + seccompProfile: RuntimeDefault
  - **Отступают точечно** — DaemonSet-агентам (CNI, node-exporter, лог-коллектор) privileged реально нужен, но это **единицы подов на кластер**, не прикладные сервисы
  - **PSA внедрять лестницей** — сначала warn + audit на restricted, неделю смотреть, что бы сломалось → потом enforce: baseline → потом enforce: restricted. enforce: restricted сразу на живой ns — способ уронить прод
  - **default deny ingress** **в каждом прикладном namespace** + точечные разрешения — дефолт зрелого кластера. Egress закрывают реже: ломает больше и требует дисциплины
  - **Закрываешь egress — явно открывай DNS** (UDP/53 + TCP/53 к kube-system) — причина №1 загадочных поломок после внедрения политик
  - **Kyverno, а не OPA/Gatekeeper**, если кластер чисто кубовый — **дефолт**, потому что политика на YAML читается любым инженером, а Rego надо учить. Gatekeeper берут, когда OPA уже используется вне куба или нужна нетривиальная логика
  - **Любую политику включать через** **Audit****, потом** **Enforce** — тот же принцип, что у PSA
  - **Trivy в CI — must have почти везде**; подпись cosign + проверка на admission — зрелая практика, встречается реже. **Подпись без проверки на admission бесполезна**

### **ð§ Команды-первого-выбора**

kubectl get pod \<p\> -o jsonpath='{.spec.containers\[\*\].securityContext}'   \# что реально применилось

kubectl get ns \<ns\> --show-labels                    \# какой профиль PSS навешен на namespace

kubectl label ns \<ns\> pod-security.kubernetes.io/warn=restricted   \# сухой прогон перед enforce

kubectl get netpol -A                                \# какие политики вообще есть

kubectl describe netpol \<name\>                       \# кого выбирает и что разрешает

kubectl get pods -n kube-system                      \# ⭐ КАКОЙ CNI — умеет ли он policy вообще

kubectl get validatingwebhookconfigurations,mutatingwebhookconfigurations   \# кто влезает в запросы

kubectl describe rs \<name\>                           \# ⭐ READY 0/N без подов — ошибка всегда здесь

  

### **⚠️ Грабли и как не наступить**

  - **CreateContainerConfigError** **+** **container has runAsNonRoot and image will run as root** → runAsNonRoot: true без runAsUser, а в образе нет USER → указать runAsUser явно. Ловит **kubelet**, не admission
  - **Приложение падает на записи после включения security** → readOnlyRootFilesystem: true → смонтировать emptyDir в те точки, куда пишет (/tmp, кэши), а не отключать поле
  - **Deployment READY 0/3****, подов нет, в** **describe deploy** **пусто** → отклоняет **admission на уровне пода** (PSA / ResourceQuota / Kyverno) → смотреть describe rs. Тот же паттерн, что квота из M17
  - **NetworkPolicy применена,** **kubectl get netpol** **её показывает, трафик ходит как ходил** → CNI не поддерживает policy → **тихий отказ**, ошибки нигде не будет. Проверять сам CNI, а не наличие объекта
  - **Закрыл egress — приложение не видит БД, но не с** **connection refused****, а с ошибкой резолва** → зарезал UDP/53 к CoreDNS. Первая мысль всегда «CoreDNS лёг» — она неверная
  - **Разрешение из чужого ns оказалось шире, чем задумано** → podSelector и namespaceSelector разнесли на два элемента списка → получилось «ИЛИ» вместо «И». Держать под **одним дефисом**
  - **kubectl apply** **виснет \~10 сек и падает с** **failed calling webhook ... connection refused** → упал под webhook'а с failurePolicy: Fail → чинить сам webhook либо аварийно удалять ...WebhookConfiguration

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Namespace изолирует поды друг от друга?»** → изолирует **API и RBAC**, сеть — **нет**. Плоская сеть кластера, любой под достучится до любого. Режется только NetworkPolicy
  - **«Написал deny-all, а поды всё равно общаются — почему?»** → две причины: **CNI не поддерживает policy** (главная) либо **селектор/namespace не тот**. Проверять в этом порядке
  - **«Чем PSS отличается от PSP?»** → PSP выпилен в 1.25, заменён **Pod Security Admission** — встроен в api-server, три готовых профиля, применяется **лейблами на namespace**, есть режимы warn/audit для мягкого внедрения
  - **«Как Istio дописывает sidecar в мой под?»** → **mutating admission webhook** → отсюда же следует, почему упавший webhook блокирует деплои
  - **«Что произойдёт с запросом на создание пода?»** → authn → authz → **defaulting** → mutating admission (LimitRanger, Kyverno-mutate) → schema → validating admission (PSA, ResourceQuota, Kyverno-validate) → etcd. Дальше scheduler → kubelet, и **runAsNonRoot** **проверяется уже на узле**

### **ð Связи**

  - Опирается на: M2 (контейнер = процесс, namespaces/cgroups), M6 (селекторы по меткам), M9/M10 (плоская сеть, кто кладёт пакеты), M16 (три ступени authn/authz/admission), M17 (Quota = validating, LimitRange = mutating, лейблы на ns).
  - Ведёт к: M19 (диагностика describe rs), M23 (webhook'и операторов), M24 (Cilium — policy на L3–L7, identity-based), M25 (mTLS как ещё один периметр).
  - Сквозные темы: №3 (метки как клей), №5 (сетевая модель), №7 (authn/authz/admission).

### **ð Что должно остаться в голове через полгода**

  - **Контейнер — процесс, ядро общее, root внутри = root снаружи** → отсюда весь смысл runAsNonRoot и drop: ALL
  - **Сеть по умолчанию открыта; namespace её не изолирует; NetworkPolicy — whitelist, и применяет её CNI** → без поддерживающего CNI она молча не работает
  - **Ingress и Egress независимы, и закрытие egress первым делом ломает DNS**
  - **Admission: mutating меняет → validating режет, именно в таком порядке**; webhook'и — это то, как операторы влезают в твои поды, и упавший webhook с failurePolicy: Fail парализует namespace
  - **READY 0/N** **и ни одного пода → всегда** **describe rs** — там лежит настоящая причина отказа

  
  

# M19. Диагностика — системный подход  

## **M19. Диагностика — системный подход**

**Одной фразой:** не набор трюков, а лестница — сначала определяешь, **докуда дошёл процесс запуска**, и только это решает, какой командой смотреть и к какому объекту идти.

### **ð§  Ментальная модель**

Симптом сам по себе не адресует причину. Адресует **стадия, на которой всё встало**: объект не записан → под не назначен → окружение не собрано → процесс умер → процесс жив, но трафика нет. Каждой стадии соответствует свой актор и своё место хранения ошибки. Отсюда главное следствие: **logs** **работают только с четвёртой ступени**, выше контейнера физически не существует — там живёт describe. Вторая ось — **поднимайся к владельцу**: ошибку видит тот, кто получил отказ, а не тот, кого не создали.

### **Что важно знать**

  - **Лестница из пяти ступеней** — объекта пода нет (актор admission, ошибка в describe rs) → Pending (актор scheduler, FailedScheduling) → ContainerCreating / CreateContainerConfigError (актор kubelet, Events) → процесс умер (актор приложение/ядро, logs --previous + Last State) → процесс жив, трафика нет (актор клей/сеть, endpointslices).
  - **READY 0/N** **без подов →** **describe rs** — отказ пришёл на **validating admission**, то есть при попытке *записать* объект пода. Объекта нет → describe'ить нечего. Ошибку получил **ReplicaSet-контроллер** и записал в события своего объекта. Источники: квота без LimitRange · PSA restricted на ns · Kyverno в Enforce · нет SA.
  - **describe** **vs** **logs --previous** **— разные ответы, не разная глубина** — describe даёт Last State: Terminated → Reason + Exit Code, то есть «умер сам или его убили» (Error+код — сам · OOMKilled — ядро · Unhealthy + Killing: failed liveness probe — проба). logs --previous даёт **трейс приложения перед смертью**, чего в describe нет никогда. Порядок — сначала надёжное: при быстром CrashLoop containerd чистит лог, и --previous вернёт unable to retrieve container logs, а Reason останется на месте.
  - **Рестартует контейнер, а не под** — kubelet по restartPolicy. Под пересоздаёт ReplicaSet, это другое событие и другое имя. --previous — предыдущий **инстанс контейнера** внутри живого пода.
  - **CrashLoopBackOff** **— это уже «жду перед рестартом»** — статус сам по себе означает наличие рестартов, «CrashLoop без рестартов» не бывает.
  - **ContainerCreating** **— три ветки с разными адресатами** — FailedMount: configmap "X" not found → свой namespace, висит вечно · Multi-Attach error → RWO-том держит другой узел, иногда доезжает сам · FailedCreatePodSandBox: failed to setup network → CNI-агент мёртв или podCIDR исчерпан, **маркер — встают ВСЕ новые поды этого узла**.
  - **502 vs 404 от ingress — кто нарисовал страницу, тот дожил** — 502 → правило нашлось, рвётся **ниже** контроллера (эндпоинты/порт/приложение) · 404 → правило **не** нашлось, копать в объект Ingress (host, ingressClassName, pathType).
  - **«Эндпоинты разъехались» — наблюдение, а не диагноз** — слайс **пуст** → selector ≠ метки пода **или** под не Ready (запись есть, но conditions.ready: false — «есть, но не лей») · слайс **полон** → неверный targetPort (Nuxt на 3000, в Service 80) · порт верный → логи приложения, 502 честный.
  - **NXDOMAIN ≠ таймаут** — NXDOMAIN значит **CoreDNS ответил**: он жив, виновато имя (короткое имя резолвится в namespace **пода-отправителя**, кросс-ns нужен FQDN). **Таймаут** значит CoreDNS **не ответил**: лёг, режет egress по UDP/53, или resolv.conf смотрит не туда (hostNetwork + дефолтный dnsPolicy → резолв через узел мимо CoreDNS).
  - **Диагностика резолва — разница двух команд** — nslookup \<svc\> vs nslookup \<svc\>.\<ns\>.svc.cluster.local: короткое падает, FQDN живёт → дело в search · оба падают → сервиса нет там, где думаешь · оба живут, curl не идёт → другой класс, режется трафик.
  - **Таймаут vs refused** — **таймаут** = пакет дропнули (NetworkPolicy, firewall), тишина · **connection refused** = пакет доехал и получил RST — порт закрыт, приложение лежит, **или за сервисом нет эндпоинтов** (отказ шлёт ядро узла-отправителя, не приложение).
  - **kubectl debug** **— ephemeral-контейнер в живой под** — под не пересоздаётся, приложение не трогается. Садится в **тот же network namespace** (pause держит netns, M2) → видит ровно ту сеть, что приложение: его resolv.conf, IP, маршруты. --target=\<c\> добавляет **общий PID-namespace** → ps, /proc/\<pid\>/environ. Статический аналог — shareProcessNamespace в спеке пода.
  - **Ephemeral-контейнер нельзя удалить и нельзя перезапустить** — живёт до смерти пода. На проде — одноразовая операция.
  - **Три режима** **debug** — в живой под (--target) · копия пода с подменённым образом (--copy-to + --set-image) для того, что в CrashLoop и не живёт достаточно · **на узел** (debug node/\<name\>) — hostNetwork + hostPID + корень узла в /host, для iptables, маршрутов, логов kubelet.
  - **port-forward** **режет дерево пополам** — туннель к поду **через api-server**, мимо Ingress, LB и входящих политик. 502 + рабочий forward → рвётся выше пода · не работает и forward → приложение. ⚠️ port-forward svc/\<x\> не балансирует — втыкается в один под.
  - **Events живут \~1 час** (--event-ttl) — ночной инцидент утром не восстановить. Это **отдельные объекты в etcd**, а не поле пода → без --sort-by вывод бесполезен. Главный аргумент за централизацию (M20).
  - **Downward API** — под узнаёт о себе через fieldRef (metadata.name, spec.nodeName, status.podIP, метки) и resourceFieldRef (limits.memory). Практика: POD\_NAME + NODE\_NAME в каждую строку лога → в централизованных логах сразу видно «один под на одном узле», а не «сервис глючит». Второе — JVM/Go берут heap от лимита cgroup, а не от памяти узла.
  - **crictl** **— единственный слой ниже kubelet** — идёшь, когда врёт сам kubelet: контейнер есть в crictl, но нет в kubectl; вечный Terminating; узел NotReady.

### **⭐ Бест-практис (golden path)**

  - **describe** **до** **logs** — дефолт без исключений. Не запустился → describe; запустился и умер → logs --previous. Половина потерянного времени на дежурстве — это logs там, где нужен describe.
  - **kubectl debug** **вместо установки пакетов в контейнер** — дефолт. Причина не в чистоте, а в улике: apt install в упавшем поде убивает воспроизводимость.
  - **--target** **всегда при сетевом дебаге** — без него нет общего PID-namespace, и ps покажет пустоту.
  - **kubectl events --for pod/\<name\>** вместо get events — отсекает шум чужих объектов. ⭐ современная замена.
  - **POD\_NAME** **+** **NODE\_NAME** **через Downward API в логи** — дефолт для всего, что деплоится репликами.
  - **Гипотезу проверяй тем, что её отличает, а не тем, что её подтверждает** — refused закрывает версию про NetworkPolicy **не заходя в под**: дроп даёт тишину, а не отказ.

### **ð§ Команды-первого-выбора**

kubectl describe pod \<p\>                       \# ПЕРВОЕ всегда: Last State (Reason+Exit Code) + Events

kubectl logs \<p\> -c \<c\> --previous             \# трейс упавшего инстанса (хрупко — containerd чистит)

kubectl describe rs \<name\>                     \# ⭐ READY 0/N без подов — ошибка ВСЕГДА здесь

kubectl events --for pod/\<name\>                \# события только этого объекта (TTL \~1 час\!)

kubectl get endpointslices -l kubernetes.io/service-name=\<svc\>   \# пусто=selector/readiness, полно=порт

kubectl debug -it \<p\> --image=nicolaka/netshoot --target=\<c\>      \# дебаг distroless: общий netns+PID

kubectl debug node/\<node\> -it --image=nicolaka/netshoot           \# на узел: iptables, маршруты, kubelet

kubectl port-forward svc/\<svc\> 8080:80         \# мимо ingress/LB — режет дерево пополам

kubectl exec \<p\> -- cat /etc/resolv.conf       \# кого под вообще спрашивает

  

### **⚠️ Грабли и как не наступить**

  - **logs** **на поде, который не стартовал** → контейнера не существует, вывод пуст или врёт → describe → Events.
  - **READY 0/N****,** **get pods** **пусто,** **describe deploy** **молчит** → отказ на admission при создании пода → describe rs. Deployment своё сделал — RS создал.
  - **ContainerCreating** **пять минут** → три разных зверя, различаются **только строкой в Events**: FailedMount (свой ns) · Multi-Attach (storage/другой узел) · FailedCreatePodSandBox (CNI, и тогда встают все новые поды узла).
  - **Гоняешь** **traceroute** **при «сервис не доступен»** → если сломан резолв, пакета не было вообще; если 404 от ingress — это L7, пакеты давно доехали. Инструмент не того слоя.
  - **Слайс полный, поды Ready, всё равно 502** → targetPort ≠ containerPort. Самый противный случай: глаз успокаивается на здоровом слайсе.
  - **Дебажишь ночной инцидент утром** → Events протухли (\~1 час). Восстанавливать нечего — только централизованные логи.
  - **exec** **в distroless** → нечего запускать, shell нет → только kubectl debug.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Под в CrashLoopBackOff — твои шаги»** → (1) describe — Last State: Reason + exit code, разводит «упал сам» vs «убили снаружи» (OOMKilled / liveness); (2) logs --previous — трейс перед смертью; (3) живой logs. Порядок = сначала надёжное, потом хрупкое.
  - **«502 от ingress — куда смотришь»** → 502 значит правило нашлось → рвётся ниже → get endpointslices первым. Пусто — selector/readiness, полно — targetPort, дальше логи приложения.
  - **«Дебажишь под на distroless — как?»** → kubectl debug --image=netshoot --target=\<c\>: ephemeral-контейнер в живом поде, общий netns и PID. exec невозможен.
  - **«Ingress виноват или приложение?»** → port-forward прямо на под, мимо всего. Работает — рвётся выше; не работает — приложение.
  - **«Не резолвится имя сервиса»** → сначала развести NXDOMAIN (CoreDNS жив, виновато имя/namespace) и **таймаут** (не дошли до CoreDNS: упал, egress, resolv.conf).
  - **«Приложение пишет** **connection refused** **— это NetworkPolicy?»** → нет. Дроп даёт **таймаут**, а не отказ. Refused — порт закрыт, приложение лежит или за сервисом пустой слайс.

### **ð Связи**

  - **Опирается на:** M2 (pause держит netns — на этом стоит --target; crictl), M4 (--previous, Last State, пробы, restartPolicy), M6 (selector → пустой слайс), M7 (FailedMount, CreateContainerConfigError), M9 (CNI и FailedCreatePodSandBox), M10 (эндпоинты, targetPort), M11 (search, FQDN, NXDOMAIN), M12 (502 vs 404), M17/M18 (квота и PSA → describe rs).
  - **Ведёт к:** M20 (Events эфемерны → централизация; метрики вместо догадок), M21 (drift и rollout при зависшем выкате), M22 (crictl, kubelet-логи, узел NotReady), M23 (та же лестница для оператора: CR → status → логи контроллера).
  - **Сквозные темы:** №2 (всё — объект API: Events и сами объекты, и отказ падает на того, кто его получил), №4 (лестница = поиск актора, чей reconcile встал), №5 (сетевой слой: DNS → Service → политика), №6 (ресурсные отказы как отдельная ветка).

### **ð Что должно остаться в голове через полгода**

  - **Сначала стадия, потом команда.** logs работают только с того момента, как процесс запустился; всё выше — describe.
  - **Нет объекта → иди к владельцу.** READY 0/N без подов = describe rs, всегда.
  - **describe** **говорит, кто убил;** **logs --previous** **говорит, на чём.** Два разных ответа, порядок неизменен.
  - **Таймаут = пакет дропнули. Refused = пакет доехал.** NXDOMAIN = CoreDNS ответил, таймаут DNS = до него не дошли.
  - **kubectl debug --target** **— сеть глазами приложения**, без shell в образе и без порчи улики. port-forward — способ за одну команду отрезать полдерева.

  
  

# M20. Наблюдаемость в кластере  

## **M20. Наблюдаемость в кластере**

**Одной фразой:** метрики отвечают «что-то не так и где», логи — «что именно случилось», трейсы — «на каком участке потерялось время»; в кубе к ним добавляется отдельный вопрос — **кто вообще поставляет цифры и кому**.

⚠️ Модуль **не пройден на занятии** — это справочная выжимка по карте курса, а не конспект занятия. Личных «мин» здесь нет.

### **ð§  Ментальная модель**

Куб сам по себе **не хранит историю**. Events живут \~час, kubectl top показывает мгновенный срез, логи умирают вместе с подом. Всё, что ты видишь через kubectl, — это **настоящее время**. Наблюдаемость — это внешние системы, которые приделывают к кластеру память. И их **две независимые ветки, которые постоянно путают**: metrics-server (свежий срез для top и HPA, в памяти, без истории) и Prometheus (временные ряды, история, алерты). Первый нужен, чтобы кластер **работал**; второй — чтобы ты **понимал**, что происходило.

### **Что важно знать**

  - **Цепочка метрик ресурсов** — cgroup в ядре → **cAdvisor** (встроен в kubelet) → **metrics-server** (агрегирует по всем узлам, держит **в памяти**, на диск не пишет) → **Metrics API** в api-server → потребители: kubectl top и **HPA**. Один кран на двоих: не работает top — не работает и HPA.
  - **metrics-server** **≠ Prometheus** — metrics-server даёт **один срез сейчас** (CPU/память подов и узлов) и нужен кубу **функционально**. Prometheus даёт **историю и алерты** и кубу не нужен — нужен тебе. Путаница между ними — источник вопроса «поставил Prometheus, почему HPA не скейлит».
  - **В kind metrics-server не стартует без** **--kubelet-insecure-tls** — kubelet предъявляет самоподписанный серт, metrics-server ему не верит. Симптом: под в Running, но Readiness probe failed, top пишет metrics not available.
  - **kube-state-metrics** **— третья, отдельная вещь** — он не про потребление, а про **состояние объектов**: сколько реплик желаемых и готовых, сколько рестартов, в какой фазе под, не истёк ли Job. Источник — api-server, а не kubelet. Отсюда: container\_memory\_usage\_bytes — это cAdvisor, kube\_pod\_container\_status\_restarts\_total — это KSM.
  - **Три источника, три ответа** — kubelet/cAdvisor: «сколько жрёт» · kube-state-metrics: «в каком состоянии объект» · сам компонент (api-server, etcd, ingress-nginx): «как я себя чувствую», через свой /metrics.
  - **Prometheus работает по PULL** — сам ходит и скребёт /metrics целей. Цели не регистрируются — Prometheus **находит их через service discovery по api-server** (тема №2). Отсюда вопрос на собесе «как он узнаёт о новых подах»: watch на объекты, а не конфиг руками.
  - **ServiceMonitor** **/** **PodMonitor** **— это CRD Prometheus Operator** — вместо правки prometheus.yml ты создаёшь **объект**, оператор реконсайлит его в конфиг и релоадит Prometheus. Тема №4 живьём: это первый оператор, с которым сталкиваются почти все. Селектор — **по меткам** (объектов много, они пересоздаются).
  - **kube-prometheus-stack** — Helm-чарт, который ставит Prometheus + Grafana + Alertmanager + kube-state-metrics + node-exporter + готовые дашборды и алерты. ⭐ Индустриальный дефолт для self-managed.
  - **Golden signals** — **latency** (сколько ждём), **traffic** (сколько запросов), **errors** (доля неуспешных), **saturation** (насколько близко к пределу). RED (Rate/Errors/Duration) — для сервисов, USE (Utilization/Saturation/Errors) — для ресурсов. Это тот же аппарат, что в курсе по сетям.
  - **CPU throttling не виден в** **kubectl** **вообще** — под Running, 1/1, healthy, приложение тормозит. Единственный способ увидеть — метрика **container\_cpu\_cfs\_throttled\_seconds\_total** (доля периодов, в которых cgroup упёрлась в квоту). Это прямой ответ на «тормозит без ошибок» из M13.
  - **Что мониторить в самом кластере** — доступность и latency api-server · etcd (задержки fsync, размер БД, кворум) · NotReady-узлы и node pressure · перезапуски подов (KSM) · истекающие сертификаты · заполнение диска на узлах. Симптом отказа control plane выглядит как «сломалось всё сразу».
  - **kubectl logs** **в проде не хватает по трём причинам** — логи умирают вместе с подом · нет поиска по нескольким подам и времени · нет истории. Отсюда централизация: **Loki** (индексирует только метки, дешёвый) или **EFK/ELK** (полнотекстовый поиск, тяжёлый). ⭐ Для кубовых кластеров чаще берут Loki — он говорит теми же метками, что Prometheus.
  - **stern** — kubectl logs по нескольким подам сразу, по селектору, с подсветкой. Не замена централизации, но закрывает 80% дежурства.
  - **Cardinality — главный способ убить Prometheus.** Каждая уникальная комбинация меток = отдельный временной ряд в памяти. Метка с user\_id, request\_id или полным URL — миллионы рядов и OOM. Правило: метка должна иметь **ограниченный и предсказуемый** набор значений.
  - **Трейсы (OpenTelemetry, Jaeger, Tempo)** — нужны там, где запрос проходит через много сервисов и непонятно, **какой хоп** съел время. Для монолита и трёх сервисов — избыточны. В кубе обычно приезжают вместе с service mesh (M25), который умеет генерировать спаны без правки кода.

### **⭐ Бест-практис (golden path)**

  - **metrics-server** **— обязателен в любом кластере**, даже учебном. Без него нет top, нет HPA, нет VPA. Дефолт без вариантов.
  - **kube-prometheus-stack** **через Helm, а не сборка руками** — дефолт: чарт тянет операторы, дашборды и набор алертов, выверенных сообществом. Собирать по частям — только если нужно урезать.
  - **Алерты на симптом, а не на причину** — ⭐ алертить на «доля 5xx выросла» и «latency 99-й перцентиль вырос», а не на «CPU 80%». Высокий CPU сам по себе не проблема; проблема — когда от него страдают пользователи. Причина ищется потом, по дашборду.
  - **Метки метрик — только с ограниченным набором значений.** status\_code, method, service — да. user\_id, path с идентификаторами — никогда.
  - **Логи структурированные (JSON) +** **POD\_NAME****/****NODE\_NAME** **через Downward API** (M19) — дефолт: иначе в централизованном хранилище невозможно отделить «один под сломался» от «сервис сломался».
  - **Централизация логов появляется раньше, чем кажется** — как только подов больше десятка или инциденты случаются ночью (Events живут час, M19).

### **ð§ Команды-первого-выбора**

kubectl top nodes                              \# жив ли источник метрик вообще (пробник metrics-server)

kubectl top pods -A --sort-by=memory           \# кто жрёт (ФАКТ, не брони — не путать с describe node)

kubectl describe node \<n\> | grep -A8 'Allocated'  \# БРОНИ, а не факт — другой вопрос, другой ответ

kubectl -n \<ns\> logs -l app=web --tail=50 -f   \# логи всех подов сервиса штатным kubectl

stern -n \<ns\> -l app=web                       \# то же удобнее: подсветка, имена подов, несколько подов

kubectl port-forward -n monitoring svc/kps-grafana 3000:80   \# СВОЯ Grafana локально

kubectl get servicemonitors -A                 \# что Prometheus Operator вообще скребёт

kubectl -n monitoring logs -l app.kubernetes.io/name=prometheus   \# почему цель не скрейпится

  

Установка (проверить актуальность под версию кластера — принцип 11):

kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml

kubectl -n kube-system patch deploy metrics-server --type=json \\

  -p='\[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}\]'   \# ⚠️ для kind

helm repo add prometheus-community https://prometheus-community.github.io/helm-charts && helm repo update

helm install kps prometheus-community/kube-prometheus-stack -n monitoring --create-namespace

  

### **⚠️ Грабли и как не наступить**

  - **kubectl top** **→** **metrics not available** → нет metrics-server. Тот же корень, что «HPA не скейлит, TARGETS \<unknown\>». Одна проверка закрывает оба симптома.
  - **metrics-server в kind не поднимается** → самоподписанный серт kubelet → --kubelet-insecure-tls. В проде так делать нельзя, там ставят нормальные серты.
  - **Поставил Prometheus, HPA всё равно** **\<unknown\>** → Prometheus и metrics-server — разные краны. HPA по CPU пьёт из Metrics API, а не из Prometheus (для Prometheus нужен prometheus-adapter и custom metrics).
  - **Prometheus съел всю память и упал** → высокая cardinality. Искать метрику с меткой, у которой значений тысячи.
  - **«Приложение тормозит, метрики зелёные»** → CPU throttling. container\_cpu\_cfs\_throttled\_seconds\_total, в kubectl этого нет никогда.
  - **Логи ночного инцидента потеряны** → под пересоздан, Events протухли. Восстанавливать нечего — это аргумент за централизацию, а не повод копать глубже.
  - **Дашборды есть, алертов нет** → мониторинг, на который никто не смотрит, инцидент не ловит. Дашборд для разбора, алерт для обнаружения.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Чем metrics-server отличается от Prometheus?»** → metrics-server: мгновенный срез в памяти, нужен кубу **функционально** (top, HPA). Prometheus: временные ряды, история, алерты — нужен людям. Разные краны, друг друга не заменяют.
  - **«Как Prometheus узнаёт о новых подах?»** → pull + service discovery через api-server (watch). Ничего не регистрируется вручную; в operator-схеме цели описываются объектами ServiceMonitor по меткам.
  - **«Что мониторить в кластере?»** → api-server (latency, ошибки), etcd (fsync, кворум, размер), узлы (NotReady, pressure, диск), рестарты подов, сертификаты. Симптом отказа control plane — «упало всё сразу».
  - **«Golden signals?»** → latency / traffic / errors / saturation. Алертить на симптомы пользователя, а не на утилизацию.
  - **«Приложение тормозит без ошибок — где смотреть?»** → CPU throttling; в kubectl невидим по определению, нужна метрика cAdvisor.
  - **«Почему высокая cardinality опасна?»** → каждая комбинация меток — отдельный ряд в памяти Prometheus; user\_id в метке кладёт сервер.

### **ð Связи**

  - **Опирается на:** M13 (cgroups, requests/limits, throttling — то, что здесь измеряется), M15 (цепочка метрик и \<unknown\> у HPA), M19 (Events живут час → отсюда растёт централизация), M5 (DaemonSet — node-exporter и лог-агенты живут именно так), сети (RED/USE, перцентили).
  - **Ведёт к:** M21 (мониторинг как код, дашборды в Git), M22 (мониторинг control plane и etcd), M23 (Prometheus Operator — живой оператор с CRD), M24 (Hubble — наблюдаемость сети), M25 (mesh даёт golden signals и трейсы без правки кода).
  - **Сквозные темы:** №2 (метрики берутся через api-server и его watch), №4 (Prometheus Operator — контроллер над CRD), №6 (всё измеряемое упирается в requests/limits), №3 (ServiceMonitor выбирает цели **по меткам**).

### **ð Что должно остаться в голове через полгода**

  - **metrics-server и Prometheus — разные краны.** Первый нужен кубу (top, HPA), второй нужен тебе (история, алерты). Симптом \<unknown\> у HPA лечится первым, а не вторым.
  - **Три источника метрик:** cAdvisor/kubelet — сколько жрёт · kube-state-metrics — в каком состоянии объект · сам компонент — как себя чувствует.
  - **Prometheus скребёт сам (pull) и находит цели через api-server.** Ничего не регистрируется руками.
  - **CPU throttling не виден в** **kubectl** **никогда** — только метрика. Это ответ на «тормозит без ошибок».
  - **Алерт на симптом пользователя, метка с ограниченным набором значений** — два правила, которые спасают и от слепоты, и от падения Prometheus.

  
  

# M21. Пакетирование и GitOps  

## **M21. Пакетирование и GitOps**

**Одной фразой:** Helm и Kustomize решают «как не дублировать манифесты по окружениям», а GitOps решает другое — **кто и когда их применяет**, превращая Git в тот же spec, к которому кластер приводит себя сам.

⚠️ Модуль **не пройден на занятии** — справочная выжимка по карте курса.

### **ð§  Ментальная модель**

Reconciliation loop из M3, поднятый на уровень **всего репозитория**. Обычный контроллер держит status пода равным spec в etcd. GitOps-контроллер держит **состояние всего кластера** равным содержимому Git. Отсюда всё поведение: ручной kubectl edit откатывается (это дрейф, его чинят), пайплайну не нужен доступ в кластер (кластер сам тянет), а «что сейчас в проде» — это git log, а не память дежурного.

Helm и Kustomize к этому отношения не имеют вовсе — это **упаковка**, слой ниже. Их путают с GitOps, потому что они обычно едут вместе.

### **Что важно знать**

  - **Helm — шаблонизатор + менеджер релизов.** Чарт = шаблоны Go + values.yaml. helm install рендерит шаблоны и применяет результат, **запоминая релиз** (в Secret'е в том же namespace) — отсюда helm rollback и helm history.
  - **Главная сила Helm — чужой софт.** ingress-nginx, cert-manager, kube-prometheus-stack, ArgoCD ставятся одной командой с сотней настроек через values. Писать своё приложение на Helm-шаблонах — уже вопрос вкуса.
  - **Главная слабость Helm — шаблоны текстовые, а не структурные.** Go-шаблон не знает, что такое YAML: {{ if }} вокруг блока с неверным отступом рождает синтаксически битый манифест. Отсюда правило helm template --debug перед выкатом.
  - **Ежедневный Helm оператора — три команды:** helm get values \<rel\> (с чем реально стоит релиз, а не что в репе) · helm template / helm get manifest (что реально отрендерилось) · helm history + helm rollback.
  - **Релиз застрял в** **pending-upgrade****/****pending-install** — процесс helm убили посреди операции, лок остался. Выход: helm rollback \<rel\> \<последняя good ревизия\>, в тяжёлых случаях — удалить Secret релиза с этой ревизией. Частая ситуация при таймауте CI.
  - **Helm hooks** (pre-install, pre-upgrade, post-delete) — Job'ы, выполняемые вокруг релиза: миграции БД, ожидание готовности. Ловушка: hook живёт **вне** обычного жизненного цикла релиза, при откате не откатывается.
  - **Kustomize — не шаблоны, а патчи.** base/ с обычными валидными манифестами + overlays/\<env\>/ с патчами. Нет плейсхолдеров — база сама по себе применима. Встроен в kubectl: kubectl apply -k.
  - **⭐ Индустриальный расклад:** **Kustomize для своих манифестов, Helm для стороннего софта.** Причина: свои манифесты читаемы и диффятся как обычный YAML, а чужой софт всё равно приезжает чартом. Консенсус не абсолютный — многие живут целиком на Helm, и это тоже рабочий выбор.
  - **kustomize** **умеет** **configMapGenerator** **с хэшем в имени** — при изменении данных ConfigMap имя меняется → меняется pod template → **штатный rolling update**. Тот же эффект, что checksum-аннотация в Helm (M7), только из коробки.
  - **GitOps — четыре принципа:** декларативное описание · версионируется в Git (единственный источник истины) · применяется автоматически · **непрерывно сверяется** и чинится (self-heal).
  - **Push vs Pull — ключевая развилка модуля.** Push (GitHub Actions делает kubectl apply): кластер меняется только в момент прогона пайплайна; между прогонами дрейф никто не видит; CI нужны **креды с правами в кластер** (наружу торчит доступ). Pull (ArgoCD/Flux): контроллер **внутри** кластера следит за репой и правит расхождения непрерывно; наружу ничего не отдаётся; дрейф виден как OutOfSync и лечится сам.
  - **Drift detection + self-heal — то, чего push не даёт в принципе.** Кто-то сделал kubectl edit на проде → ArgoCD показывает OutOfSync и (при selfHeal: true) возвращает как в Git. Это и главная фича, и главный источник конфликтов.
  - **ArgoCD vs Flux** — Argo: сильный UI, Application как объект, удобен командам и наглядно на демо. Flux: без UI, набор контроллеров, ближе к «чистому» GitOps и легче встраивается в автоматизацию. ⭐ Для человека, который хочет **видеть** состояние — Argo; консенсуса «лучше» нет.
  - **App-of-apps** — одно приложение Argo, которое разворачивает остальные Application. Так описывают целый кластер одним корневым объектом.
  - **Sync waves** — порядок применения внутри синка (argocd.argoproj.io/sync-wave): сначала CRD и namespace, потом то, что на них опирается. Лечит no matches for kind на первом деплое.
  - **Секреты в Git — отдельная проблема, у неё три ответа:** **SOPS** (файл шифруется, ключ в KMS/age) · **sealed-secrets** (шифруется публичным ключом контроллера, расшифровать может только он, в Git лежит SealedSecret) · **External Secrets Operator** (в Git только *ссылка*, значение приезжает из Vault/AWS SM в рантайме). ⭐ Для зрелых установок — ESO; для одного кластера без Vault — sealed-secrets.
  - **Прогрессивная доставка (Argo Rollouts, Flagger)** — заменяет Deployment на Rollout с canary/blue-green по метрикам: льём 5% трафика, смотрим error rate из Prometheus (M20), решаем катить дальше или откатывать. Мостик к M25 — веса трафика умеет либо ingress, либо mesh.

### **⭐ Бест-практис (golden path)**

  - **Kustomize для своих, Helm для чужого** — частый индустриальный выбор. Не догма, но хорошая отправная точка.
  - **Pull-модель (ArgoCD/Flux) вместо** **kubectl apply** **из CI** — дефолт для зрелой доставки: нет секретов кластера в CI, есть drift-detection и self-heal, состояние прода = состояние ветки.
  - **CI собирает образ, CD его выкатывает — разные роли.** Пайплайн после сборки коммитит новый тег в репозиторий манифестов, дальше работает Argo. Так граница ответственности проходит по Git, а не по правам доступа.
  - **Никогда** **:latest** **в манифестах** — иммутабельный тег или digest, иначе непонятно, что именно катится, и rollback ничего не значит.
  - **helm template --debug** **перед выкатом чужого чарта** — единственный способ увидеть, что реально поедет в кластер.
  - **Auto-sync включать вместе с командой, а не втихую** — иначе kubectl edit дежурного молча откатывается, и человек считает, что кластер сошёл с ума.
  - **Секреты — не в Git открытым текстом никогда.** Минимум — sealed-secrets; зрелый вариант — ESO с внешним хранилищем.

### **⚠️ Грабли и как не наступить**

  - **Helm-шаблоны превратились в нечитаемую лапшу** → признак, что своё приложение стоило описать Kustomize. Отладка: helm template --debug.
  - **Релиз в** **pending-upgrade****, ничего не делается** → лок от убитого процесса → helm rollback на последнюю рабочую ревизию.
  - **Kustomize-патч «не применился», ошибки нет** → патч не нашёл цель (не совпало name/kind/namespace). Проверять kubectl kustomize, а не глазами.
  - **ArgoCD дерётся с ручным** **kubectl edit** → selfHeal возвращает как в Git. Это не баг; чинить надо в Git, а на время разбора — Sync Policy в manual.
  - **no matches for kind** **на первом деплое** → CRD ставится тем же синком, что и CR → sync waves или отдельное приложение под CRD.
  - **Секрет уехал в Git в открытом виде** → он там навсегда, в истории. Ротировать значение, а не только удалять файл.
  - **Приложение** **Synced****, но** **Degraded** → Git применён верно, а поды не поднимаются. Argo тут ни при чём — идёшь по лестнице M19.
  - **Образ по тегу** **latest** **+ auto-sync** → Git не изменился, значит Argo не видит причин синкать, а под при рестарте вдруг приезжает другой. Иммутабельные теги.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Чем GitOps лучше** **kubectl apply** **из CI?»** → три вещи: непрерывный reconcile вместо разового применения (дрейф чинится сам) · кластерные креды не уезжают в CI (pull вместо push) · состояние прода читается из Git, а не из кластера. Тема №1, поднятая на уровень репозитория.
  - **«Helm или Kustomize?»** → Helm — упаковка и распространение чужого софта, есть релизы и rollback. Kustomize — патчи поверх валидной базы, без шаблонов, встроен в kubectl. Частый выбор: своё — Kustomize, чужое — Helm.
  - **«Как хранить секреты при GitOps?»** → SOPS / sealed-secrets / External Secrets. В Git — только шифротекст или ссылка, никогда значение.
  - **«Приложение в Argo** **OutOfSync** **— что это значит?»** → кластер разошёлся с Git: кто-то правил руками, либо контроллер (или mutating webhook) дописал поля. Второе — частая причина «вечного OutOfSync».
  - **«Как выкатить canary?»** → веса трафика даёт ingress-аннотациями или mesh; решение катить/откатывать принимается по метрикам (Argo Rollouts + Prometheus).

### **ð Связи**

  - **Опирается на:** M3 (декларативность, apply, reconcile — GitOps это он же в масштабе), M5 (rolling update как механизм выката), M7 (checksum-аннотация ↔ configMapGenerator; секреты), M17 (namespace как единица разграничения), M20 (метрики как критерий прогрессивной доставки).
  - **Ведёт к:** M22 (кластер как код, восстановление из Git после аварии), M23 (ArgoCD и cert-manager — операторы с CRD; webhook'и как причина вечного дрейфа), M25 (canary и traffic shifting на уровне mesh).
  - **Сквозные темы:** №1 (reconcile — ядро модуля), №2 (всё — объект API, поэтому Git может описать что угодно), №4 (Argo/Flux — обычные контроллеры), №7 (pull-модель убирает кластерные права из CI).

### **ð Что должно остаться в голове через полгода**

  - **Helm/Kustomize — про упаковку, GitOps — про то, кто применяет.** Разные слои, их постоянно путают.
  - **Push применяет разово, pull держит непрерывно.** Отсюда drift-detection, self-heal и отсутствие кластерных кредов в CI.
  - **Git — это** **spec** **для всего кластера.** Ручная правка на проде = дрейф, который контроллер обязан откатить.
  - **Своё — Kustomize, чужое — Helm** как рабочая отправная точка; helm get values и helm template --debug — две команды, которые спасают на дежурстве.
  - **Секрет в Git — только шифротекст или ссылка.** SOPS / sealed-secrets / ESO.

  
  

# M22. Как кластер поднимается по-настоящему  

## **M22. Как кластер поднимается по-настоящему**

**Одной фразой:** kubeadm init — это не магия, а генерация PKI, запуск etcd и трёх статик-подов; всё остальное в кластере вырастает уже поверх, и потому потеря etcd или протухший сертификат убивают его целиком.

⚠️ Модуль **не пройден на занятии** — справочная выжимка по карте курса. Это тот модуль, который без рук почти бесполезен: его смысл в том, чтобы один раз собрать кластер самому.

### **ð§  Ментальная модель**

Курица и яйцо. Чтобы запускать поды, нужен api-server. Но api-server сам — под. Разрыв разрывается **static pods**: kubelet стартует раньше всех, читает YAML **с диска узла** (/etc/kubernetes/manifests/) и поднимает api-server, scheduler, controller-manager и etcd, ни у кого не спрашивая. Только после этого api-server оживает, и kubelet начинает получать задания уже нормальным путём. Отсюда практическое следствие: эти поды **нельзя удалить через API** — в etcd лежат лишь их зеркала (mirror pods), а правда лежит файлом на узле.

### **Что важно знать**

  - **Что делает** **kubeadm init** — проверяет узел (preflight) → генерирует **PKI** в /etc/kubernetes/pki (свой CA + серты для api-server, kubelet, etcd, service account keys) → пишет kubeconfig'и для компонентов → раскладывает манифесты статик-подов в /etc/kubernetes/manifests/ → ждёт, пока control plane оживёт → создаёт **bootstrap-токен** для присоединения узлов → ставит CoreDNS и kube-proxy. **CNI не ставит** — его ты кладёшь сам, и до этого узлы NotReady.
  - **Почему узел** **NotReady** **сразу после init** — kubelet сообщает NetworkPluginNotReady: /etc/cni/net.d пуст, IP выдавать некому (M9). Ставишь CNI → узел становится Ready. Это не поломка, а нормальный порядок.
  - **kubeadm join** — узел приходит с **bootstrap-токеном**, api-server выдаёт ему право запросить клиентский сертификат, CSR подписывается автоматически (TLS bootstrap), после чего у kubelet появляется свой серт и он становится полноправным. Токен живёт по умолчанию **24 часа** — отсюда «а как теперь добавить узел через неделю»: kubeadm token create --print-join-command.
  - **PKI — это несколько независимых CA**, а не один: кластерный CA (клиенты и api-server), etcd CA (взаимная аутентификация etcd), front-proxy CA (агрегация API). Плюс пара ключей для подписи SA-токенов. Понимание этого объясняет M16: твоё имя = CN в клиентском серте, подписанном кластерным CA.
  - **etcd — единственный источник истины и единственная точка невозврата.** Всё остальное восстанавливается: узлы переустанавливаются, поды пересоздаются, манифесты лежат в Git. etcd без бэкапа не восстанавливается ничем.
  - **Бэкап etcd — снапшот**, снимается etcdctl snapshot save с сертификатами etcd; восстановление — etcdctl snapshot restore в новую директорию данных + перезапуск статик-пода etcd на неё. ⭐ Снимать по расписанию и **проверять восстановление**: непроверенный бэкап — это не бэкап.
  - **Кворум etcd —** **N/2+1****.** 3 узла переживают потерю одного, 5 — двух. Чётное число узлов бессмысленно: 4 узла переживают столько же отказов, сколько 3, но вероятность отказа выше. Потерян кворум → кластер в read-only, api-server не принимает записи.
  - **HA control plane** — несколько мастеров за одним VIP/LB + etcd-кластер (стековый на тех же узлах или внешний). Реплики api-server **все активны** (он stateless); controller-manager и scheduler работают через **leader election** (Lease в kube-system), активен один; у etcd свой лидер по Raft. Три разных механизма, не путать.
  - **Managed vs self-managed — граница ответственности.** В GKE/EKS облако держит control plane, etcd и его бэкапы, апгрейд мастера, доступность api-server; на тебе — узлы, воркоады, сеть внутри, RBAC, стоимость. В kubeadm — **всё твоё**, включая ротацию сертификатов и снапшоты. Плата за managed — цена и потеря доступа к внутренностям (в GKE ты не увидишь /etc/kubernetes).
  - **Порядок апгрейда жёсткий: control plane → узлы.** Внутри control plane: сначала первый мастер (kubeadm upgrade plan / apply), потом остальные, потом kubelet на каждом узле.
  - **Version skew** — kubelet может отставать от api-server, но не опережать (поддерживается отставание на несколько минорных версий, точное окно зависит от релиза — сверять в документации своей версии). Прыгать через минорные версии нельзя: только 1.29 → 1.30 → 1.31.
  - **cordon** **/** **drain** **/** **uncordon** — cordon помечает узел SchedulingDisabled (новые поды не сядут, старые работают) · drain дополнительно **выселяет** поды, соблюдая **PodDisruptionBudget** · uncordon возвращает в строй. drain без --ignore-daemonsets зависает: DaemonSet-поды пересоздаются на том же узле по определению.
  - **PDB — то, что делает drain безопасным и то, что его блокирует.** minAvailable: 1 при одной реплике → выселить нельзя никогда → drain висит вечно, а Cluster Autoscaler не удаляет узел (M15). Один и тот же объект в двух ролях.
  - **Ротация сертификатов** — клиентские серты kubeadm выпускает на **год**. Кластер, который никто не трогал 12 месяцев, однажды перестаёт отвечать: x509: certificate has expired. kubeadm certs check-expiration / kubeadm certs renew all, дальше перезапуск статик-подов. Сертификат CA живёт 10 лет — вот его истечение уже беда.
  - **Disaster recovery, порядок мыслей:** api-server отвечает? → нет: жив ли etcd и есть ли кворум → нет: восстановить из снапшота → диск control plane не заполнен ли (etcd падает от нехватки места и от истёкшего compaction) → серты не протухли ли.

### **⭐ Бест-практис (golden path)**

  - **Снапшоты etcd по расписанию + регулярная проверка восстановления** — дефолт, без вариантов. Хранить вне узлов control plane.
  - **Нечётное число etcd-узлов: 3 для прода, 5 для крупного.** Один — только для лабы.
  - **drain** **перед любыми работами с узлом**, --ignore-daemonsets обязателен, --delete-emptydir-data — осознанно (данные emptyDir теряются).
  - **PDB на всё, что должно пережить апгрейд** — но с числом реплик больше одной, иначе он превращается из защиты в блокировку.
  - **Апгрейд по одному узлу с проверкой между шагами**, никогда не прыгать через минорную версию.
  - **Managed control plane, если нет причин обратного** — дефолт индустрии для продакшена: бэкапы etcd и апгрейды мастера мало кто делает лучше облака. Self-managed берут ради on-prem, суверенности данных, цены на масштабе или специфичных требований.
  - **Кластер как код** — kubeadm-конфиг, Terraform для машин, Ansible для bootstrap, манифесты в Git (M21). Кластер, который нельзя пересоздать с нуля за час, — это питомец, а не скот.

### **⚠️ Грабли и как не наступить**

  - **Узлы** **NotReady** **после** **init** → CNI не поставлен, /etc/cni/net.d пуст. Норма до установки плагина.
  - **drain** **висит** → нет --ignore-daemonsets, либо PDB не даёт выселить последнюю реплику. Смотреть kubectl get pdb -A.
  - **kubeadm join** **не проходит через сутки** → bootstrap-токен протух. Создать новый.
  - **x509: certificate has expired****, кластер «умер» через год** → истекли клиентские серты kubeadm. kubeadm certs renew all + перезапуск статик-подов + обновить свой \~/.kube/config.
  - **kubectl delete pod kube-apiserver-...** **не работает** → это static pod, kubelet поднимает его заново из файла. Меняется только правкой манифеста на узле.
  - **etcd не стартует / кластер read-only** → нет кворума, или диск control plane заполнен, или БД разрослась без compaction. Смотреть etcdctl endpoint status и место на диске.
  - **Апгрейд сломался** → прыгнули через минорную версию или подняли kubelet выше api-server. Порядок: control plane → узлы, по одной минорной.
  - **Восстановились из снапшота, а кластер «помнит» старое** → снапшот — это срез времени: объекты, созданные после него, исчезли. Отсюда GitOps как второй слой восстановления (M21).

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Что делает** **kubeadm init****?»** → PKI → kubeconfig'и компонентов → статик-поды control plane + etcd → bootstrap-токен → CoreDNS и kube-proxy. **CNI не ставит.**
  - **«Зачем бэкапить etcd и что теряешь без него?»** → etcd = всё состояние кластера. Без снапшота потеря control plane = потеря кластера; манифесты в Git спасают воркоады, но не то, что создавалось руками и операторами.
  - **«Managed vs self-managed?»** → в managed на облаке control plane, etcd, бэкапы и апгрейд мастера; в self-managed это твоя работа целиком, включая ротацию сертов.
  - **«Как проходит апгрейд?»** → control plane → узлы; на каждом drain (с --ignore-daemonsets) → апгрейд kubelet → uncordon; PDB определяет, можно ли выселять; version skew ограничивает шаг.
  - **«Три мастера — не подерутся ли контроллеры?»** → нет: leader election через Lease, активен один. api-server реплики активны все, у etcd свой лидер по Raft.
  - **«Почему нельзя удалить под api-server?»** → static pod; в etcd лежит зеркало, правда — файл в /etc/kubernetes/manifests на узле.

### **ð Связи**

  - **Опирается на:** M1 (компоненты control plane, static pods, leader election — здесь всё это руками), M1.1 и M16 (PKI: CN=имя, O=группы; kubeconfig), M9 (CNI ставится отдельно, иначе NotReady), M14 (PDB и выселение), M5 (DaemonSet при drain).
  - **Ведёт к:** M21 (кластер как код, восстановление воркоадов из Git), M23 (операторы поверх собранного кластера), M24 (CNI выбирается на этом же этапе), финальный чекпоинт.
  - **Сквозные темы:** №2 (etcd — истина, api-server — дверь; ровно тут это перестаёт быть абстракцией), №1 (kubelet держит статик-поды по файлу — reconcile без всякого API), №7 (PKI как основание authentication).

### **ð Что должно остаться в голове через полгода**

  - **Static pods разрывают курицу-яйцо:** kubelet поднимает control plane с диска, до всякого api-server. Правда лежит в /etc/kubernetes/manifests, в etcd — зеркало.
  - **kubeadm init** **не ставит CNI.** Узлы NotReady до плагина — это ожидаемо.
  - **etcd — единственное, что не восстанавливается ничем, кроме снапшота.** Кворум N/2+1, число узлов нечётное.
  - **Сертификаты kubeadm живут год.** Кластер, который забыли, умирает по таймеру.
  - **Апгрейд: control plane → узлы, по одной минорной, через** **drain** **с оглядкой на PDB.**

  
  

# M23. CRD и операторы  

## **M23. CRD и операторы**

**Одной фразой:** CRD добавляет в API кластера **свой тип объекта**, оператор добавляет **контроллер, который его отрабатывает** — и вместе они превращают «инструкцию в вики» в reconcile-петлю.

⚠️ Модуль **не пройден на занятии** — справочная выжимка по карте курса.

### **ð§  Ментальная модель**

Ты уже пользуешься операторами каждый день, просто не называл их так: cert-manager, Prometheus Operator, ArgoCD, а на проде Clickadilla — **Deckhouse**, который выдаёт свой ClusterAuthorizationRule и генерирует из него обычные Role и RoleBinding. Оператор — это **упакованный опыт эксплуатации**: то, что дежурный делал бы руками по runbook'у, записано кодом и крутится в цикле.

Ключ: **CRD без контроллера — мёртвая запись в etcd.** api-server честно примет твой kind: Certificate, положит в базу и ничего не сделает. Всё, что «происходит», делает контроллер, который на этот тип смотрит. Отсюда вся диагностика операторов.

### **Что важно знать**

  - **CRD (****CustomResourceDefinition****)** — объект, который **регистрирует новый тип** в api-server: группу, версию, kind, схему полей (OpenAPI), область (namespaced/cluster). После установки твой тип неотличим от встроенного: работает kubectl get, describe, explain, RBAC, watch, метки, финализаторы (тема №2 в чистом виде).
  - **CR (custom resource)** — экземпляр этого типа. Certificate, Issuer, ServiceMonitor, Application — всё это CR.
  - **Оператор = CRD + контроллер.** Контроллер — обычный Deployment в кластере, который через watch следит за CR и **приводит внешний мир в соответствие** с ним: выпускает сертификат в Let's Encrypt, создаёт бэкап БД, конфигурирует Prometheus.
  - **status** **— способ оператора говорить с тобой.** Хорошо написанный оператор пишет в status.conditions (Ready, Issuing, причина и сообщение). Диагностика CR начинается **со status**, а не с логов.
  - **Лестница разбора чужого оператора** (та же, что в M19, просто этажом выше): describe \<cr\> → status + Events → **объекты, которые оператор создал по цепочке** → логи контроллера. У cert-manager цепочка буквально видна: Certificate → CertificateRequest → Order → Challenge.
  - **no matches for kind "X"** — CRD не установлен (или не той версии/группы). Классика при первом деплое и при GitOps без sync waves (M21).
  - **Финализаторы операторов** — оператор ставит финализатор на CR, чтобы успеть убрать внешний ресурс (облачный диск, DNS-запись, LB). Удалили оператор раньше CR → **объект висит в** **Terminating** **вечно**, снимать финализатор руками = осиротить внешний ресурс (M7).
  - **Admission webhooks — второй способ расширить кластер** (тема №7). **Mutating** дописывает/меняет объект (инъекция sidecar Istio/Linkerd, дефолты, Kyverno-mutate). **Validating** только выносит вердикт (Kyverno/Gatekeeper, PSA-подобные проверки). Порядок жёсткий: все mutating → schema → все validating.
  - **Webhook — это HTTPS-сервис в кластере**, на который api-server ходит при каждом подходящем запросе. Отсюда главная эксплуатационная опасность: **failurePolicy: Fail** **+ упавший webhook = блокировка всех попадающих под правило запросов.** Симптом: kubectl apply висит \~10 секунд и падает с failed calling webhook ... connection refused.
  - **Аварийный выход** — удалить ValidatingWebhookConfiguration / MutatingWebhookConfiguration (сам объект правила, не под). После починки оператор поставит его обратно.
  - **failurePolicy: Ignore** — противоположный размен: кластер продолжает работать, но политика молча не применяется. Для политик безопасности это дыра, для удобных мутаций — разумно.
  - **Reconcile-паттерн концептуально** (без Go): контроллер держит **informer** (watch + локальный кэш), при событии кладёт **ключ объекта** в очередь, воркер берёт ключ, читает **актуальное** состояние, сравнивает с желаемым, действует, пишет status. Отсюда два свойства: обработка **идемпотентна** (один и тот же объект может обрабатываться много раз) и **level-triggered**, а не edge-triggered — контроллер реагирует на *состояние*, а не на *факт события*, поэтому переживает пропущенные события и рестарты.
  - **Ошибки → экспоненциальный backoff** и повтор. Поэтому «оператор молчит» почти всегда значит: контроллер упал / не имеет прав / застрял на внешней зависимости.
  - **У оператора свой ServiceAccount и часто широкие права** (M16). Оператор, умеющий создавать поды и читать секреты во всех namespace, — это лакомая цель. Смотреть, что именно даёт его ClusterRole, — нормальная практика перед установкой.
  - **Operator Lifecycle Manager (OLM)** — надстройка для установки и обновления операторов (каталоги, версии, зависимости). В экосистеме OpenShift обязательна, в обычном кубе чаще ставят чартами.
  - **Когда оператор — оверинжиниринг.** Если задача решается Deployment'ом с конфигом или CronJob'ом — оператор не нужен: он добавляет CRD, контроллер, права и ещё одну вещь, которая может упасть. Оператор оправдан там, где есть **нетривиальная эксплуатация**: failover БД, ротация сертификатов, координация кластера с состоянием.

### **⭐ Бест-практис (golden path)**

  - **Пользоваться зрелыми операторами вместо своих** — дефолт: cert-manager, Prometheus Operator, CloudNativePG/Percona для БД, ArgoCD. Свой оператор пишут, когда своя доменная логика, а не когда «хочется красиво».
  - **Разбор CR всегда начинать со** **status** **и** **Events****, а не с логов контроллера** — status для этого и придуман; логи нужны, когда status пуст или врёт.
  - **CRD выкатывать отдельным шагом раньше CR** — sync waves в Argo или отдельный чарт. Иначе no matches for kind на чистом кластере.
  - **Webhook'и операторов исключать из своего же namespace** (namespaceSelector) — иначе упавший webhook не даёт поднять под, который его чинит. Классический deadlock.
  - **Перед установкой смотреть ClusterRole оператора** — least privilege применим и к операторам.
  - **failurePolicy: Fail** **для политик безопасности,** **Ignore** **для косметики** — осознанный выбор, а не значение по умолчанию.

### **ð§ Команды-первого-выбора**

kubectl get crd                                   \# сколько кастомных типов уже живёт в кластере

kubectl api-resources --api-group=cert-manager.io \# какие kind'ы дал конкретный оператор

kubectl explain certificate.spec                  \# у CRD тоже есть встроенная схема

kubectl describe certificate \<name\>               \# ⭐ ПЕРВЫЙ шаг: status.conditions + Events

kubectl get certificaterequest,order,challenge -A \# цепочка объектов, созданных оператором

kubectl logs -n cert-manager -l app=cert-manager --tail=100   \# reconcile глазами контроллера

kubectl get mutatingwebhookconfigurations,validatingwebhookconfigurations   \# кто влезает в запросы

kubectl get \<cr\> \<name\> -o jsonpath='{.metadata.finalizers}'  \# кто держит объект в Terminating

  

### **⚠️ Грабли и как не наступить**

  - **no matches for kind** → CRD не установлен или другая версия API. Ставить CRD раньше CR.
  - **CR создан, ничего не происходит,** **status** **пуст** → контроллер упал, не имеет прав или не установлен вовсе. Идти в логи контроллера и в его RBAC.
  - **kubectl apply** **виснет и падает с** **failed calling webhook** → под webhook'а недоступен при failurePolicy: Fail. Чинить сервис; в аварии — удалить объект ...WebhookConfiguration.
  - **CR висит в** **Terminating** **после удаления оператора** → финализатор снимать некому. Правильный порядок: сначала удалить CR, потом оператор.
  - **Удалили CRD — исчезли все CR этого типа** (каскадно, вместе с данными состояния). Необратимо.
  - **Оператор «дописал» поле, GitOps считает это дрейфом** → вечный OutOfSync в Argo (M21). Лечится игнорированием этих полей в конфигурации приложения.
  - **Sidecar не инжектнулся** → namespace без нужной метки/аннотации, либо mutating webhook упал, либо namespaceSelector не совпал (M25).

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Что такое оператор и зачем?»** → CRD (свой тип в API) + контроллер с reconcile-логикой. Смысл — закодировать эксплуатационные знания: failover, бэкапы, выпуск сертификатов. Ты чаще **пользуешься** операторами, чем пишешь.
  - **«Создал Certificate, серт не выпустился — куда смотришь?»** → describe certificate (status + Events) → цепочка CertificateRequest → Order → Challenge → логи cert-manager. Частая причина — ACME-челлендж не проходит (порт 80 перехвачен CDN → DNS-01).
  - **«Mutating vs validating webhook?»** → mutating меняет объект (инъекция sidecar, дефолты), validating только допускает или отклоняет. Все mutating идут раньше всех validating.
  - **«Почему упавший webhook блокирует деплои?»** → api-server обязан спросить его при failurePolicy: Fail; нет ответа — нет записи в etcd. Выход — удалить конфигурацию webhook'а.
  - **«Как понять, что делает незнакомый оператор в кластере?»** → get crd → api-resources по его группе → его ClusterRole (какие права взял) → его webhook-конфигурации (куда влезает).
  - **«Deckhouse на нашем проде — это что?»** → набор операторов: свои CRD (например, ClusterAuthorizationRule) + контроллеры, которые **генерируют** из них обычные объекты куба. Правишь CR — оператор перегенерирует Role/Binding; правишь Role руками — вернёт как было.

### **ð Связи**

  - **Опирается на:** M3 (объект API, spec/status, watch/informer, финализаторы, owner references), M4/M5 (контроллер как паттерн), M16 (SA и права операторов; три ступени), M18 (admission, Kyverno как валидирующий webhook), M19 (лестница диагностики), M20 (Prometheus Operator, ServiceMonitor), M21 (Argo — тоже оператор; CRD и sync waves).
  - **Ведёт к:** M25 (инъекция sidecar — mutating webhook; Istio/Linkerd как операторы), финальный чекпоинт.
  - **Сквозные темы:** №2 (всё — объект API, включая твои собственные типы), №4 (контроллер как универсальный паттерн — кульминация), №7 (admission webhooks — третья ступень), №1 (reconcile для произвольной доменной логики).

### **ð Что должно остаться в голове через полгода**

  - **CRD без контроллера — мёртвая запись.** api-server примет объект и не сделает ничего.
  - **Диагностика оператора:** **status** **→ Events → порождённые объекты → логи контроллера.** Та же лестница M19, только этажом выше.
  - **Упавший webhook с** **failurePolicy: Fail** **блокирует запись объектов.** Аварийный выход — удалить конфигурацию webhook'а, а не под.
  - **Финализатор оператора + удалённый оператор = вечный** **Terminating****.** Порядок удаления имеет значение.
  - **Контроллеры level-triggered и идемпотентны** — реагируют на состояние, а не на событие; поэтому переживают рестарты и пропущенные события.

  
  
  

# M24. Продвинутая сеть: eBPF и Cilium  

## **M24. Продвинутая сеть: eBPF и Cilium**

**Одной фразой:** eBPF позволяет положить логику Service, политик и наблюдаемости **прямо в ядро**, минуя длинные цепочки iptables — и заодно перевести правила с эфемерных IP на устойчивые identity.

⚠️ Модуль **не пройден на занятии** — справочная выжимка по карте курса.

### **ð§  Ментальная модель**

Всё в этом модуле растёт из одной боли: **iptables — это линейный список правил, который перечитывается и перезаписывается целиком.** Пока сервисов десятки, это незаметно. На тысячах — каждая перезапись становится дорогой, а поиск правила линейным. eBPF отвечает на это иначе: вместо списка правил в ядро загружается **программа с хэш-таблицами**, которая делает подстановку адреса за константное время, и обновляется точечно, а не целиком.

Второй сдвиг важнее первого: в мире, где под живёт минуты, **правило, привязанное к IP, устарело в момент написания**. Cilium привязывает политику к **identity** — устойчивому набору меток, — и IP перестаёт быть носителем смысла (тема №3 и №5 вместе).

### **Что важно знать**

  - **Проблема iptables-режима kube-proxy** — правила образуют цепочки, поиск линейный, а обновление требует перезаписи большого блока. При тысячах сервисов и частых изменениях эндпоинтов растёт и латентность программирования правил, и нагрузка на узел. **Функционально всё работает — деградирует масштаб.**
  - **IPVS-режим — первый ответ на ту же боль**: правила лежат в хэш-таблице ядра, поиск константный, доступны настоящие алгоритмы балансировки (rr, lc, sh). Всё ещё kube-proxy, всё ещё L4. Дефолтом не стал по историческим и совместимостным причинам.
  - **eBPF — третий ответ.** Верифицируемые программы, загружаемые в ядро **без модулей и без перезагрузки**, с хуками в разных точках (сетевой путь, сисколы, tracepoints). Ядро проверяет программу на завершаемость и безопасность памяти перед загрузкой — поэтому это не «модуль ядра, который может уронить хост».
  - **Cilium может полностью заменить kube-proxy** (kubeProxyReplacement): подстановка ClusterIP → pod IP делается eBPF-программой на хуке сокета/XDP, iptables для сервисов не нужен. Побочный выигрыш: DNAT происходит раньше в стеке, часть накладных расходов исчезает.
  - **Identity-based политики — главное концептуальное отличие.** Cilium вычисляет для каждого набора меток **числовой identity** и раздаёт его по кластеру; правила пишутся между identity. Под пересоздался, IP сменился — identity тот же, правило работает. Обычная NetworkPolicy тоже пишется по меткам, но **исполняется** через развёртывание в IP-адреса; на масштабе и при частых пересозданиях это дороже.
  - **L7-политики** — CiliumNetworkPolicy умеет то, чего штатная NetworkPolicy не умеет в принципе: разрешить GET /api/v1/\* и запретить POST, разрешить конкретные gRPC-методы, ограничить Kafka-топики, фильтровать по DNS-именам (toFQDNs: api.stripe.com). Штатная политика оперирует только L3/L4.
  - **Штатная** **NetworkPolicy** **при этом продолжает работать** — Cilium её реализует. L7 требует своего CRD, потому что стандарту такого поля просто нет.
  - **Hubble** — наблюдаемость поверх той же eBPF-инфраструктуры: **кто с кем говорит, по какому протоколу, разрешено или отброшено, каким правилом**. Это тот самый ответ на вопрос «политику написал — а она вообще применяется?», который на обычном CNI решается только tcpdump'ом. Плюс сервисная карта в UI.
  - **Тихий отказ, который лечит Hubble** — на kindnet/Flannel объект NetworkPolicy принимается api-server и **не исполняется никем**; ошибки нет нигде (M18). В Cilium дроп виден как событие с указанием политики.
  - **Оси сравнения CNI** — **режим доставки** (overlay/VXLAN vs native routing vs BGP) · **policy** (нет / L3-L4 / L3-L7) · **datapath** (iptables vs eBPF) · **масштаб и наблюдаемость**. Flannel: overlay, без политик, просто. Calico: routing/BGP или overlay, зрелые политики, опционально eBPF. Cilium: eBPF, L7-политики, Hubble, замена kube-proxy. kindnet: только для лабы.
  - **BGP-режим** (Calico и Cilium) — узлы **анонсируют маршруты к своим pod CIDR** соседям по BGP, физическая сеть узнаёт о подах, инкапсуляция не нужна, MTU не режется. Это ровно то, что ты проходил в курсе по сетям, только с подами вместо офисных подсетей. Он же даёт замену MetalLB: анонс сервисных адресов наружу.
  - **Требования и цена** — eBPF-датаплейн хочет **свежее ядро** (чем новее, тем больше фич доступно; часть возможностей отключается на старых ядрах и молча деградирует в iptables-совместимый режим). Hubble на больших кластерах даёт заметный оверхед — его включают выборочно.
  - **eBPF шире сети** — Tetragon/Falco используют те же хуки для runtime-безопасности (кто запустил процесс, кто открыл файл), Pixie/Parca — для профилирования и трейсинга без инструментирования кода. Сеть — просто первое массовое применение.

### **⭐ Бест-практис (golden path)**

  - **Для нового кластера, где нужны политики и наблюдаемость, — Cilium** (частый современный дефолт). Calico — когда нужен зрелый BGP, on-prem-интеграция или консервативный стек. Flannel — когда политики не нужны вовсе.
  - **Один CNI на кластер.** Смешивать нельзя: два плагина будут спорить за netns и маршруты.
  - **kubeProxyReplacement** **включать осознанно** — выигрыш заметен на масштабе; на кластере из трёх узлов это скорее про изучение, чем про производительность.
  - **Hubble включать точечно** (на время расследования или с семплированием), а не всегда и везде.
  - **Начинать с обычной** **NetworkPolicy****, переходить на** **CiliumNetworkPolicy** **только когда нужен L7 или FQDN** — переносимость дороже, чем кажется.
  - **cilium connectivity test** **после установки** — дефолт: он ловит проблемы датаплейна до того, как их найдут приложения.

### **ð§ Команды-первого-выбора**

kind create cluster --config kind-nocni.yaml     \# кластер БЕЗ дефолтного CNI (иначе конфликт)

cilium install && cilium status                  \# установка + сводка датаплейна

cilium connectivity test                         \# встроенный тест сети (долгий, но честный)

cilium hubble enable --ui                        \# включить наблюдаемость

hubble observe --follow                          \# живой поток: кто с кем говорит

hubble observe --verdict DROPPED                 \# ⭐ только отброшенное — и каким правилом

kubectl get ciliumnetworkpolicies -A             \# L7-политики (обычные netpol — get netpol)

kubectl -n kube-system exec ds/cilium -- cilium-dbg endpoint list   \# identity каждого пода

  

### **⚠️ Грабли и как не наступить**

  - **Поставил Cilium поверх работающего CNI** → конфликт датаплейнов, поды без сети. Кластер поднимается **без** CNI, плагин один.
  - **eBPF-фичи молча не включились** → старое ядро; Cilium деградирует в совместимый режим. Проверять cilium status — там видно, что реально активно.
  - **Ждёшь от kindnet/Flannel того, что умеет только Cilium/Calico** → политика принята и не работает (M18). Смотреть, какой CNI стоит, а не наличие объекта.
  - **Hubble включён везде на большом кластере** → заметный оверхед по CPU и памяти на узлах.
  - **Написал** **CiliumNetworkPolicy** **с L7 и переехал на другой кластер** → CRD там нет, политика не применяется. Переносимость теряется вместе с L7.
  - **Закрыл egress, забыл DNS** → та же грабля, что в M18, и в Cilium она заметнее: с toFQDNs политика **сама** зависит от DNS-прокси.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Что даёт eBPF против iptables в kube-proxy?»** → константный поиск вместо линейного и точечное обновление вместо перезаписи цепочек; выигрыш проявляется на масштабе сервисов и частых изменениях эндпоинтов. IPVS — промежуточный ответ на ту же боль.
  - **«Чем identity-based политика лучше IP-based?»** → правило привязано к устойчивому набору меток, а не к эфемерному IP; при пересоздании подов ничего не протухает. Темы №3 и №5.
  - **«Что умеет CiliumNetworkPolicy сверх обычной?»** → L7: HTTP-методы и пути, gRPC-методы, Kafka-топики, toFQDNs для внешних доменов.
  - **«Как убедиться, что политика реально применяется?»** → Hubble: hubble observe --verdict DROPPED покажет и факт дропа, и правило. На обычном CNI это слепая зона.
  - **«Overlay или BGP?»** → overlay работает поверх любой сети, но платит MTU и инкапсуляцией; BGP/native routing быстрее и прозрачнее, но требует, чтобы сеть знала маршруты к pod CIDR.

### **ð Связи**

  - **Опирается на:** M9 (модель сети, CNI, overlay vs routing, MTU), M10 (kube-proxy, ClusterIP как правило DNAT — здесь его заменяют), M18 (NetworkPolicy и тихий отказ без поддержки CNI), M11 (DNS — на нём стоят FQDN-политики), курс по сетям (BGP, netfilter, инкапсуляция).
  - **Ведёт к:** M25 (Cilium mesh и sidecarless — прямое продолжение), M20 (Hubble как ещё один слой наблюдаемости), M22 (выбор CNI при сборке кластера).
  - **Сквозные темы:** №5 (сетевая модель — кульминация), №3 (метки как клей, доведённые до identity), №4 (cilium-agent — контроллер: watch → программирование ядра), №7 (политики как периметр).

### **ð Что должно остаться в голове через полгода**

  - **Проблема iptables — не корректность, а масштаб:** линейный поиск и перезапись цепочек. IPVS и eBPF — два ответа на одну боль.
  - **eBPF — программы в ядре без модулей**, проверяемые верификатором; сеть лишь первое их применение (есть ещё безопасность и профилирование).
  - **Identity вместо IP** — правило переживает пересоздание пода. Это главное концептуальное отличие Cilium.
  - **L7-политики и** **toFQDNs** **— только через CRD Cilium**, стандартная NetworkPolicy этого не умеет и не будет.
  - **Hubble отвечает на вопрос «применяется ли политика»**, который на обычном CNI не имеет ответа без tcpdump.

  
  

# M25. Service Mesh  

## **M25. Service Mesh**

**Одной фразой:** вынести из кода приложений то, что каждое из них всё равно реализует по-своему — mTLS, ретраи, таймауты, метрики, управление трафиком — и отдать это прокси-слою, которым управляет отдельный control plane.

⚠️ Модуль **не пройден на занятии** — справочная выжимка по карте курса.

### **ð§  Ментальная модель**

Ingress решает задачу «снаружи внутрь» (north-south). Mesh решает «внутри между сервисами» (east-west). Механика та же самая, что у ingress-контроллера: **есть прокси, который реально гоняет трафик (data plane), и есть контроллер, который его конфигурирует по объектам API (control plane)** — тема №4 в очередной раз. Разница в том, что прокси не один на входе, а рядом с каждым приложением.

И главное, что стоит держать в голове: **mesh — это не фича, а налог.** Он покупает шифрование, отказоустойчивость и наблюдаемость ценой латентности, ресурсов и операционной сложности. Вопрос «нужен ли mesh» — это всегда вопрос, окупается ли налог.

### **Что важно знать**

  - **Что mesh даёт без правки кода** — **mTLS** между всеми сервисами · **ретраи, таймауты, circuit breaking, outlier detection** · **traffic shifting** (canary, blue-green, A/B, зеркалирование) · **golden signals и трейсы** для каждого хопа автоматически. Приложение продолжает говорить обычный HTTP на localhost.
  - **Data plane — обычно Envoy** (Linkerd использует свой лёгкий прокси на Rust). Прокси перехватывает весь входящий и исходящий трафик пода и применяет к нему политику.
  - **Control plane** (istiod, linkerd-destination) — watch'ит объекты API и **раздаёт прокси конфигурацию**. Прокси сами по себе ничего не решают: упал control plane — существующие соединения продолжают работать по последней известной конфигурации, но новые изменения не приезжают.
  - **Sidecar-модель** — прокси-контейнер в каждом поде, инжектится **mutating admission webhook'ом** (M23) по метке на namespace или поде. Трафик заворачивается в него через iptables-правила init-контейнера. Отсюда: пересоздание всех подов при включении mesh, +1 контейнер в каждом поде, ресурсы и латентность на каждый хоп.
  - **Ambient / sidecarless — куда идёт индустрия.** Istio ambient разделяет функции: L4 (mTLS, идентичность, базовая телеметрия) обслуживает **ztunnel — один агент на узел**, а L7-функции включаются точечно через **waypoint-прокси на namespace/сервис**. Cilium делает похожее на eBPF. Мотив один: сайдкар в каждом поде оказался слишком дорогим и слишком инвазивным (рестарты подов при апгрейде mesh, проблемы с Job'ами, порядок старта).
  - **Плата за ambient — другая модель отладки:** трафик идёт не «в моём поде», а через узловой агент; привычные приёмы (посмотреть логи сайдкара рядом) не работают.
  - **mTLS и identity** — каждый воркоад получает **криптографическую идентичность** (в Istio — SPIFFE-идентификатор, привязанный к ServiceAccount, M16), сертификаты выпускаются и **ротируются автоматически** (часы, не месяцы). Политики пишутся не «с этого IP», а «этому сервису можно вызывать вот тот». Это и есть zero-trust внутри кластера.
  - **mTLS-режимы** — PERMISSIVE (принимает и plaintext, и mTLS — нужен для миграции) и STRICT. Переключение сразу в STRICT на живом кластере ломает всё, что ещё не в mesh.
  - **Traffic management** — canary по весам (90/10 с плавным сдвигом), A/B по заголовкам, **зеркалирование** (копия боевого трафика в новую версию без влияния на ответ пользователю), **fault injection** (искусственные задержки и ошибки для проверки устойчивости). Зеркалирование и fault injection — то, чего ingress-аннотациями не сделать.
  - **Istio vs Linkerd vs Cilium mesh** — **Istio**: максимум возможностей, Envoy, ambient-режим, самый сложный и самый распространённый в крупных компаниях. **Linkerd**: минимализм, свой лёгкий прокси, лучший «включил и работает», меньше фич traffic management. **Cilium mesh**: переиспользует eBPF-датаплейн (M24), sidecarless по природе, привлекателен если Cilium уже стоит.
  - **Mesh vs Ingress vs Gateway API** — Ingress/Gateway: вход **снаружи** (north-south). Mesh: трафик **между** сервисами (east-west). Пересечение — mesh-gateway, который может выполнять роль входа. Gateway API постепенно становится общим языком для обоих (в Istio — Gateway API вместо своих VirtualService).
  - **Честная цена** — латентность **на каждый хоп** (сайдкар добавляет один-два прокси в путь запроса; для цепочки из пяти сервисов это умножается) · CPU и память на каждый прокси · операционная сложность (ещё один control plane, свои CRD, свои сбои) · более трудная отладка.
  - **Когда mesh НЕ нужен** — сервисов мало и вызовы простые · нужен только mTLS (дешевле взять Linkerd, Cilium mTLS или вообще TLS в приложении) · нужны только ретраи и таймауты (это библиотека в коде или ingress) · команда не готова эксплуатировать ещё один слой. **Mesh «потому что модно» — классическая ошибка.**

### **⭐ Бест-практис (golden path)**

  - **Начинать с Linkerd, если задача — mTLS и базовые golden signals** (частый совет): он ставится и эксплуатируется заметно проще. Istio берут, когда действительно нужен богатый traffic management или уже есть экспертиза.
  - **Если Cilium уже стоит — сначала смотреть его mesh**, а не тащить второй датаплейн.
  - **Внедрять по одному namespace**, начиная с некритичного, и **mTLS через** **PERMISSIVE** **→** **STRICT** — тот же принцип постепенности, что Audit → Enforce у политик (M18).
  - **Не включать mesh ради одной фичи** — сначала честно спросить, решается ли она ingress-аннотацией, библиотекой или NetworkPolicy + cert-manager.
  - **Ambient/sidecarless как направление по умолчанию для новых внедрений** — индустрия идёт туда; но это молодой режим, и отладка в нём другая.
  - **Ресурсные лимиты на сайдкары задавать явно** — иначе прокси конкурируют с приложением за CPU и создают латентность, которую потом ищут в коде.

### **ð§ Команды-первого-выбора**

linkerd install --crds | kubectl apply -f -      \# CRD отдельным шагом (M23: CRD раньше CR)

linkerd install | kubectl apply -f -

linkerd check                                    \# ⭐ первая команда при любой проблеме

kubectl annotate namespace \<ns\> linkerd.io/inject=enabled

kubectl rollout restart deployment -n \<ns\>       \# поды пересоздаются УЖЕ с сайдкаром

linkerd viz stat deploy -n \<ns\>                  \# success rate, RPS, latency — без строчки кода

linkerd viz tap deploy/web                       \# живой трафик по запросам

kubectl get pod \<p\> -o jsonpath='{.spec.containers\[\*\].name}'   \# инжектнулся ли прокси вообще

istioctl proxy-config routes \<pod\>               \# что реально приехало в Envoy (Istio)

  

### **⚠️ Грабли и как не наступить**

  - **Сайдкар не инжектнулся** → namespace без метки/аннотации · поды не пересозданы после включения · mutating webhook недоступен (M23). Проверять список контейнеров пода.
  - **Включили** **STRICT** **mTLS сразу** → всё, что вне mesh (legacy-сервисы, health-чеки, скрейпинг Prometheus), отваливается. Только через PERMISSIVE.
  - **Mesh mTLS дерётся с NetworkPolicy** → политика видит трафик от sidecar/ztunnel, а не «от пода к поду», и правила по портам перестают совпадать. Два периметра надо проектировать вместе (M18).
  - **Латентность выросла после внедрения** → это ожидаемо, вопрос лишь в величине. Мерить до и после, а не удивляться постфактум.
  - **Job'ы не завершаются** → классическая проблема sidecar-модели: main отработал, прокси живёт. Лечится нативными sidecar-контейнерами (init + restartPolicy: Always, M4) или исключением Job'ов из инжекции.
  - **Апгрейд mesh требует рестарта всех подов** → в sidecar-модели прокси обновляется только с пересозданием пода. Один из главных мотивов ухода в ambient.
  - **Отладка в ambient идёт не там, где привыкли** → трафик обрабатывает узловой ztunnel, а не контейнер в поде.

### **ð¯ Ситуации (для собеса/дежурства)**

  - **«Зачем нужен service mesh?»** → mTLS, устойчивость (ретраи/таймауты/circuit breaking), traffic management и observability — **без правки кода приложений**. Механически это data plane (прокси) + control plane (конфигуратор), тот же паттерн, что ingress-контроллер, но east-west.
  - **«Нужен только mTLS между тремя сервисами — брать Istio?»** → скорее нет. Дешевле Linkerd, Cilium mTLS или вообще TLS в приложении. Istio оправдан богатым traffic management. Всегда взвешивать латентность и сложность.
  - **«Sidecar vs ambient?»** → sidecar: прокси в каждом поде, максимум возможностей, дорого и требует рестартов. Ambient: L4 на узловом агенте, L7 точечно через waypoint — дешевле и менее инвазивно, но моложе и отлаживается иначе.
  - **«Как sidecar попадает в под?»** → mutating admission webhook по метке namespace (M23). Отсюда и типовой отказ: упал webhook — не инжектится.
  - **«Mesh или Ingress?»** → Ingress — вход снаружи (north-south), mesh — трафик между сервисами (east-west). Это не конкуренты; Gateway API постепенно становится общим языком.
  - **«Как выкатить canary?»** → веса в mesh (или ingress-аннотациями), решение о продвижении — по метрикам (M20), автоматизация — Argo Rollouts/Flagger (M21).

### **ð Связи**

  - **Опирается на:** M10 (Service и балансировка на коннект — mesh решает ровно проблему gRPC/HTTP2), M12 (ingress-контроллер как data/control plane; Gateway API), M16 (ServiceAccount как основа идентичности воркоада), M18 (NetworkPolicy как второй периметр), M23 (mutating webhook — механизм инжекции), M24 (Cilium mesh, sidecarless), сети (mTLS, TLS-хендшейк).
  - **Ведёт к:** финальный чекпоинт; практика прогрессивной доставки (M21).
  - **Сквозные темы:** №4 (control plane конфигурирует data plane — паттерн в третий раз), №5 (ещё один слой поверх плоской сети), №7 (identity и zero-trust между сервисами), №3 (селекторы по меткам во всех политиках mesh).

### **ð Что должно остаться в голове через полгода**

  - **Mesh = data plane (прокси у каждого воркоада) + control plane (конфигуратор).** Тот же паттерн, что ingress, только east-west.
  - **Он даёт mTLS, устойчивость, traffic management и телеметрию без правки кода** — и берёт за это латентностью, ресурсами и сложностью.
  - **Sidecar инжектится mutating webhook'ом** и требует пересоздания подов; ambient/sidecarless — то, куда индустрия уходит именно из-за этой цены.
  - **mTLS внедряется через** **PERMISSIVE** **→** **STRICT**, иначе ломается всё, что вне mesh.
  - **Правильный ответ на «нужен ли mesh» чаще «нет»**: для чистого mTLS есть варианты дешевле, для ретраев — библиотека или ingress. Mesh оправдан, когда нужен весь пакет сразу и есть кому его эксплуатировать.

# **Памятка-оси: как выводить ответ, а не вспоминать**

Ты просил собрать это к концу курса. Смысл файла — **не факты, а вопросы**, которые задаёшь себе, когда факт не вспомнился. Почти любой вопрос по кубу (и на собесе, и в 4 утра на дежурстве) раскладывается по этим осям.

Это же лекарство от твоей корневой ошибки: **вывод верный, актор неверный.**

## **1. Кто актор?**

Первый и главный вопрос. Куб намеренно разделён на компоненты, и почти всё «странное поведение» объясняется тем, **кто именно** это сделал.

|  |  |  |
| :-: | :-: | :-: |
| \*\*Актор\*\* | \*\*Что делает\*\* | \*\*Что НЕ делает\*\* |
| \*\*api-server\*\* | принимает, валидирует, пишет в etcd | ничего не запускает |
| \*\*scheduler\*\* | выбирает узел, проставляет nodeName | не запускает под, не следит за ним |
| \*\*kubelet\*\* | запускает контейнеры, следит, репортит status, монтирует тома, читает Secret'ы | не создаёт объекты подов |
| \*\*controller-manager\*\* | пачка контроллеров: RS, endpointslice, node-ipam, PV | не принимает решения о размещении |
| \*\*container runtime\*\* (containerd) | создаёт sandbox и контейнеры, зовёт CNI-плагин | не знает про поды и Service |
| \*\*CNI-плагин\*\* (бинарь) | даёт поду IP, veth, маршрут — один раз при создании | не живёт постоянно |
| \*\*CNI-агент\*\* (DaemonSet) | маршруты к чужим узлам, \*\*фильтрация пакетов по политикам\*\* | не выдаёт IP каждому поду сам |
| \*\*kube-proxy\*\* | пишет правила DNAT в ядро | \*\*не пропускает трафик через себя\*\* |
| \*\*CoreDNS\*\* | резолвит имя → ClusterIP | на пути пакета его нет вообще |
| \*\*ядро (netfilter/cgroups)\*\* | исполняет правила, убивает по OOM, троттлит CPU | не знает слов «под» и «namespace куба» |
| \*\*HPA / VPA / CA\*\* | число реплик / размер пода / число узлов | все трое считают \*\*брони\*\* |
| \*\*admission-плагины и webhook'и\*\* | мутируют и валидируют объект при записи | не следят за объектом дальше |

**Твои исторические ловушки:** NetworkPolicy применяет **CNI-агент**, а не CoreDNS · подсети узлам режет **node-ipam-controller**, а не CNI · PV создаёт **external-provisioner**, а не kubelet · под убивает при OOM **ядро**, а выселяет при node pressure **kubelet**.

## **2. Смотрит на брони или на факт?**

  - **Брони (****requests****):** scheduler, Cluster Autoscaler, ResourceQuota, describe node → Allocated resources.
  - **Факт:** kubectl top, ядро при OOM, kubelet при eviction, HPA (но делит факт **на брони**).

Отсюда сразу: «узлы пустые по top, а под Pending» и «CA докинул узел на пустом кластере» — это не парадокс, а разные оси.

## **3. Момент или непрерывно?**

  - **Один раз, при записи объекта:** admission (mutating и validating), defaulting, ResourceQuota, PSA.
  - **Один раз, при размещении:** scheduler, preemption.
  - **Непрерывно:** все контроллеры, kubelet, eviction, kube-proxy, CNI-агент (на каждом пакете).

Практический вывод: **объект, уже лежащий в etcd, новая политика не тронет.** Включил PSA enforce — работающие поды продолжат работать, упадёт только следующее создание.

## **4. Жёсткое или мягкое?**

|  |  |  |
| :-: | :-: | :-: |
| \*\*Механизм\*\* | \*\*Жёстко (→ Pending / отказ)\*\* | \*\*Мягко\*\* |
| affinity | requiredDuringScheduling... | preferredDuringScheduling... |
| taint | NoSchedule / NoExecute | PreferNoSchedule |
| topology spread | DoNotSchedule | ScheduleAnyway |
| PSA / политики | enforce | warn / audit |
| webhook | failurePolicy: Fail | Ignore |

NoExecute — единственный, кто трогает **уже работающие** поды.

## **5. Ссылка по ИМЕНИ или по МЕТКАМ? ⭐⭐ (твоя главная мина)**

**Правило вывода, а не запоминания:**

  - Объект **один и конкретный** → **имя**: serviceAccountName, roleRef, subjects\[\].name, scaleTargetRef, ownerReferences, secretRef, configMapRef, ingressClassName, storageClassName.
  - Объектов **сколько угодно и они пересоздаются** → **метки**: Service.selector, Deployment.selector, NetworkPolicy.podSelector, nodeSelector, ServiceMonitor.selector, PSS-лейблы на namespace.

**Вся цепочка RBAC — чистые имена, ни одной метки:** Pod --serviceAccountName--\> SA \<--subjects\[\].name-- RoleBinding --roleRef--\> Role

**Единственное известное исключение:** aggregated ClusterRoles собираются **по метке** rbac.authorization.k8s.io/aggregate-to-\*.

## **6. Кто на что вешается?**

taint → **узел** · toleration → **под** · PSS-лейбл → **namespace** · quota/LimitRange → **namespace** · PDB → **набор подов** · finalizer → **сам объект**.

## **7. На каком слое живёт симптом?**

Ошибка «инструмент не того слоя» — вторая по частоте после ошибки актора.

  - **Имя не резолвится** → пакета ещё нет. traceroute бесполезен, нужен nslookup и resolv.conf.
  - **404 от ingress** → L7, пакеты давно доехали. Смотреть объект Ingress, не сеть.
  - **502 от ingress** → правило нашлось, рвётся ниже: эндпоинты, порт, приложение.
  - **Таймаут** → пакет **дропнули** (NetworkPolicy, firewall).
  - **connection refused** → пакет **доехал**: порт закрыт, приложение лежит, или за сервисом нет эндпоинтов.
  - **NXDOMAIN** → CoreDNS **ответил**, виновато имя (кросс-namespace нужен FQDN).
  - **Таймаут DNS** → до CoreDNS **не дошли**: упал, режет egress по UDP/53, resolv.conf не туда.

## **8. На какой ступени лестницы встало? (диагностика)**

|  |  |  |
| :-: | :-: | :-: |
| \*\*Стадия\*\* | \*\*Актор\*\* | \*\*Где ошибка\*\* |
| объекта пода нет | admission | describe rs ⭐ |
| Pending | scheduler | describe pod → FailedScheduling |
| ContainerCreating / CreateContainerConfigError | kubelet | describe pod → Events |
| процесс умер | приложение / ядро | logs --previous + Last State |
| процесс жив, трафика нет | клей / сеть | get endpointslices, readiness |

**logs** **работают только с четвёртой строки.** Выше контейнера не существует. **Нет объекта → иди к владельцу.**

## **9. На какой фазе обработки запроса?**

authn → authz → **defaulting** → **mutating admission** → schema → **validating admission** → **etcd**

Следствия: limits без requests превращается в requests = limits **до** LimitRange · сначала все mutating, потом все validating · **runAsNonRoot** **— единственная проверка безопасности вне admission**, её делает kubelet на узле.

## **10. Проверка или подстановка?**

  - **Подстановка (mutating):** LimitRange, defaulting, инъекция sidecar, Kyverno-mutate.
  - **Проверка (validating):** ResourceQuota, PSA, Kyverno-validate, runAsNonRoot (но на узле).

## **11. Область — namespace или кластер?**

**Область задаёт БИНДИНГ, а не роль.** ClusterRole + RoleBinding = кластерная роль, запертая в один namespace (рабочий дефолт). Обратной комбинации не существует.

Cluster-scope объекты: Node, PV, StorageClass, Namespace, CRD, ClusterRole(Binding), IngressClass, PSS — нет (это лейбл на ns).

## **12. Объект принят ≠ механизм работает**

NetworkPolicy без поддерживающего CNI · подпись образа без проверки на admission · PDB без второй реплики · HPA без requests · Ingress без контроллера. **Во всех случаях api-server принимает объект и никто не сообщает об ошибке.** Тихий отказ — самый дорогой класс.

## **13. Пропорция или инкремент?**

HPA — **пропорция**: ceil(текущие × факт/цель), вверх мгновенно, вниз через окно стабилизации (\~300с). Не «добавить одну реплику».

## **14. Объект в etcd или строка из документа?**

**ServiceAccount существует, User — нет.** Имя человека приезжает в сертификате (CN), группы — в O, и живут только на время обработки запроса. Отсюда: юзера нельзя удалить и нельзя получить список; отзыв доступа = снести биндинги или ротировать CA.
